# 软件 MVP 后端基础设施协作计划

编写日期：2026-10-13。源码核对基线：`a406df1f` 及编写时的工作树。

本文供负责后端基础设施的会话与负责 MVP 主线的 agent 分工使用。
它是一份开发计划，不是实现记录，也不代表以下任务已获开发或数据库操作授权。
当前有其他会话正在修改账户、契约和前端代码；正式开工时必须重新确认相关文件，不能把这里的源码快照当成永久事实。

## 1. 这份计划要解决什么问题

主线 agent 要把用户操作做通：登录、建立团队、登记材料、入库、流转、审批和查看待办。
本会话负责让这些操作有可靠的公共支撑，避免每个业务模块都重新写一次邮件发送、权限检查、审计和文件上传。

**分工原则是：这里负责公共机制，主线负责业务规则和完整用户操作。**

例如，公共权限模块可以回答“这个人在当前工作区能否执行这个动作”，但不能替产品决定谁可以审批、能否自审。
公共文件模块可以管理上传和绑定，但不能替材料模块决定允许上传什么附件。

这也不意味着所有基础设施都必须先写完。
第一阶段只补眼前流程会用到的能力，后面的工作随着主线推进再启动。
计划中出现的目录不必全部填满；已有代码能解决问题，就直接复用。

## 3. 两边具体怎么分工

### 本会话负责

- 公共能力的接口、实现、生命周期、必要配置和技术错误处理。
- 说明这些接口需要什么前提、什么时候会失败、是否参与当前事务。
- 检查公共实现的隔离、并发、回滚、重试和退出行为。
- 给出真实可调用的例子、接入步骤和验证记录，而不是只交一批类型和空类。

### 主线 agent 负责

- 产品规则、业务输入输出、业务权限清单和各模块的操作编排。
- 在真实用例中调用公共能力，并完成 Controller、共享契约、前端接入。
- 决定哪些业务事实要进入审计、哪些参数算同一次请求、什么资源属于哪个工作区。
- 完成跨模块流程验收，并统一更新主工作计划的状态。

### 不能只按目录认领工作

`core/identity`、`core/access`、`core/tenant` 等也包含主线正在依赖的业务能力。
它们位于 Core，并不意味着全部交给本会话。
业务模块中的存储树 SQL 虽然是技术实现，也不因此搬进通用 Database 模块。

每次开工先写清楚具体文件和接口由谁修改。
同一项工作若需要两边修改同一个文件，先约定修改次序，避免互相覆盖。
不恢复或删除另一边的在途改动。

### 代码主要放在哪里

下面是接入时的主要位置，不是要求预先创建全部文件。
路径相对 `packages/backend/`；新的公开请求/响应契约仍放在 `packages/contract/`。

## 5. 每个工作包做到哪里

### I01：把现有邮件模块补到能放心使用

**为什么现在做：** P02 要发恢复链接，P06 也需要邀请邮件。已有发送方法能复用，但技术失败的处理需要明确。

**本会话要做：**

1. 核对 SMTP 必需配置、端口、TLS 与认证组合；配置错误在可排查的位置失败，不等用户第一次恢复密码才发现。
2. 为连接、握手和发送等待设置明确上限；需要取消或关闭时，说明底层连接如何结束。
3. 把已知供应商错误转换成邮件模块自己的错误。调用方能区分配置问题、明确拒收、暂时不可用和发送结果不确定，不接触 Nodemailer 错误细节。
4. 只向调用方暴露应用所需的发送输入与结果，不导出原生 Transporter。SMTP 接受邮件不等于收件人已收到邮件。
5. 补关闭处理和必要的英文日志；日志不包含密码、完整恢复链接、凭据或正文。不因这一项重做日志系统。
6. 明确自动重试边界。连接中断可能发生在服务器已经接收邮件之后，不能默认当作“没发出去”并无限重发。

**主线要提供：** 发件身份、邮件模板与链接、是否必须自动可靠重试、发送失败的用户提示、重新申请规则。
恢复凭据的生成、保存、过期和消费仍属于 Identity/Auth；邮件模块不自己查用户或修改凭据。

**交付物：** 可直接调用的 Mail 模块、配置说明、错误语义、发送与关闭的验证记录。

**完成标准：** 合成邮件能被测试 SMTP 接受；配置错误、拒收、超时和关闭都符合约定；日志无凭据。
只能验证本地测试 SMTP 时，要明确“未验证实际邮件投递”，不能宣称已进入收件箱。

**先不做：** 多供应商路由、营销邮件平台、模板编辑器。若主线要求可靠后台重试，另外启动 I09。

2026-10-13，I01 邮件公共能力已交付。接口、内部兼容性变化、合成 SMTP/TLS 验证与真实投递边界见
[I01 实施记录](mvp-i01-mail-2026-10-13.md)。未接入 P02/P06 业务，不据此修改主任务完成状态。

### I02：让关键业务操作与审计一起提交

**为什么做：** 建立团队、修改成员和入库都需要留下操作者与历史，不能等库存模块完成以后才补。

**本会话要做：**

1. 实现最小审计写入，使用现有 `AuditEvent` 和必要的资源引用，不再建第二份历史事实。
2. 输入明确包含组织、可选工作区、操作者、动作、发生时间、允许保存的详情及资源快照。请求 ID 可用于排查，但不把整个请求上下文塞进详情。
3. 必须与业务保持一致的审计加入同一数据库事务；业务回滚时审计一起回滚，审计写入失败时也不能留下未经审计的成功结果。
4. 校验所引用资源与事件的组织一致，保留事件当时的名称快照；资源改名后不重写旧审计。
5. 不自动抓取完整请求体。公共层检查结构与安全上限，业务层按明确字段挑选详情，凭据和私密内容不进入历史。
6. 为后续按组织、工作区、对象和时间读取提供必要能力；第一批先满足 P04，不提前建设全域审计分析平台。

**主线要提供：** 动作名称、哪些结果必须审计、允许保存的字段、操作者及查询权限。
P04 的组织管理事件可以先记录组织/工作区与安全详情，不为了引用审计而强迫所有管理对象变成 Resource。

**交付物：** 最小审计写入接口、P04 接入例子、回滚与字段安全的验证记录。

**完成标准：** 一次成功操作对应约定审计；人为制造业务或审计失败时两者都不落库；跨组织引用被拒绝；敏感字段不会被自动记录。

**先不做：** 自动富化插件、日志替代审计、所有失败请求持久化、复杂留存与归档系统。

2026-10-14，用户授权的 I02 最小公共能力已交付：事务内追加、显式范围查询、已验证操作者 ALS 绑定、
P04 直接输入示例及隔离数据库验证。见 [I02 实施记录](mvp-i02-audit-2026-10-14.md)。
P04-P06 仍待启动，真实业务动作、字段白名单及查询授权由主线接入；不据此宣称团队闭环完成。

### I03：让业务定义在启动时被找到并检查

**为什么做：** 权限定义以后来自各业务模块。Core 不应每增加一个业务就修改一份硬编码总清单。

**本会话要做：**

1. 使用 Nest Discovery 采集明确标记的、已经装配的 Provider，不扫描目录，不靠导入文件产生注册副作用。
2. 第一版只处理真实需要的授权贡献，接收启动时可确定的单例定义。
3. 提供共同的重复标识检查、来源信息与冻结步骤。具体授权、资源或文件用途是否合法，仍由各自模块检查。
4. 把顺序落实为“采集、检查、冻结、允许服务”；缺定义或冲突时停止启动，不能已经接收请求才发现。
5. 之后 Resource/File 接入时复用采集机制，但不把各模块知识汇总到一个插件总管。
6. 队列、供应商适配器和普通配置继续显式装配，不因为用了 Discovery 就把所有依赖都改成注册表。

**主线要提供：** 第一批组织/工作区授权定义、稳定标识、哪些定义必须存在，以及一个实际贡献 Provider。
没有真实贡献之前，可讨论接口，不单独写一个空框架并宣称 P05 完成。
Discovery 不自动向数据库写入权限目录；目录初始化与代码定义的对应方式在 I04/P06 中交接。

**交付物：** 实际能采集贡献的 Platform 桥接、授权注册表、Bootstrap 启动装配及接入示例。

**完成标准：** 导入一个合法贡献后能使用；重复、非法或缺失必需定义时启动失败；冻结后不能修改；新增贡献不需要修改公共采集实现。

**先不做：** 插件热加载、请求级注册、第三方插件市场、一次接入全部 Registry。

### I04：统一权限判断，接好当前组织和工作区

**为什么做：** 列表、详情、写入和导出不能各自判断权限，更不能把前端选中的工作区当作授权证据。

**开始前必须有：** 主计划 D04/D05 的首批角色、权限点、角色作用范围和设施使用规则。
allow-only 已确定；具体执行方式仍待确认，不能因为旧文件叫 `permission-engine.port` 就默认引入 Casbin。

**本会话要做：**

1. 实现最小 Permission 公共入口，根据当前有效成员、角色与动作定义作出判断。未知动作、无授权或无有效成员一律拒绝。
2. 对接 HTTP 工作区绑定：用户来自现有认证，组织和工作区必须通过实际关系校验；请求中传入 ID 只是选择上下文。仅在需要工作区的入口要求这一上下文，不让账户或首次创建组织的操作凭空依赖已有工作区。
3. 组织角色与工作区角色按各自范围使用，不能混绑。离开或被移除后，旧 AT 尚有效也不能保留工作区权限。
4. 明确列表如何取得可查询范围；业务模块将范围落实进查询，再进行分页、统计和导出。不先读完整集合再过滤。
5. 同一公共判断供详情与写入复用，但各资源所有者仍负责对象归属和其特殊条件。可使用共享设施不等于可读取其他工作区的材料。
6. 日志保留可排障的拒绝原因，公开响应不泄露其他组织对象或内部权限配置。

**主线要提供：** 权限与角色清单、组织/工作区成员接口、设施与资源授权规则，并负责邀请、授予/撤销角色、成员移除的业务流程。
本会话不再维护第二套成员关系，也不在 Platform 里做成员管理。
P06 主线负责确定并实施权限目录的初始化与变更，交接代码定义与目录的一致性规则及已批准的初始化入口。
公共权限模块按这些规则校验与使用目录；缺失、失效或未知权限不得自动放行，Discovery 也不顺便执行写库。

**重要模型缺口：** 现有 Role/Permission 模型不能直接表达存储节点授权与停止继承。
若 D05 把这些纳入首发，先说明所需模型和执行规则，获得确认后再做；既不能假装 `ltree` 已自动实现继承，也不能静默取消已批准功能。

**交付物：** Permission 最小实现、HTTP 上下文接入、业务查询接入说明及团队拒绝场景记录。

**完成标准：** 同组织无权限、跨组织、伪造工作区和角色范围错误都拒绝；成员移除后下一次访问失效；列表总数、详情和写入采用一致授权口径。

**先不做：** 显式 Deny、任意 ABAC 编辑器、全量策略模拟、长期缓存旧授权。

### I05：给附件、任务和审计一个可靠的资源引用入口

**为什么做：** 这些公共能力需要知道对象是什么、属于谁，而不是各自查询 Material、Facility 等所有业务表。

**本会话要做：**

1. 从材料资源开始实现 Resource 公共入口与 Provider 注册，后续按真实需求增加设施、位置、库存等类型。
2. 按现有 `ResourceIdentity` 创建跨模块标识，具体业务对象与标识在同一事务中建立。
3. 由对应业务 Provider 解析实际所有者、组织、工作区及安全描述；Resource 不硬编码全部业务表。
4. 检查 `kind` 与实际对象匹配，避免一个标识关联多个不同所有者。仅有若干可选关系字段，不足以自动保证这个条件。
5. 描述信息本身也可能敏感。未授权时不能返回对象名称或跳转信息；“知道 resourceId”不等于“允许读取”。
6. 所有者归档或成员关系变化后，附件等调用方重新按当前规则授权，而不是永久相信创建时的结果。

**主线要提供：** 第一种具体资源、类型与归属规则、生命周期，以及该模块的 Provider。材料不跨工作区共享，不由公共层放宽。

**交付物：** Resource 最小实现、材料 Provider 接入例子、原子创建和授权读取说明。

**完成标准：** 材料与标识创建失败一起回滚；错误类型和跨组织引用拒绝；未知 Provider 明确失败；未授权对象不会通过描述接口泄露信息。

**先不做：** 通用实体 CRUD、把所有业务表改成一张资源表、任意多态查询框架。

### I06：解决存储树、查询和数量表示的实际技术难点

**为什么做：** 这些地方既容易产生隐蔽错误，又不应让主线为了接入数据库而绕过现有保护。
这一包分三部分交付，不要求把它们塞进同一个通用模块。

**A. 存储树写入与受管事务对接**

1. 修改现有 writer 所需的查询接口，让它能通过受管 `queryClient` 执行原生操作，不让调用方强转成原生 TransactionClient。
2. 对必须参与事务的写入明确要求已有事务；不在 writer 内偷偷开启独立事务，也不使用 `DatabaseRuntime.client` 绕过上下文。
3. 保留 ltree 路径维护、拓扑锁和原生约束。SQL 继续由 Facility 的 persistence 实现管理，Database 不吸收存储节点业务。
4. 在失败时验证受管错误处理和 rollback-only 仍有效。外层库存或资源创建失败后，节点操作也必须回滚。

**B. P08 真正需要的树查询与分页**

1. 与主线一起确定子节点、祖先、定位和必要子树查询，原生 SQL 使用参数化输入，排序只接受批准字段。
2. 需要 TypedSQL 时才补生成、构建和环境说明；生成结果必须可重现，不让开发机的隐含数据库状态成为构建前提。
3. 需要游标的查询使用稳定排序与唯一 ID 兜底，校验游标与当前查询上下文。游标编码不是授权；每次仍执行当前权限限制。
4. 通用层最多负责游标数据格式与校验，具体字段、过滤和 SQL 属于查询所有者。小型列表不被强迫全部改成游标分页。
5. 在获准的隔离环境用万级合成节点查看执行计划、索引与分页表现，记录数据量和实际耗时，不先承诺没有依据的毫秒指标。

**C. 数量和大整数的输入输出**

1. 给 P09 提供 Decimal 使用和 wire 表示方案；数量计算不经过 JavaScript 浮点数，明确精度、范围与格式。
2. 在相关共享契约与业务响应里显式处理 Decimal/BigInt，不把原生 Prisma 对象直接当 JSON 响应。
3. 库存单位、允许数量和舍入规则归库存业务。先放在实际所有者旁边，有真实复用再提取，不先加全局 Common 数值工具层。

**主线要提供：** 位置读写场景、授权范围、排序、数量规则与响应契约。主线负责 Controller、节点生命周期、库存原子操作和界面。

**交付物：** writer 对接、P08 查询支撑、所需游标和数值约定、回滚与查询性能证据。

**完成标准：** 外层失败后没有残留节点；原生错误不绕过统一处理；未授权节点不能靠查询或游标访问；稳定数据下翻页不重不漏；精度边界得到明确拒绝或正确结果。
并发修改时分页是否保证快照一致要单独说明，不能把稳定排序说成一致性快照。

**先不做：** 万能查询构建器、所有列表统一改写、Database 内建业务权限、独立事务框架、自动位置分配。

### I07：让重试不会重复入库或重复执行

**为什么做：** 用户双击、超时后重试、网络断开都可能让同一个业务请求到达多次。
幂等的含义是“同一操作重来不会再生效一次”，不是“把所有相同请求缓存起来”。

**开始条件：** P09 第一条入库操作与重放结果确定。先以它验证，再判断哪些机制值得提取进 `core/idempotency`。

**本会话要做：**

1. 复用 `InventoryTransaction.idempotencyKey/requestHash` 及现有唯一约束；不一开始就加一张通用幂等表。
2. 与主线确定作用范围。现有唯一约束是工作区内的 key，公共接口不能暗中改成每个动作各用一份空间。
3. 对主线提供的规范化请求计算指纹；动作、关键参数与格式版本必须能区分。字段顺序与业务等价性如何处理由业务明确，不能对原始 HTTP body 随便算一次 hash 就结束。
4. 同 key 同内容取得原业务结果；同 key 不同内容拒绝。重放前仍检查当前身份与权限，不能用 key 访问其他人的结果。
5. 用数据库唯一性、事务和条件写入解决并发。业务修改、执行流水、必要审计一起提交；失败不留虚假成功记录。
6. 明确回滚、已提交但响应丢失、并发进行中及提交结果不明的处理。不能因为没收到成功响应就盲目重新执行，更不自动重试整个数据库事务。

**主线要提供：** 同一次操作的定义、哪些字段纳入指纹、是否允许不同操作者重放、原结果的安全投影与业务错误。
公共层不接管库存状态机，也不另开独立事务让幂等记录先于库存提交。

**交付物：** P09 可用的幂等机制、必要的公共部分、并发和响应丢失的验证记录。

**完成标准：** 并发同 key 只产生一份有效执行；内容改变被拒绝；回滚后可按约定重新申请执行；成功后重试不重复数量、位置、流水或审计；跨工作区和无权限重放拒绝。

**先不做：** 分布式锁平台、全接口幂等中间件、缓存认证响应、脱离业务事务的通用执行框架。

### I08：在现有 Storage 上完成绑定型附件

**为什么做：** 对象成功上传到 S3，不等于文件已经验证、归用户所有或允许其他人下载。
File 才负责这些应用层条件，Storage 继续只处理对象存储协议。

**开始前必须有：** D10 的首发用途、大小/类型、内容校验、后处理、签名时限和失败清理规则；P07 的资源与权限接口可用。

**本会话要做：**

1. 按真实用途注册文件约束，第一批只接材料附件，不设计全平台文件类型权限枚举。
2. 实现开始上传、单次/分片计划、完成确认和中止，记录可恢复的必要状态。进程重启后不能完全依赖内存判断上传是否存在。
3. 对照现有 FileObject/FileAsset/FileReference 检查状态是否够用。它们没有直接提供完整分片 uploadId、预期清单等信息；需要新增持久化内容时先提出方案，不假装骨架中的 UploadSession 类型已经落库。
4. 完成时核对真实对象、大小和批准的内容校验；客户端声称“上传好了”不能直接让状态变成可绑定。
5. 确保重复完成不生成多份资产或引用；绑定校验用途与当前资源权限，必要的数据库改变在同一事务内完成。
6. 未绑定文件只供上传者按约定使用。绑定后的下载与解绑按当前资源权限检查，不以 objectId、bucket 或 key 当访问凭据。
7. 说明签名 URL 到期前的撤权窗口；清理过期会话和孤立对象时检查引用与上传状态，不能删除仍在使用的对象。
8. 继续使用现有 StorageService，不为文件骨架再造一套对象存储适配器。

**主线要提供：** 材料的附件用途、文件 Controller 与公开契约、绑定业务入口、附件界面及进度/失败恢复交互。

**交付物：** File 最小实现、用途接入、必要状态模型方案、上传/绑定/下载和清理验证记录。

**完成标准：** 未完成或校验失败的上传不能绑定；其他人不能读未绑定文件；重复确认和分片重试不产生重复资产；撤权后不能签发新下载地址；清理不会误删有效引用对象。
同时说明已有签名 URL 不会仅因数据库撤权立即失效。

**先不做：** 文件版本、网盘、在线编辑、全文索引、所有图片/视频后处理。必须后处理且不能丢的用途先补 I09。

### I09：确有需要时补可靠后台执行

**什么时候才做：** 邮件必须自动可靠重试、文件必须完成后处理、提醒需要跨进程触发，或批准的大导出需要后台执行。
普通待办和审批不因此变成 BullMQ Job。

**先向主线问清：** 哪项工作不能丢、成功怎么判断、允许等待多久、失败后谁处理，以及重复执行会造成什么后果。
回答不清楚时先解决这些问题，不先选队列。

**本会话要做：**

1. 与业务事实同事务记录待发送工作；Outbox 是这份待发送记录，不是额外保存一份业务状态。
2. 在事务外派发，支持重启后继续处理、并发领取、失败重试和无法自动恢复的失败记录。队列不是唯一的任务事实。
3. 选一种满足首批需求的派发方式，说明是数据库派发还是队列，以及由谁维护。不要同时接 BullMQ、RocketMQ 和另一套通用调度层。
4. 对实际 Handler 定义最小输入、结果和错误约定；重复投递由消费方安全处理，不宣称跨数据库与外部服务能自动“恰好执行一次”。
5. 设置次数、退避、超时和人工处理入口；取消等待不等于外部操作未生效，结果不确定时不能一律安全重发。
6. 与现有关闭流程对接：停止接新工作、处理正在执行的任务、在预算内退出，留下可继续处理的事实。
7. 记录可定位的工作标识和失败信息，不在日志保存邮件凭据或文件访问签名。

**特别注意恢复邮件：** 账户表只保存恢复凭据 hash，并不意味着可以把明文恢复链接随意放进 Outbox。
可靠重试若需要保留可发送内容，要先设计受限、短期的载荷保护和过期处理，并获得确认；不能借后台重试违背凭据存储约定。

**主线要提供：** 业务 Handler、提交时点、输入保护要求、过期/取消规则和重复执行处理。提醒规则与通知收件人不归调度器决定。

**交付物：** 一条真实后台工作可用的最小可靠执行链、必要模型与配置方案、重启和重复投递记录。

**完成标准：** 业务回滚不发工作；提交后进程退出仍可继续派发；重复消费不会重复关键副作用；永久失败可查；停机不静默丢失。
`afterCommit` 只在确认提交后尝试执行回调，不能替代以上持久化保证。

**先不做：** 通用工作流、任意长任务编排、全部事件注册表、使用队列保存普通待办事实。

## 6. 主线接入前，双方要交接什么

每个工作包开始前，双方在同一份短说明里对齐以下内容，不需要写几十页接口规范：

1. **使用场景：** 例如“组织创建成功时记录审计”，而不是“完善 AuditKernel”。
2. **主线输入：** 已确认规则、必要字段、合法身份与权限、一个成功例子和几个拒绝例子。
3. **公共接口：** 参数、结果、错误、事务前提、超时和重复调用的行为。返回值不泄露原生 SDK 或内部 Prisma 创建输入。
4. **修改范围：** 谁改 Core/Infra、谁改业务调用、谁改共享契约和 Bootstrap；不要两边同时猜着编辑同一文件。
5. **数据与配置：** 是否改 schema、DDL、公开 wire 形状或运行配置；有破坏性变更先告知用户。
6. **验收环境：** 哪些是替身，哪些是真实数据库/SMTP/对象存储，哪些操作已有本轮授权。

本会话交付后，给主线一份简短接入说明：入口、示例、前置条件、失败场景、未实现项和验证证据。
主线用真实业务完成接入后，再进行联合验收。

建议以接口是否就绪作为交接点，而不是以“目录代码写完”作为交接点。
没有真实调用方接入的公共能力可以记为已交付子项，不能据此把整个 P 任务标成已完成。

## 7. 如何判断真的做完了

### 每包的共同要求

- 接口能被真实调用方使用，成功、拒绝和失败语义写得清楚；没有靠空 Provider 或模拟成功交差。
- 构建、定向 lint、格式和差异检查通过；必要的 Context、设计和公开文档同步更新。
- 适用的跨租户、失效授权、并发、重复请求、回滚、超时和关闭场景有实际记录。
- 新配置说明是否必需、缺失如何处理、由谁注入；变更已获批准时才同步相应 example/环境配置，不输出真实凭据。
- 数据模型与实际服务行为一致；原生约束只证明它负责的条件，不能替代权限和业务流程验收。

### 验证边界要说明白

| 验证方式              | 能说明什么                 | 不能替代什么                         |
| --------------------- | -------------------------- | ------------------------------------ |
| 静态阅读、类型与构建  | 结构、类型和引用成立       | 数据库并发、实际投递、真实上传       |
| 一次性替身验证        | 公共调用流程与失败分支     | 外部依赖的实际行为                   |
| 获准隔离数据库验证    | 事务、约束、竞争和执行计划 | 生产部署与真实团队使用               |
| SMTP/对象存储实际验证 | 指定依赖上的协议与操作结果 | 收件箱送达或全部附件授权闭环         |
| 主线联合验收          | 本轮选择的用户流程可用     | 未纳入范围的功能、其他载体或生产 SLA |

本项目目前不自动新增或维护测试脚本。获准时使用一次性检查并留下结论；需要长期回归脚本时另行确认。
写这份计划不授权执行 `db:push`、DDL、清理数据、停止服务、轮换密钥或发送真实用户邮件。
主线已有的受限环境授权也不自动扩大到所有基础设施任务。

### 如何记进度

主工作计划仍是唯一 P00-P19 状态表。
I01-I09 只是分工编号，实施记录写清它支持哪个 P 任务，再由主线更新相应状态。
只有后端子项完成，就说明“后端子项已交付，业务/前端待接”，不重复维护另一张主状态表。

## 8. 发布前的基础设施收尾

这些工作配合 P19，不另起一轮大重构；需要先确认 D13 的载体与部署环境。

1. 检查新增模块的配置注入、启动顺序、冻结时机和关闭预算；新 Worker 要纳入原有生命周期。
2. 对容器内日志、SMTP、数据库、对象存储与必要队列检查实际连接方式，不把开发机可用当作容器可用。
3. 核对数据库初始化、schema 同步和业务原生约束的顺序；既有环境发生变化时明确升级方式，不恢复历史 migrations/seed。
4. 配合主线演练数据库与文件对象的备份恢复，检查恢复后引用仍然对应。数据保留、允许丢失量与恢复时限由试点要求确定。
5. 给出初始化、停机、恢复和常见故障的操作说明；已有 ready 的进程就绪含义不被偷换成所有外部系统实时健康。

## 9. 本计划明确不推进什么

不重新设计已可复用的日志、错误、HTTP、认证和数据库事务基座，不进行全仓搬迁。
没有具体阻塞时，不预建 Search、Realtime、Quota、Risk、全套缓存、分布式锁和通用插件系统。
不引入硬件联动、可配置审批工作流、商业计费、专业培养/QC/谱系等新范围。

如果主线出现这些需求，先说明它阻塞哪个用户操作、最小做到哪里、怎么验收，再单独确认。

## 10. 建议下一步

1. 先按 P02 的范围确认邮件可靠性要求，再批准 I01 的具体补齐工作；密码恢复本身仍由主线实施。
2. 主线开始 P04-P06 前，给出第一条管理写入与首批权限定义，本会话据此推进 I02-I04。
3. 团队权限可用后，以材料和存储位置作为第一批真实调用方，按需交付 I05/I06；用 P09 验证 I07。
4. 在材料资源可用时推进 I08，I09 只在相应任务确有可靠后台要求时插入。

最终交付目标不是“Core 全部写完”，而是每个已批准业务流程都能用上必要、可靠、职责明确的公共实现。
