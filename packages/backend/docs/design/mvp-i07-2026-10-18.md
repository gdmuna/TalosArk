# I07：请求幂等内核

实施日期：2026-10-18。状态：业务无关的核心能力已交付；尚未接入 Inventory、Approval、File、HTTP 拦截器或启动装配，也未新增通用幂等表。

## 这轮交付什么

`src/core/idempotency/` 现在提供一个小的幂等接口：调用方先用 `prepare` 规范化请求，再在已经打开的业务事务中调用 `run`。
内核负责指纹、事务内 claim/执行/complete 顺序、结果快照、重放和冲突判断；业务模块仍负责身份、权限、输入语义和具体持久化适配器。

```ts
const request = kernel.prepare({
    scope: { kind: 'workspace', organizationId, workspaceId },
    operation: 'inventory.receive',
    key: input.idempotencyKey,
    payload: normalizedInput,
});

return database.transaction.run(async () =>
    kernel.run(request, () => receiveInventory(normalizedInput), inventoryResultCodec),
);
```

`run` 自己使用 `mandatory` 传播，因此只能加入现有的受管事务，不会偷偷创建根事务或独立事务。业务编排层仍应在同一个事务中完成权限检查、业务写入、审计和幂等完成。

## 持久化 Port

`IdempotencyRepository` 是类型 Port，不是当前可运行的 Prisma 实现。未来由拥有唯一约束的业务模块提供适配器；适配器必须在当前 `DatabaseRuntime.queryClient` 上实现：

- `claim` 原子地按所属业务定义的 `scope + key` 竞争唯一记录；`operation` 参与指纹，但不会被内核偷偷加入唯一命名空间。
- `complete` 只能完成同一 `leaseId`、同一物理事务中的预留；返回 `false` 表示预留已丢失。
- 并发竞争、条件更新和数据库回滚由适配器与数据库保证，内核不伪装成分布式锁。

现有 `InventoryTransaction`、`ApprovalRequest` 和 `FileUploadSession` 的业务唯一约束保持不变。本轮不修改 Prisma schema，也不为没有真实调用方的场景提前抽象通用表。

## 指纹与结果

- 指纹为 SHA-256，输入包含 `operation`、指纹版本和有界 canonical JSON payload；scope、key 用于定位记录，不进入哈希。
- JSON 只接受 null、字符串、布尔值、有限安全数字、稠密数组和普通对象；键按字典序排序，数组顺序保留。深度、节点数和 UTF-8 字节数均有上限。
- 结果必须通过调用方提供的 typed codec 编码；内核只保存安全 JSON 快照，不保存任意 HTTP response、类实例或错误对象。
- 已完成记录若结果缺失，返回 `result-unavailable`，不会因为旧结果丢失而自动再次执行。

同 key 同指纹会重放投影结果；同 key 不同指纹返回冲突；已有执行尚未完成返回进行中。重放仍需由调用方先完成当前身份和权限检查，不能把 key 当作访问凭证。业务状态后来被归档或改变时，也不能绕过正常授权和业务规则。

## 失败与事务边界

工作函数、codec 或 repository 失败都会留在 `mandatory` 事务中。即使调用方捕获异常，数据库事务也会被标记 rollback-only，不能提交部分业务结果。提交结果不明时，调用方不得因为没有收到响应就盲目重新执行；应依据数据库中的 reservation 状态处理。

`leaseId` 使用单调 ULID，并绑定当前物理事务 ID。它不是带过期时间的分布式 lease，也不提供续租、缓存、自动重试或跨进程协调。

## 未包含的能力

本轮明确不做通用幂等表、缓存、全局 HTTP 中间件、分布式锁、后台任务、自动事务重试、业务权限判断和结果长期保留策略。P09 仍需确定规范化请求、唯一约束、结果投影和真实 PostgreSQL 并发行为，然后实现第一个业务适配器。
