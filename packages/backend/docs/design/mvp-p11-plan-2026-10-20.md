# P11 代码层实施方案

日期：2026-10-20。状态：已按用户授权实施，本地真实 HTTP、PostgreSQL 与 Web 定向验收通过。业务依据为 [P11 对齐记录](../../../../docs/product/mvp-p11-alignment-2026-10-20.md)，实际结果和边界见 [实施与验收记录](../../../../docs/product/mvp-p11-acceptance-2026-10-20.md)。下文保留实施前的代码层设计。

## 1. 目标与范围

新增登记消耗、单件转移、数量调整、移出管理四类直接执行命令。复用现有 OrganizationWriteKernel、IdempotencyKernel、InventoryOperation、StockItem、Placement、库存流水和 AuditKernel，不增加第二套事务、分布式锁、任务表、工作流引擎或状态机库。

不做整件借出、普通归还、实物拆分/合并、单位换算、跨组织/工作区所有权调拨、批量执行、在途运输和审批实现。原因全部选填；未知有效期没有风险确认开关。P12 的审批资格以后接入同一库存执行规则，本轮不预造审批绕过参数或空实现。

四类动作均在服务端重查成员、库存/材料读取权限、动作权限、数量与状态。存储设施、源位置或其祖先停用时冻结库存事实写入；纯数量调整不需要设施使用权，但仍必须通过这一生命周期检查。已有已完成操作的回执读取不属于再次写库存。

`InventoryActionService` 对 controller 提供一个有类型的 `execute(scope, stockItemId, command)` 接口。controller 根据固定路由构造命令种类，不接收客户端任意指定的内部执行模式。私有编排集中承担组织锁、幂等、版本更新、占位、流水及审计，业务差异由四种明确命令和纯函数处理，不开放调用方自定义步骤。

`domain/inventory-action.ts` 接收实际数量、库存状态、材料精度/日期事实和动作输入，返回目标数量、目标状态及占位变更意图；业务拒绝以明确的失败标识交回编排，由现有 InventoryError 创建错误实例，不增加另一套领域异常继承。它复用已有精确 Decimal 助手；不执行 SQL、不验证 JWT、不计算设施授权、不改 MaterialInstance 初始量。

`InventoryOperationService` 是从当前 InventoryService 中有界提取，不是新的全局操作平台。P09 入库、整体搬迁与 P11 共用回执 codec 和完成记录授权，避免新增执行者反向依赖整个库存读取类。P11 内部的源/目标设施重放检查仍由自己的动作编排按既有流水事实调用 Facility 完成。

Material 不新增模块或写入口。动作所需的单位、精度、有效期和归档事实使用当前库存关联读取或现有 Material 公共读取能力；不要把只允许活动材料入库的校验误用于既有库存操作。

## 4. HTTP 和命令契约

统一前缀 `W = /organization/:organizationId/workspace/:workspaceId/inventory`，四个 POST 均返回 201 的操作回执，继续使用 Method + ApiRoute 的请求、成功与错误包络校验。

| 路径 | 动作专有输入 | 成功后的事实 |
| --- | --- | --- |
| `W/:stockItemId/consume` | `quantity`：本次实际消耗量，大于 0 | 当前量减去本次量；减至 0 为 DEPLETED，保留占位 |
| `W/:stockItemId/transfer` | `position: { facilityId, topologyId, nodeId }` | 同一实物从当前位移至真实空位，数量/状态/所有权不变 |
| `W/:stockItemId/adjust` | `actualQuantity`：核实后的非负实际余量 | 更新当前量；0 为 DEPLETED，正量为 IN_STOCK；保留占位 |
| `W/:stockItemId/dispose` | 无额外数量输入 | 服务端按实际旧余量归零，置 DISPOSED，结束占位 |

共同输入为 `expectedVersion`、`idempotencyKey` 和选填的 `reason`。数量全程使用十进制字符串；原因省略或空白统一规范化为空字符串后参与指纹，不设必填。组织/工作区/库存身份来自路径，执行人来自 ALS；不允许客户端写状态、初始量、执行时间、库存归属或源位置。

```json
{
  "expectedVersion": 3,
  "quantity": "20.000000",
  "idempotencyKey": "client-generated-stable-key",
  "reason": ""
}
```

这是消耗请求示例。调整使用 `actualQuantity` 而不是同名数量字段，避免把“扣除多少”和“调整到多少”混为一谈。首版不为无效果的调整、原位转移或零量消耗创建成功流水，使用无效输入响应；零量实物的明确处置则是有效状态和占位变化。

回执继续包含 `operationId/kind/stockItemId/instanceId/nodeId`，新增 `inventory.consume/transfer/adjust/dispose` 四个 kind。新动作的 stockItemId 和 instanceId 必须非空；转移的 nodeId 为执行当时目标位，处置为 null，消耗/调整为执行当时原位。既有入库与整体搬迁分支语义不变，不能再因为新增动作将旧入库的合法 null nodeId 拒绝。

通过分支 schema 描述新动作必填身份，GET operation 和幂等 codec 接受完整回执联合。回执是当时执行结果，不因后续又发生动作而被改写，也不冒充最新库存；最新状态通过库存读取取得，流水仍可凭 operationId 查询。实现时进一步区分持久结果与公开投影：当前无设施读取权时，公开回执的 nodeId 可为 null，原始成功结果不变。

## 5. 库存状态与物理占位

本轮启用 IN_STOCK、DEPLETED、DISPOSED 的动作规则，不实现 CHECKED_OUT、QUARANTINED 的流转，也不顺手删除现有预留枚举及其未交付的其他领域结构。

| 原状态 | 消耗 | 转移 | 数量调整 | 移出/处置 |
| --- | --- | --- | --- | --- |
| IN_STOCK | 量足、未过期时允许 | 允许 | 允许增减 | 允许 |
| DEPLETED | 不允许 | 允许 | 可纠正为正量 | 允许 |
| DISPOSED | 不允许 | 不允许 | 不允许恢复 | 新请求拒绝；原成功请求可受权重放 |

所有允许项仍受成员、动作授权及存储停用检查限制。材料/批次归档不阻止上述存量操作，过期只额外禁止正常消耗；未知有效期不增加确认步骤。资料修订和库存 version 各司其职，库存动作推进 stock.version，不伪造资料编辑或改初始量。

转移更新同一 Placement 的目标节点及 placedAt，在同一事务释放旧位置并占用新位置。处置删除当前 Placement，保留 StockItem、MaterialInstance、ResourceIdentity 和全部历史，不以硬删除或设置实例 archivedAt 替代处置。

## 6. Facility 公共检查能力

在现有 FacilityPositionReader 内增加下列明确能力；只服务当前调用点，不增加前端可直接访问的任意内部查询接口。

| 能力 | 调用者和用途 |
| --- | --- |
| `inspectSources({ organizationId, nodeIds })` | 已授权的 Inventory 在受管事务中，以真实 Placement 推导的节点批量取得设施/拓扑、节点身份、当时路径及有效生命周期；供首次写入、读投影和整体搬迁使用 |
| `requireUse(subject, scope, facilityIds)` | 检查当前成员、设施使用权限和整设施准入关系；只判断授权，不混入“必须空闲”或生命周期条件；同时用于受权重放 |
| `visibleFacilities(subject, scope, facilityIds)` | 按当前设施读取授权返回可描述的设施集合，供当前位置与历史快照的安全投影 |

以上名称可随实际接口约定微调，职责不可合并成含 `skipAuthorization` 的万能方法。源位置事实必须批量查询，复用 Facility 现有祖先/设施生命周期规则；Inventory 不直接拼接或解释 ltree。缺失组织关联或应有的在管占位属于数据不一致，不能静默当成“未存放”。

调整只调用库存授权和源位置生命周期检查，不调用 requireUse，不向用户返回内部位置事实。消耗、转移、处置另外检查源设施使用权；转移目标继续调用 requireAvailable，重新检查正常生命周期、真实 POSITION、共享准入及空闲，不将候选当预留。

库存列表最多 100 条，新增可用性投影按去重的位置/设施批量处理；权限按当前工作区及设施集合复用计算，不为每行每个动作重复查一次数据库。单项命令则只检查实际涉及的一件实物和至多两个设施。

## 7. 四类动作的一次事务

执行顺序固定为：

1. ApiRoute 校验输入；规范化数量与原因，将固定动作种类、库存 ID、执行人、版本和完整业务参数纳入幂等指纹。沿用工作区幂等作用域，动作种类参与指纹，不另造键空间。
2. OrganizationWriteKernel 开启 ReadCommitted 事务，锁定组织行，再重新校验有效成员、材料/库存读取权及本次动作权限。
3. IdempotencyKernel 在同一事务认领原键；已完成请求走下面的受权重放，不进入新执行分支。
4. 首次执行读取真实 StockItem、实例和 Placement，比较 expectedVersion，再检查库存状态、源生命周期及所需设施使用权；转移另检查实际目标位。
5. 领域规则计算目标数量/状态/占位意图，禁止负数、精度溢出、过期消耗、对已移出实例操作及无效果变更。
6. 条件更新 StockItem：限定组织、工作区、库存 ID 和旧 version，成功时 version + 1。没有匹配行返回冲突，不覆盖别人已经提交的事实。
7. 在同一事务更新或删除 Placement，创建一条对应业务流水和前后值明细，记录审计，再完成幂等回执。

组织行锁已经串行协调同组织写入，不再无依据地叠加全表锁或四套锁服务。CAS 用于拒绝旧用户视图，现有位置唯一约束保底处理占位竞争。任何占位、流水、审计或幂等完成失败均回滚整次动作，不能留下只扣量或只释放位置的半次成功。

执行时间使用服务端实际时间，有效期使用现有 InventoryCalendar 的业务日期。首版不接受客户端回溯生效时间，不通过补记覆盖历史流水。

## 8. 成功重放与当前权限

新执行的 expectedVersion、余量、空位和生命周期检查必须在幂等 acquired 分支中。原消耗成功后已经耗尽，原转移成功后目标已被本件占用，原处置成功后已经没有 Placement，均不能让同键重放错误地当成一次新执行而失败。

POST 重放仍检查当前有效成员、材料/库存读取权和相应动作权限；需要设施使用权的动作根据原流水中的源/目标设施快照检查当前授权，不把现在实物可能已变更的位置当成原操作的源位置。调整重放不增加设施使用权要求。

停用在此禁止的是新的库存变更，不否定已经完成的历史事实；已完成操作只读回执不会重新修改库存。GET operation 沿用受权的回执读取语义，不要求旧位置仍空闲或旧版本仍是当前值。无权、回执损坏和结果暂不可用明确失败，不能换键重新执行。

## 9. 权限、错误、流水与审计

在 inventory-authorization.contribution 增加 `inventory.consume`、`inventory.adjust`、`inventory.dispose`，复用现有 `inventory.transfer`。InventoryAccessService 使用具名映射生成能力投影，不能在新增权限后继续依赖 decisions 数组的固定下标。

新组织默认工作区管理角色沿用组合根现有的 Object.values(inventoryPermission) 装配。已有组织通过现有显式 inventory/initialize 或 P06 自定义角色配置授予，不在登录、查询、模块启动或 Discovery 阶段自动加权。

公开错误新增正常消耗已过期、剩余量不足的明确错误；现有 invalid/conflict/state/forbidden/result 继续表达输入、版本冲突、状态禁止、拒绝访问和回执问题。错误协议仍由 contract 的 public/backend 两层声明，领域仍用 defineErrorClass，不重新引入领域 mapper 对每种业务错误逐一转换。

输入为 400，版本/状态/数量竞争为 409，拒绝访问沿现有不泄露范围的策略处理。过期消耗不能复用 P09 的“确认后可登记过期存量”错误，也不新增 confirmExpired 绕过参数。未知数据库、CHECK 或程序错误不润色成用户填错，继续交给现有内部错误边界；不公开 metadata 或位置细节。

流水新增 CONSUMPTION、DISPOSAL 两种类型，单件转移和数量纠错复用 TRANSFER、ADJUSTMENT。消耗和调整的位置前后为同一位置；转移保留旧/新路径；处置保留旧位置、目标为 null。数量和状态全部保存实际前后值，不以数量差值猜动作种类。

原因选填且有长度上限。审计按白名单记录 operationId、库存/实例/设施标识及数量/状态事实，自由原因可沿已有自由文本摘要模式保存摘要；完整原因在受权业务流水中保留。不要把完整实体或无限长度位置路径塞进有体积限制的审计详情。

## 10. 必须随 P11 修正的读取授权

静态检查发现：当前 InventoryService.project 已对不可见位置返回 location=null/locationRestricted=true，但 transactions 会直接投影 from/toNodePathSnapshot 等字段，未作同等设施读取检查。不能据此声称所有已有流水读取都满足位置隐藏规则。

P11 引入无需设施使用/读取权限的数量调整后，必须在流水列表、独立详情和 Inspector 共用的后端投影中补齐安全处理：按历史快照中的源/目标 facilityId 分别验证当前可见性；无权的一侧隐藏节点/设施/拓扑 ID 与路径，增加 fromLocationRestricted/toLocationRestricted，区分“无来源/目标”和“存在但不可见”。

数据库保留完整历史，不重写快照；不能使用已经搬迁后的节点现路径重建旧历史或替代旧设施授权判断。前端将历史路径作为事件快照显示，不能把旧设施 ID 和已搬迁节点 ID 直接拼成保证有效的当前位置链接；当前位置入口使用当前受权库存投影。

库存响应另增加四类动作的逐件 `actions` 可用性布尔投影，结合当前权限、状态、余量、有效期与存储生命周期。现有 capabilities 仍表示工作区动作权限，不悄悄改成逐件状态判定。所有布尔值均为 UI 提示，不是执行授权凭据；不可见位置只返回通用不可操作结果，不暴露具体哪个设施/祖先被停用。

## 11. P09 联动与数据库变化

P09 整体搬迁在 preview 与首次 execute 的 inspect 中检查全部受影响 Placement 的有效源状态。来源设施或任一承载实物的祖先链停用，整次拒绝，不跳过被冻结的实物继续搬。目标继续检查正常状态和各工作区准入；已完成重放保留第 8 节的只读受权语义。

这收紧了现有 P09 允许从停用来源移出的部分行为，是需要明确告知的行为变更，不是代码当前已经具有的能力。已有预览也不能作为豁免，执行时重查；本轮不新增“只出不进”配置。

Prisma 仅为流水类型增加 CONSUMPTION、DISPOSAL；StockItem、Placement、InventoryOperation 和流水表无需重建或新增平行实体。复用现有唯一约束。inventory.sql 补充本轮启用状态的 CHECK：IN_STOCK 必须正量，DEPLETED/DISPOSED 必须零量。DISPOSED 无 Placement 属于跨表事务不变量，不能伪装成行级 CHECK。

实施时先只读核对目标库和实际差异，再对明确授权的 test.local 应用必要定向结构变化和 DDL；不顺手同步并行分支的全库差异。已有不满足 CHECK 的记录须先报告，不自动清洗或把它们改成成功业务流水。不会因编写本方案执行任何 db push、DDL 或业务写入。

跨 Facility 的目标位置选择继续放页面编排，不增加 inventory -> facility 的前端模块依赖。纯数量/动作业务由 inventory 模块持有。普通归还、整件借出不显示成可点击但不可执行的假功能。

四种表单分别输入实际消耗量、目标位置、核实余量或移出确认，显示当前量与本次执行结果；所有原因输入均可留空。移出管理需明确确认结束管理与释放占位，但不要求补填原因或宣称现实销毁已完成。

新恢复 owner 复用既有规则，不在本轮把入库/搬迁两个已工作的 owner 顺手合并成通用命令框架。发送前按账户保存原命令，失败不盲目换键；刷新和路由往返保留，明确退出/切换账户清理。未知结果只确认原请求；收到成功回执后，列表/详情/流水/位置刷新失败只重读，不重发库存写入。版本冲突保留草稿，明确加载新事实并由用户确认后才形成新命令。

当前前端正在其他线程演进，接入时以最新页面和公共导出为准，不覆盖已存在的 InventoryStockInspector、InventoryMovementList 或页面重排。本方案给出职责和协议，不要求另一线程恢复旧布局。

## 13. 实施顺序和签收

| 步骤 | 交付内容 | 完成判据 |
| --- | --- | --- |
| P11-A 契约与状态计划 | action schema、回执联合、错误、权限及领域数量规则 | 请求能准确区分消耗量和核实余量，原因选填，旧 P09 回执仍能正确解码 |
| P11-B Facility 能力及安全投影 | 批量源事实/授权/可见性、P09 停用联动、流水隐藏 | 调整不额外要求设施使用权但不能绕过停用；无权用户看不到位置快照 |
| P11-C 原子执行 | 四类动作编排、操作 owner 提取、CAS、占位、流水和审计 | 每次成功只有一套业务事实；任一后置失败整体回滚 |
| P11-D 前端接入 | 实际动作入口、受权目标位、原键恢复和只读同步 | 不靠 mock 或仅弹窗假装执行；未知结果不另建写入 |
| P11-E 定向联合验收 | 获准 test.local 的真实 HTTP/数据库及必要 Web 场景 | 对应下表留下实际证据，不把静态通过当真实业务通过 |

验证集中在本轮新增及被收紧的规则，不重跑附件、邮件、完整成员邀请或全仓旧导入失效的测试。依照 backend/CONTEXT 当前约定，不擅自新增或维护永久后端测试脚本；实施阶段的临时定向验证与证据放忽略的 output 目录，永久测试建设另获明确授权。

| 场景组 | 必须证明 |
| --- | --- |
| 数量规则 | 部分/全部消耗、余量不足、精度边界、调整增减、初始量不变、原因留空 |
| 实物状态 | 耗尽保留占位；零量/正量移出均释放位置；移出后不能调整复活；处置不记成消耗 |
| 生命周期 | 归档存量可用、过期不能消耗、未知无额外确认；停用冻结四种动作及涉及存量的整体搬迁 |
| 当前权限 | 动作彼此独立；来源/目标设施准入；调整无设施使用权可执行但停用仍拒绝；撤权后请求被拒绝 |
| 读取保密 | 当前及历史位置隐藏、快照与当前位置分开、不可见原因不泄露具体路径 |
| 并发与回滚 | 两人消费最后余量、两件争同一空位、旧 version 拒绝；占位/流水/审计/幂等后置失败无半提交 |
| 幂等与 Web 恢复 | 同键同参数不重复；同键改动作/数量冲突；消耗至零/移出后仍能受权重放；断响应刷新复用原键；写后同步失败只读恢复 |

本地真实 HTTP/数据库、浏览器、Tauri、生产部署各自签收；不以某一项成功替其他环境背书。

## 14. 提前说明的变更影响

本方案不要求整体重做 Inventory、Material、Facility 或现有 Core。明确需要协调发布的内容包括：公开回执 kind 和流水类型扩充、Stock.actions 与流水位置受限投影、三项新增权限，以及 P09 的来源停用冻结收紧。
