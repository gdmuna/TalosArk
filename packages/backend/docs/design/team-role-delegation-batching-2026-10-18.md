# 团队角色委派读取批量化

状态：已实现并完成下述验证。范围仅为 `OrganizationTeamService.snapshot` 的角色读取与 `grantable` 投影。

## 问题与目标

当前每个候选角色分别调用 `PermissionKernel.evaluateMany`。不同角色经常包含相同权限，仍会重复读取绑定和创建独立 Casbin Model/Enforcer；普通成员最终收到空角色列表，也会先执行角色查询和委派评估。

目标是使一次管理快照的委派评估批次数为零或一，并保持成功响应中的角色、权限、排序、能力字段和成员/邀请分页结果一致。治理资格等前置授权批次不属于本项优化。

## 已确定的规则

- 沿用 P06：角色仅对组织所有者或当前范围的成员管理者可见。组织所有者看到当前查询原本返回的两类角色，其他管理者只看到工作区角色。
- 只有与当前查询 scope 相同、且代码不是 `organization-owner` 或 `organization-governance` 的角色才可能被委派。
- 组织管理者沿用现有直接委派规则；其他可见角色的委派要求当前用户在当前 scope 持有角色的全部权限。组织所有者身份本身不触发此放行。
- `protected` 与 `grantable` 是不同投影。不能因为基础成员或工作区管理者角色受保护，就禁止委派它们。
- 空权限角色继续遵守原来的全部匹配语义：符合其他条件时可委派。
- 只读取本次 RepeatableRead 快照；不修改角色、绑定或权限目录。实际绑定写入仍重新授权。

## 方案与取舍

直接调整 Organization module 内的 implementation，复用 Permission module 已有的 `evaluateMany` interface 作为 seam；不新增 adapter、委派模块或缓存。相同 subject 和 scope 已由一次快照固定，只需按权限码去重。

执行顺序：

1. 保留现有成员关系、组织读取、工作区存在性和管理资格检查。
2. 已确定角色不可见时，跳过角色查询；否则保留原来的过滤、排序及字段选择。
3. 从当前 scope 下的委派候选角色收集权限码，排除两个不可委派的组织内置角色并去重。
4. 组织管理者或没有待评估权限时跳过委派评估；其他情况只调用一次 `evaluateMany`。
5. 只在本次调用的局部集合中保存允许的权限码，逐角色判断是否全部满足，完成原有投影。`roleViews` 中的 `grantable` 先记录 scope/角色资格，在返回前收敛为最终委派结果；只修改新建投影，不修改查询得到的角色对象。

这种改动提高 locality：角色可见性、委派规则和输出仍集中在原用例中；借助既有批量 interface 获得 leverage，不增加新的协调层。Permission 内隔离可变策略的 depth 保持不变。删除一个仅转发委派调用的包装模块只会移动复杂度，因此不创建此类模块。

组织治理权限必须先求值才能确定可见性，本轮不把它们强行合并进委派批次。每个实际评估批次仍拥有独立 Model/Enforcer；不跨用户、scope、事务或请求复用允许结果。

## 验收方式

- 修改前保存当前工作区源码基线，以该基线而非 Git HEAD 比较，避免混入既有改动。
- 通过一次性内存探针运行修改前后的真实 `OrganizationTeamService`，对比整个成功响应。覆盖所有者不同治理资格、工作区管理者、普通成员、无角色、空权限、重复权限、缺失权限、受保护角色、跨 scope 角色和不同工作区。
- 对比角色数增长时的委派批次；新实现应最多一次，每个权限码在本批次内最多出现一次。普通成员不执行角色查询；组织管理者不执行委派评估。
- 探针确认权限拒绝及错误继续传播，调用仍处于同一 RepeatableRead 用例事务中。
- 执行后端类型检查、构建、本次源码 ESLint/Prettier 和差异空白检查；现有套件单独报告。
- 遵守当前迭代约定，不新增或维护测试脚本。探针不连接数据库、SMTP、KVS 或 Casdoor，不执行 Schema/DDL。
