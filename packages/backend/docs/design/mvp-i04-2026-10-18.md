# I04 补充：业务目标权限上下文解析

日期：2026-10-18。设计依据：[权限与权限上下文设计](permission-authorization-2026-10-18.md)。

本轮交付 I04 的公共解析、贡献装配及授权编排机制，不实现 P07 材料业务、I05 Resource、
节点继承或 Schema 变更。P06 已有团队管理规则与 wire 契约不变。
公共机制已验证；首个真实材料 Provider 与业务查询仍须 P07 联合验收，不能据此将 P07 或 I04 的业务接入标为完成。

## 1. 对外入口

`core/authorization/index.ts` 继续公开 `AuthorizationModule/AuthorizationKernel`。
`check/require/scope` 的职责不变；旧的组织、工作区 target 可以原样使用。

新增业务目标调用形态：

```ts
await authorization.require({
    subject: { kind: 'user', userId },
    permissionCode: 'material.read',
    target: { kind: 'material', id: materialId },
    expectedScope: { kind: 'workspace', organizationId, workspaceId },
});
```

公共入口现在支持这种结构，但 `material.read` 与材料目标 Provider **尚未由本轮注册**，
不能在当前运行时直接使用此例获得成功结果。新增领域按 P07 注册真实定义及 Provider 后才可用。

- 业务目标 ID 为 UUID；用户、目标及 scope 中的 UUID 统一小写。目标类型采用 1-64 位小写字母/数字/连字符标识，必须以字母开头。
- `organization/workspace` 是保留类型，只接受现有显式 scope 结构，不能用业务 `id` 分支冒充。
- `expectedScope` 可选，是调用方附加限制，不是事实来源。当前工作区业务入口应明确传入，不能靠“用户刚在界面选过”推断。
- 预期组织限制必须匹配真实组织；预期工作区还要求真实目标确属该工作区。预期组织允许匹配其下真实工作区，但不授予该工作区权限。
- 输入、Provider scope 均作严格校验并生成冻结快照，不保留调用方可变对象或额外 Prisma 字段。

### 已解析与已授权

`ResolvedContext` 包含 target、真实 scope、subject、permissionCode 和有效组织/工作区成员事实，
仅由内部解析器使用。`AuthorizedContext` 在此基础上多一个 `authorized: true`，只在 Permission 允许后生成。
原有 context 字段保留，现有调用方不需要迁移。它们仍只是当前操作观察结果，不是令牌或长期授权缓存。

## 2. 业务如何贡献事实

`AuthorizationTargetProvider` 的唯一方法：

```ts
resolve(query: AuthorizationTargetQuery): Promise<AuthorizationTargetFacts | null>;
```

`query` 是冻结的 `{ target: { kind, id }, permissionCode }`。
结果只包含 `{ scope: PermissionScope }`；实体不存在或按领域已确认的动作/生命周期规则不可用时返回 `null`。
返回 `undefined`、非法 scope 或额外字段是接入错误，不按“没有权限”吞掉。

Provider 读取领域真实归属，使用 `DatabaseRuntime.queryClient` 加入调用方事务。
它不信任客户端 scope，不自行作角色授权，不递归调用 Authorization，也不输出名称、链接或完整业务行。
`permissionCode` 供领域区分已确认的生命周期规则，不意味着可以用 Provider 替代 Permission 的最终判定。
归档记录是否可读由 P07 的实际规则决定，不在公共层统一猜测。

### 已有单例 Provider：隐式贡献

在实现该接口的已有 Injectable 类上添加：

```ts
@Injectable()
@AuthorizationTargetExtension({ kind: 'material' })
export class MaterialAuthorizationTargetProvider implements AuthorizationTargetProvider {
    // resolve 由领域公开事实查询实现；本例不代表当前已有这个业务类。
}
```

这是装饰器位置示意，不是完整可编译的业务实现。实际类必须实现 `resolve` 并注册到已导入模块的 providers。
默认启用 Discovery，只接收 provider 类的静态单例，拒绝方法装饰、request/transient 实例及包含 request 依赖的树。
Nest 别名不会重复注册同一个 Provider。宿主在 `onApplicationBootstrap` 一次性收集、校验和发布，
不会在启动时调用 `resolve` 查业务数据，也不在请求期间重新扫描。

### 纯对象：显式贡献

组合根按需添加一次配置，业务调用模块仍普通导入 `AuthorizationModule`：

```ts
AuthorizationConfigurationModule.forRoot({
    explicit: [
        {
            key: 'material',
            value: materialTargetProvider,
            source: { kind: 'explicit', owner: 'material' },
        },
    ],
    discovery: true,
    required: ['material'],
});
```

`materialTargetProvider` 是满足契约的对象，不是 Nest token 或未绑定实例；有依赖的服务优先使用上一种发现方式。
配置可省略，此时默认发现已装配 Provider，没有额外必需项。`discovery: false` 只关闭该宿主发现，不影响其他扩展宿主。
公开的是配置 token，不是全局授权服务；不用给每个业务模块重复注册一套配置。

两条路径复用 I03 的只读唯一索引，类型标识冲突直接阻止启动，错误保留贡献来源。
`required` 缺失阻止启动；运行时使用未注册类型也明确失败。
发布时捕获绑定的 `resolve`，保留实例 `this`，不冻结领域服务本身；启动后替换该方法不会偷偷改变已发布的分发函数。

## 3. 一次检查的顺序与错误

1. 校验并冻结请求，确认权限码已注册。
2. 在受管事务内，根据业务 target 调用 Provider；直接组织/工作区 target 不需要 Provider。
3. 校验 Provider 返回的真实 scope 与权限定义兼容，比对 `expectedScope`。
4. 校验组织、工作区及有效成员关系，得到 ResolvedContext。
5. Permission 根据真实 scope 作本地 Casbin 判定；仅允许时生成 AuthorizedContext。

| 情况 | 结果 |
| --- | --- |
| 实体不存在/不可用、预期 scope 不匹配、成员无效 | `check` 返回 `context-unavailable` |
| 上下文有效但未持有动作授权 | `check` 返回 `no-grant` |
| 以上两种拒绝调用 `require` | 保持既有不泄露详情的团队 403 |
| 非法请求、Provider 结构/返回值非法、Provider 缺失 | 内部 `AuthorizationTargetError`，不转换为普通拒绝或空范围 |
| 未知权限、权限作用范围不兼容 | 既有 `PermissionError` |
| 重复贡献、非法发现作用域 | 既有 `ExtensionError`；启动失败 |
| Provider 或数据库依赖故障 | 原错误透传，安全诊断不保留任意输入值 |

只在成员查询调用处捕获已知成员拒绝；Provider 自己抛出的同类错误也原样透传，不能借外层通用 catch 隐藏依赖故障。
未知权限或未注册 Provider 从不自动放行，`ResolvedContext` 也不能直接当作授权成功结果。

## 4. 事务、列表和模块边界

- 独立检查使用 RepeatableRead；已有事务时 mandatory 加入，Provider、成员和策略读取使用同一受管上下文，不另开事务或更改隔离级别。
- 参与检查的异常会让已有事务 rollback-only，捕获 Provider 错误不能挽救受损事务；正常拒绝是返回值，`require` 的业务使用仍须遵守既有事务控制。
- 写入由用例包住授权、实际修改与审计。此机制不替代领域锁、版本/条件写入，也不宣称撤权会取消在途操作。
- `scope` 和有限的 none/组织/工作区查询计划保持原样；本轮没有通用策略到 SQL 编译器。列表必须授权下推后分页、统计及导出，不能逐行详情检查替代。
- Authorization 不读请求 ALS、不导入 Material/Resource 或任何业务表；Session、Permission 和成员事实内核职责保持不变。
- I05 的资源 Provider 可与目标 Provider 复用领域事实查询；本轮不建立 ResourceIdentity 强制绕行路径或循环依赖。
