## 实际能力

Facility 属于组织，指定一个管理工作区。创建设施同时创建初始活动拓扑和两项 ResourceIdentity，业务与审计同事务。首版每个设施最多一个活动拓扑，不暴露拓扑切换或复制。

CONTAINER/POSITION 保留任意深度结构。容器分类为冰箱、液氮罐、柜体、层架、提篮、抽屉、盒、逻辑分区、其他。位置最多同时占用一个实物，POSITION 的 kind 不通过编辑改变。人为划分的区域可以作为容器，跨位置逻辑集合尚未实现。

Facility 新增 location、disabledAt、revision；StorageTopology 新增 revision；StorageNode 新增 containerType、description、disabledAt、rowCount、columnCount。公开行列坐标从 1 开始；成对、同级唯一、在父网格范围内。网格中实际未创建的格子不视为可用位置。

节点编号改为同父节点唯一；根节点通过部分唯一索引保证同拓扑根级唯一。归档仍保留编号，不借归档复用历史节点身份。设施编号仍在组织内唯一。

停用不隐藏既有内容，但可用位置候选排除设施或任一祖先已停用/归档、已有占用的节点。归档先检查占用与活动下级，恢复要求父级有效。更换管理工作区和撤销使用关系时检查原工作区存量，不删除 Placement。

## 授权与显式初始化

| 权限 | Scope | 用途 |
| --- | --- | --- |
| facility.create | ORGANIZATION | 登记设施；同时要求治理权限以指定管理关系 |
| facility.govern | ORGANIZATION | 组织管理入口、管理工作区、共享关系、设施生命周期 |
| facility.read | WORKSPACE | 在合法设施关系范围内浏览 |
| facility.use | WORKSPACE | 选取可使用位置，供后续库存用例重新验证 |
| facility.manage | WORKSPACE | 在管理工作区或 MANAGE 共享关系内维护结构 |

工作区访问取有效成员、动作权限和设施关系的交集。USE 不允许维护结构；MANAGE 不允许自行重新共享或变更设施管理工作区。无 workspaceId 的组织管理入口要求 facility.govern，不能借省略工作区参数绕开授权。

新组织的 owner 角色获得设施创建/治理权限，新建 workspace-manager 角色的默认定义包含设施 read/use/manage。已有角色不由启动或读取修复。

已有组织通过 `GET /organization/:organizationId/facility/context` 读取 canCreate/canGovern/canInitialize。组织所有者显式调用 `POST /organization/:organizationId/facility/initialize`，在组织锁内补齐受保护 owner 角色，以及仍有效的 workspace-manager 角色所需设施权限，写入审计。重复调用无变更时返回 updated=false。其他角色仍通过 P06 显式授权。

## 实现分工

FacilityService 管设施资料、初始化和共享；StorageStructureService 管节点业务；FacilityAccessService 集中组合设施关系与动作权限。FacilityOperations 管两类用例共用的身份、事务传播、锁后授权、错误映射和审计入口，不对外暴露底层服务容器。

底层仍通过 DatabaseRuntime.queryClient 访问当前事务。写入采用 OrganizationWriteKernel 的 ReadCommitted 协议，再按固定顺序锁拓扑。新增 ResourceKernel.createBatch 仅创建同组织、同 kind 的有界身份集合；返回 ID 无输入排序含义。孔位生成一次读取父节点和排序，批量写入资源及节点，失败整体回滚。

列表和统计先应用设施访问条件。节点查询在已获准设施/拓扑范围内执行，游标绑定查询上下文和拓扑 revision，不能用作权限凭据。节点事实由有界 SQL 查询；没有为每个节点逐项调用权限引擎或读取材料内容。

Facility、Topology、Node 的 Resource Provider 均返回真实组织归属。ResourceLookup 新增可选 accessContext，设施 Provider 验证其中的当前操作上下文；expectedScope 仍只限制资源归属，不充当使用工作区。缺少访问上下文时不返回设施描述。Material Provider 语义不变。

## 跨设施搬迁

移动明确接收来源和目标拓扑及各自 expected revision、目标设施、父节点和必要的新编号/坐标。来源和目标设施分别鉴权；禁止跨组织、循环、目标类型不符、编号或坐标冲突。

原生函数 `storage_node_move` 改为八参数，旧四参数入口已移除。topologyId 不再一概不可变；节点 ID、组织和 kind 仍不可变。父子复合外键使用 NO ACTION 和事务末延迟检查，保持最终一致性；原生 guard、路径一致性验证和拓扑锁继续生效，没有关闭触发器绕过约束。

全部后代（包括归档后代）的 topologyId 和路径在同一事务中迁移；ResourceIdentity 和节点 ID 不变。审计保存来源/目标设施、拓扑、前后路径和目标父节点。普通结构入口发现子树存在 Placement 即拒绝，不隐式迁移库存。

P09 必须在组织写锁后、同一受管事务内调用 FacilityPositionReader.requireAvailable，并在实际写占用时处理唯一位置竞争。该 Reader 只是当前观察，不锁定或预留位置。P09 的库存写入必须参加相同锁协议，才能与结构归档、迁移和撤权正确协调。

带存量搬迁需要 Inventory 编排结构移动、实物授权和历史路径流水。多个工作区各自保留库存和流水归属，整体同事务提交；这项仍待 P09。

## 前端接口交接

公开 Schema、类型和错误契约位于 `@talos-ark/contracts/facility`；后端错误协议目录位于 `@talos-ark/contracts/backend`。控制器通过 ApiRoute 校验请求和响应包络。

设施前缀：`/organization/:organizationId/facility`。

| Method / 后缀 | 输入 | 输出 data |
| --- | --- | --- |
| GET context | 组织参数 | FacilityGovernanceSchema |
| POST initialize | 组织参数 | FacilityInitializeSchema |
| GET 空后缀 | FacilityQuerySchema，含可选 workspaceId | FacilityPageSchema |
| POST 空后缀 | FacilityWriteSchema | FacilitySchema |
| GET :facilityId | 可选 workspaceId | FacilityDetailSchema |
| PATCH :facilityId | FacilityUpdateSchema，含 expectedRevision | FacilitySchema |
| POST :facilityId/state | FacilityStateSchema | FacilitySchema |
| POST :facilityId/access | FacilityGrantSchema，level=null 表示撤销 | StorageMutationSchema |

节点前缀：`/organization/:organizationId/facility/:facilityId/topology/:topologyId/node`。

| Method / 后缀 | 输入 | 输出 data |
| --- | --- | --- |
| GET 空后缀 | StorageQuerySchema；mode=children/search/positions | StorageNodePageSchema |
| GET :nodeId | 可选 workspaceId | StorageNodeDetailSchema |
| POST 空后缀 | StorageNodeCreateSchema | StorageNodeDetailSchema |
| PATCH :nodeId | StorageNodeUpdateSchema | StorageNodeDetailSchema |
| POST :nodeId/state | StorageNodeStateSchema | StorageMutationSchema |
| POST :nodeId/move | StorageNodeMoveSchema | StorageMoveResultSchema |
| POST :nodeId/reorder | StorageNodeReorderSchema，beforeNodeId=null 表示移到末尾 | StorageMutationSchema |
| POST :nodeId/grid | StorageGridSchema，1..1000 个明确孔位 | StorageMutationSchema |

节点列表和查询默认 limit=50、最大100；设施列表使用 page/pageSize。parentId 省略表示根级；位置选择可指定 parentId 限定子树。详情带合法祖先路径、revision 和 capability；位置的 usable/unavailableReason 已考虑生命周期与占用，但提交入库时仍须重验。

前端旧 data/source.ts 是此前的候选适配接口，不是本轮的 wire 契约。需要将 managementWorkspaceId 映射为合法工作区显示，使用单个 topology 对象，不能继续假定后端返回 topologies 或完整管理工作区对象。共享关系仅治理入口返回，普通使用入口为 null。资源深链通过 organization/workspace/facility/node query 指明范围，前端接入时校对路由参数。

读接口返回 Cache-Control: no-store。资料编辑使用 Facility revision；所有结构动作使用拓扑 revision，跨拓扑迁移同时校验双方。409 后重新读取并保留合法草稿，不盲目自动重放。前端依 capability 展示动作，后端仍每次重新鉴权。

## 验证与环境边界

本轮先只读确认目标为本机 talos-ark_backend_test，Facility、StorageNode、Placement 均为零，ltree 已存在。仅同步 P08 所需字段、枚举、索引、父子外键和存储树 DDL；没有对当前完整 Prisma Schema 执行 db push，未将其他会话尚未同步的文件模块模型带入测试库，也未操作 dev/prod。

采用真实 PostgreSQL、实际 Nest FacilityModule、Permission/Authorization/Resource/Audit、DatabaseRuntime 和受管事务完成 12 组定向场景：显式初始化、共享权限交集、批量回滚与同级编号、跨设施迁移、根级唯一与重排和设施生命周期、位置查询与资源上下文、修订冲突与并发、祖先停用与游标失效、审计失败回滚、合成 HTTP 响应契约、最大批量和占用保护。HTTP 使用合成受信身份，不代表登录到前端的真实端到端验收。

1000 孔位批量创建在本机一次合成运行约 273 毫秒，另一次为 389 毫秒，均在默认事务预算内；该数据不是生产负载或远程数据库性能承诺。验收合成业务记录按本轮专用组织与用户 ID 清理，没有清空已有库。

Contracts 构建、后端独立输出目录的完整 TypeScript 编译及 tsc-alias、Prisma format/validate、定向 ESLint 已执行。标准 Nest build 首次遇到共享 dist 目录 ENOTEMPTY，未删除或重置用户正在使用的输出，改为隔离目录编译并执行上述运行验收。临时探针在忽略的 output 下，不增加长期测试脚本。

前端真实接线、浏览器页面验收、真实会话链路、生产数据升级和 P09 带存量搬迁尚未执行。
