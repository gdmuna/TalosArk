# I01：邮件发送基础设施

实施日期：2026-10-13。对应 [基础设施计划 I01](mvp-foundation-work-plan.md)。
本轮只交付邮件公共能力，不实现密码恢复、邀请、邮件模板、Outbox 或后台重试。
P02/P06 仍由主线完成；本文不是它们的完成记录。

## 1. 这次怎么设计

参考现有 Storage/IAM 的做法：配置由调用方显式提供，模块不读全局 ConfigService；Nest 管理实例和关闭。
错误使用现有 owner-local 工厂，诊断接现有 Pino 基座，不创建另一套日志或错误体系。

对外只有一个 MailService，业务模块不用认识 Nodemailer。内部职责如下：

| 文件                                                                      | 做什么                                                  |
| ------------------------------------------------------------------------- | ------------------------------------------------------- |
| [mail.module.ts](../../src/infra/mail/mail.module.ts)                     | 同步/异步配置与 Nest 装配，只导出 MailService Provider  |
| [mail.options.ts](../../src/infra/mail/mail.options.ts)                   | 配置校验、默认值和不可变配置快照                        |
| [mail.contract.ts](../../src/infra/mail/mail.contract.ts)                 | 邮件输入、取消信号、SMTP 接收结果；没有 SDK 类型        |
| [mail.service.ts](../../src/infra/mail/mail.service.ts)                   | 参数检查、启动验证、业务调用入口和安全摘要日志          |
| [mail.transport.ts](../../src/infra/mail/mail.transport.ts)               | SMTP 连接、认证、MIME、期限、并发限制与实际清理         |
| [mail.error.normalize.ts](../../src/infra/mail/mail.error.normalize.ts)   | 归一化已识别的 SDK 错误，保留 cause；未知程序错误不改写 |
| [mail.error.diagnostic.ts](../../src/infra/mail/mail.error.diagnostic.ts) | 只投影安全、英文诊断，不输出服务端原始回复或凭据        |

继续使用 Nodemailer 的 SMTPConnection 和 MailComposer，未重写 SMTP 协议或 MIME。
选择管理连接，是因为当前普通 SMTP transporter 的 `close()` 并不终止在途发送；只写 Promise.race 会让调用超时而实际工作继续。
内部使用 SDK 标明为 public 的 `_socket` 完成强制销毁，没有修改 SDK 或扫描连接池私有成员。
这是技术适配层的版本耦合；升级 Nodemailer 时须重新检查关闭、TLS、MIME 和错误行为，业务接口不因此暴露 SDK。

## 2. 主线怎么接

在实际需要发邮件的业务 Module 中注册，不在 AppModule 默认启用，也不是全局 Module：

```ts
import { ConfigModule, ConfigService } from '@nestjs/config';
import type { AllConfig } from '@/config/index.js';
import { MailModule } from '@/infra/mail/index.js';

MailModule.forRootAsync({
    imports: [ConfigModule],
    inject: [ConfigService],
    useFactory: (config: ConfigService<AllConfig, true>) => ({
        options: config.get('mail', { infer: true }),
    }),
});
```

也可用 `MailModule.forRoot({ options: ... })` 直接提供配置。
业务通过 Nest 注入 MailService，不自己 new Transporter。

```ts
const result = await mail.sendMail(
    {
        to: 'reader@example.test',
        subject: 'Account recovery',
        text: 'The business module supplies the recovery message.',
    },
    { signal }
);

// result.status: accepted | partial
// result.messageId: 本次 MIME Message-ID，不是幂等凭据。
// result.accepted / result.rejected: 本次 SMTP 接收/拒绝的收件人地址。
```

输入支持一个 mailbox 或 1-50 个 mailbox，可带显示名；每项最长 1024 字符，不接受地址组或逗号分隔列表。
地址格式使用 Nodemailer 的解析器校验，不自行实现 RFC 地址解析，from/to 均拒绝换行。
正文至少提供非空 text 或 html；同时提供时使用 MIME alternative。
不接受任意 Nodemailer 参数、附件路径、URL 内容源、逐封认证或逐封发件人覆盖。
文件用途、模板和 HTML 内容的安全规则仍由业务所有者负责。

**兼容性变化：** 裸 `MailModule` 不再注册服务，必须显式 forRoot/forRootAsync；`sendMail` 从 void 返回改为上述结果。
from/to 仍支持 `TalosArk <sender@example.test>` 这样的显示名；多收件人使用数组。
源码核对未发现旧业务调用方，本轮没有改变已有账户操作。

## 3. 配置和安全默认值

[环境示例](../../secrets/env/.env.example) 已加入 SMTP 字段。实际提供商未指定，未改写现有环境的 SMTP 凭据。
新增时限使用模块默认值，主线启用模块前再配置 host/from/必要认证。

| 配置                       | 默认值/含义                                                         |
| -------------------------- | ------------------------------------------------------------------- |
| SMTP_HOST / SMTP_FROM      | 无可用默认；模块实例创建时必须有效，from 为一个可带显示名的 mailbox |
| SMTP_PORT                  | 465                                                                 |
| SMTP_SECURE                | 未指定时按端口推断：465 为 true，其他端口为 false                   |
| SMTP_REQUIRE_TLS           | true；非隐式 TLS 连接必须升级 STARTTLS                              |
| SMTP_SERVERNAME            | 可选；IP 连接需与证书域名匹配时显式指定                             |
| SMTP_USER / SMTP_PASS      | 可都省略用于可信 relay；不能只配置一个，也不允许明文认证            |
| SMTP_CONNECTION_TIMEOUT_MS | 15000；连接等待上限                                                 |
| SMTP_GREETING_TIMEOUT_MS   | 10000；服务器问候等待上限                                           |
| SMTP_SOCKET_TIMEOUT_MS     | 15000；socket 空闲上限，不是整次操作时限                            |
| SMTP_DNS_TIMEOUT_MS        | 5000；DNS 等待上限                                                  |
| SMTP_SEND_TIMEOUT_MS       | 30000；verify/send 整次操作上限，包含连接、认证和 DATA              |
| SMTP_CLOSE_TIMEOUT_MS      | 2000；关闭时等待在途操作的预算                                      |
| SMTP_MAX_CONCURRENT_SENDS  | 3；范围 1-20，包括 verify；超出时返回 busy，不建立无界内存队列      |

各时限为 1-120000ms。应用装配时须让关闭预算符合现有进程关闭预算，模块不擅自读取全局 lifecycle 配置。
端口 465 不允许显式关闭隐式 TLS；587 通常使用 secure=false 与 requireTLS=true。
证书校验始终开启，最低 TLS 1.2，没有 `rejectUnauthorized=false` 出口。
仅可信、无认证 relay 才可显式放宽 requireTLS。需要内部 CA 时通过部署的 Node 信任配置提供，不关闭证书验证。
SMTP/TLS 选项依据 [Nodemailer 官方说明](https://nodemailer.com/smtp)。

模块注册时冻结已验证的配置，不在每封发送时重新读取环境。
Nest 初始化时执行 verify：连接、TLS 和配置的认证失败会使该模块启动失败；不发送邮件，也不证明某个发件人一定会被接受。
未启用 MailModule 时不访问 SMTP；环境解析仍检查已经填写的端口、布尔值和时限是否有效。

## 4. 结果和错误怎么理解

`accepted` 表示服务器对 DATA 给出成功响应；不是邮件进入收件箱的保证。
`partial` 表示部分收件人被接收、其余被拒绝。调用方应明确处理拒绝名单，不把整封邮件无条件重发。

MailError 的私有 failure 包括 reason、operation、phase、outcome 和必要的数字 SMTP 状态；不直接作为公开 HTTP 错误契约。
业务按自身含义转换错误，原始 SDK cause 仅用于现有安全诊断链。

| reason              | 调用方需要知道什么                                                      |
| ------------------- | ----------------------------------------------------------------------- |
| configuration       | 静态配置、认证或已识别的 TLS 配置错误；静态校验只报告字段名，不附带输入 |
| invalid-request     | 邮件输入或已识别的消息构造错误                                          |
| unavailable         | 网络/服务问题，或 SMTP 暂时拒绝；不意味着适合无条件重试                 |
| rejected            | 服务器明确拒绝，保留数字状态，不输出原始回复                            |
| timeout / cancelled | 等待结束或调用被取消，连接与流会终止；已经开始发送时可能无法确认结果    |
| busy                | 已达到并发上限，本次未发送                                              |
| closed              | 模块正在或已经关闭；关闭预算到期时也用于拒绝被终止的在途操作            |
| close-timeout       | 等待关闭预算耗尽，已强制清理，但不将此次停机报成成功                    |
| invalid-response    | 发送返回值不足以确认成功，不能随意报告已送达                            |

outcome 的口径：

- `not-sent`：本次尚未进入发送，或已知在 DATA 前失败。
- `rejected`：已得到明确 SMTP 拒绝响应。
- `unknown`：发送已开始，但缺少足以判断结果的响应；服务器可能已经接收。

网络错误在 MAIL/RCPT 阶段能证明未发出时返回 not-sent，其余不确定发送保守返回 unknown。
SDK 覆盖了部分 TLS 错误代码：证书域名不匹配可通过保留结构识别，无法确认根因的 socket 错误不按文案猜测。
无论哪种结果，都没有隐藏重试、自动重新排队或 SingleFlight 合并。
若 P02 要求自动可靠重试，先确认凭据载荷的安全和重复发送语义，再实施 I09，不能用 afterCommit 冒充可靠投递。

## 5. 关闭与日志

关闭时停止接受新操作，等待当前操作完成；超过预算后终止所有在途连接与 MIME 流，再报告 close-timeout。
重复关闭复用同一次关闭结果，不另装 SIGTERM/SIGINT 处理，不改变现有进程关闭顺序。
SDK 内尚未结束的 DNS 工作遵循 DNS 时限；取消后不再进入发送，已创建的 SMTP socket 会被销毁。

正常日志只有英文消息、事件、耗时、状态和人数统计；不记录收件地址、标题、正文、认证或链接。
Nodemailer 协议/debug 日志关闭。模块不重复记录将向上传播的失败；最终失败由既有边界记录。
MailError 加入现有显式错误诊断组合，未创建自动注册机制或新的全局错误分类。

## 6. 实际验证

遵循当前迭代政策，没有增加或维护仓库测试脚本，也没有更改数据库。
一次性检查使用编译产物和只监听 loopback 的合成 SMTP，所有收件人、内容和认证均为合成数据。

| 检查                 | 结果                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 普通 SMTP 与错误行为 | 49 项通过：MIME alternative、完整/部分接收、永久/暂时拒绝、发送断连、取消、并发上限、配置快照、总超时、正常/超预算关闭与安全日志 |
| TLS、认证、Nest 装配 | 12 项通过：隐式 TLS、STARTTLS、错误凭据、证书域名不匹配、forRoot/forRootAsync、启动 verify 与关闭、连接拒绝                      |
| 不可信证书           | 移除临时 CA 信任的独立进程中正确拒绝自签名证书                                                                                   |
| 环境配置             | 默认值、587 的 TLS 推断、布尔/数字解析与非法配置拒绝通过                                                                         |
| TypeScript 公开接口  | 正常调用通过；6 种 SDK/凭据/附件/结果类型等错误用法被拒绝                                                                        |
| 构建与静态检查       | backend/contract 构建、定向 ESLint、格式与差异检查通过；首次 Windows ENOTEMPTY 清理失败重试后通过                                |

TLS 使用 OpenSSL 生成的临时本地证书，信任仅对探针进程设置；检查后清理生成物，不修改用户或系统 CA。
没有连接真实 SMTP 提供商、发送真实邮件、启动完整 AppModule 或验收 P02/P06 业务；没有收件箱送达证据。
主线接入时仍须检查真实发件身份、供应商限制、失败提示、恢复链接及必要的可靠性要求。
