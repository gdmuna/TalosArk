# Storage 对象存储契约与 W06 实施记录

日期：2026-10-12。用户批准在 W06 协议修复基础上重整 Storage，以便接入 File。

## 范围与职责

依赖方向：`业务模块 -> FileKernel -> StorageService -> S3 SDK`。

- Storage 负责对象、流、预签名、分片协议、元信息及技术错误归一化。
- File 负责上传会话、用途与授权编排、核验和就绪、资产与业务引用、转正及清理恢复。
- 业务模块定义具体附件用途和资源绑定/读取规则；Composition 显式装配技术依赖。
- File 仍是 TODO 骨架。本轮没有实现 File 服务、公开文件接口、数据库状态推进、清理作业或多云路由。
- 不建立与 Storage 等价的转发 Port，不把 SDK 类型带入 Core 的公开契约。

## 契约与破坏性变化

当前源码没有业务 Storage 调用方，因此不保留兼容包装。公开 HTTP 契约没有变化。

| 旧接口                                   | 新接口/处理                                                                        |
| ---------------------------------------- | ---------------------------------------------------------------------------------- |
| 桶别名或任意字符串 + key                 | 显式 `ObjectLocation { bucket, key }`，key 必须是原始未编码值                      |
| `resolveBucket` / `stagingBucket`        | 移除；部署桶名仍保留在 typed StorageConfig，File 决定使用策略                      |
| `getUploadUrl` / `getDownloadUrl`        | `presignUpload` / `presignDownload`，返回 `PresignedRequest`                       |
| `getUploadUrlCAS`                        | 移除；普通上传的 `sha256` 选项保留校验能力，不决定暂存键或去重规则                 |
| `promoteFromStaging`                     | 移除；独立 `copyObject` / `deleteObject`，不隐藏跨系统状态推进                     |
| `objectExists` / `getObjectSize`         | `statObject`；不存在抛 `not-found`，缺失大小抛 `invalid-response` 而非伪造零       |
| `initMultipartUpload` 一次性生成所有 URL | `createMultipartUpload` 只创建句柄；`presignMultipartPart` 按需签指定分片          |
| `getResumablePartUrls`                   | `listMultipartParts` 返回所有 provider-confirmed 分片；File 决定剩余清单与签名窗口 |
| SDK `CompletedPart`                      | 自有 `MultipartCompletionPart`，校验编号/ETag/重复项，复制后排序，不修改调用方数组 |
| `deleteObjects(bucket, keys)`            | 对象位置数组，按桶与最多 1000 项分批；空数组不发请求                               |
| Module 导出 S3Client / S3_OPTIONS        | 仅导出 StorageService；SDK client 由 Module 内部创建并在销毁时关闭                 |

`getPublicUrl` 仍是 URL 构造器，保留 `base/bucket/key` 语义。配置的 `publicBaseUrl`
是路径前缀，不是已经包含桶名的 URL；缺省使用 endpoint。它不证明对象公开、不检查权限，
也不跟随 SDK 的 virtual-host addressing 改变分发 URL。需要独立公开分发路由时应显式配置此前缀。
原始 key 按 segment 编码，保留 `/` 层级；原始 `%2F` 会表示字面字符，而不是另一个路径分隔符。

## 签名、核验与错误

- 预签名结果包括 `url / method / headers / expiresAt`；上传方必须原样发送 headers。
  Content-Type 和 SHA-256 header 被纳入签名；校验和保留为请求头，不依赖 SDK 自动生成 CRC32。
- 签名有效期默认 3600 秒，允许 1 至 604800 秒；expiresAt 是名义签名截止时间，底层凭据可能更早失效。
- 单对象写入和指定分片写入接受 64 位十六进制 SHA-256，由 Storage 翻译为协议格式。
  multipart 初始化可声明 SHA-256 算法；采用此算法时 File 必须保留并提交每片校验信息。
- SDK 自动分片的 `uploadStream` 不接受一个冒充 multipart 校验和的完整文件 SHA-256；
  仍使用 AWS Upload 的背压、有限并发与失败分片清理机制。
- `statObject({ ... }, { checksum: true })` 显式请求 provider 的校验信息。
  返回的 `checksum.value` 是 provider 原值；类型可能是 `full-object`、`composite` 或未知。
  ETag 不是内容哈希，未知类型不能默认当作完整文件 SHA-256。
- Content-Type 是声明信息，不是文件内容识别；对象存在和大小正确也不等于 File 的用途核验完成。
- `listMultipartParts` 内部处理全部分页，不信任客户端的已完成列表。缺失、越界或不推进的
  marker，以及无效/重复分片元信息，均拒绝为 `invalid-response`，不返回静默截断集合。
- 增加 `invalid-request`（非法签名有效期、摘要、分片编号/完成清单）及 `stat` operation。
  provider 的 `BadDigest` 归一化为 `checksum-mismatch`，File 不必识别 SDK 原生类。
  `partial-delete` 的私有 failure 携带失败对象与 provider code；失败不会伪装成全批成功。
- 批量删除不是原子操作，后批失败时前批可能已成功；复制不删除源，分片完成不推进数据库。
- 保留 SDK/网络错误归一化、cause 和晚到流错误处理；未知错误继续抛出。
  File 未来通过 owner-local mapper 重述已知 StorageError，本轮没有追加公开错误 catalog 或重试层。

## File 接入要求（尚未实现）

首次附件切片需要持久化上传意图、所属组织/上传者、对象位置、预期大小/校验信息与有效期。
对续传、完成和取消先校验会话权限，不接受客户端任意提交的 bucket/key/uploadId。
完成时核对预期清单并验证对象，然后才推进 FileObject 就绪和后续 FileAsset/Reference。

对象复制/上传与数据库事务不能被包装为同一个原子操作。File 必须能识别并恢复或清理
“对象已写入但数据库未提交”“复制完成但源清理失败”等状态，不以一次技术操作成功代替业务提交。
暂存键应按实际会话隔离；内容相同不授予共享权限，不自动开启跨组织去重或复用。
具体状态机和恢复方案随首个批准的附件用例实施，不在本轮构造队列或 Saga 框架。

## 验证记录

没有新增或维护测试文件；一次性探针通过 stdin 执行，没有落盘为仓库测试。

- backend / contract 构建通过；Storage 与相关配置文件的 ESLint、格式和 diff 检查通过。
- 安装 SDK + stub 一次性探针通过 68 项断言：1001 分片跨页合并、异常 marker、清单校验/
  非突变排序、批量分组与分批、失败明细、特殊 key、错误 cause/未知错误、晚到流错误、
  true/false/缺省 addressing、分片签名参数、必需签名请求头及签名到期时间。
- 真实 Nest 装配探针通过同步/异步两种 factory：不读取环境配置兜底，缺省 region 一致，
  显式 false 保留，每个模块关闭恰好一次 SDK client。
- 临时 RustFS 使用本机已有 image 的固定 ID、合成凭据、独立随机端口和 tmpfs；
  真实请求通过 18 项断言：直传与错误 SHA-256 拒绝、BadDigest 归一化、签名下载、HEAD、
  特殊 key 跨桶复制且保留源、11 MiB 三分片上传/续传查询/完成、取消、带 SHA-256 的两分片
  签名/错误摘要拒绝/合并、6 MiB SDK 自动分片及流式下载、删除和 not-found。
- 临时 RustFS 的单对象 HEAD 返回 SHA-256 值但没有返回 checksum 类型；multipart HEAD 返回
  composite SHA-256，ListParts 未返回每片摘要。实现保留缺失，不推断不存在的核验证据。
- 临时容器与其 tmpfs 数据已经移除。
- 未使用既有 RustFS/PostgreSQL/KVS/Casdoor 数据或凭据，未执行数据库同步。
- 未验证 AWS 云端、真实公网 virtual-host DNS/CORS、生产桶策略、断网提交结果不明、
  真实 File 生命周期或业务恢复。1001 分片分页使用模拟响应，不冒充云端分页验收。
