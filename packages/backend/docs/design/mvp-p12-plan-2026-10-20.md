# P12 固定审批代码级实施方案

日期：2026-10-20。状态：已实施，后端与前端本地真实定向验收通过，见[联合验收记录](../../../../docs/product/mvp-p12-acceptance-2026-10-20.md)。下文保留实施方案及实施前核对依据；以末节的实际落点和验收记录为准。业务依据为[已确认的 P12 对齐记录](../../../../docs/product/mvp-p12-alignment-2026-10-20.md)，任务入口为[MVP 工作清单](../../../../docs/product/mvp-work-plan.md#p12完成固定审批并保持批准与执行分开)。

## 1. 本轮交付与职责

交付消耗和转移申请，一单一种动作、多件实物、指定一名非申请人的审批人。一次决定全部明细，可以部分批准；申请人逐明细执行，每条最多成功一次。待审批整单可撤回，获批未执行明细可放弃或撤销。读单、恢复结果和工作台摘要属于本轮。

Approval 拥有申请、审批决定、获批资格的生命周期和单据可见性；Inventory 拥有库存校验、数量和占位变化、实际流水及库存回执；Facility 提供位置事实、当前治理设施和设施授权。Approval 不直接改 StockItem 或 Placement，Inventory 不反向导入 ApprovalModule 或解释审批状态。

不扩建通用工作流、授权插件注册器或批量引擎。不做整件借出、普通归还、自动到期、服务端草稿、通知交付、跨单批量审批及多明细一键执行。

## 2. 实施前核对的问题

| 当前文件或结构 | 事实 | 对应改动 |
| --- | --- | --- |
| `modules/approval/approval.module.ts`、`api/approval.controller.ts` | 仍为 TODO 骨架 | 实现真实用例、装配和 HTTP 契约 |
| `prisma/model/approval.prisma` | 有多条明细，但决定仅在整单，明细无审批结论 | 分开保存整单生命周期、明细决定和明细执行结果 |

## 4. 数据模型与状态

| 对象 | 拟定内容 | 不变量 |
| --- | --- | --- |
| ApprovalRequest | 组织/工作区、ResourceIdentity、CONSUME 或 TRANSFER、申请人、审批人、标题/说明、原申请引用、版本及时间 | 提交后意图不改；同工作区；禁止自审；新申请另建身份 |
| 整单生命周期 | PENDING、DECIDED、WITHDRAWN | PENDING 只能决定或撤回；不重新开启旧单 |
| ApprovalLine | 同域 StockItem、稳定行序、申请数量或目标、来源 POSITION/设施绑定、转移目标 POSITION/设施绑定、单位及展示快照 | 同单实物唯一；消耗为精确正数量；转移不使用“转移部分数量”字段 |
| 明细决定 | UNDECIDED、APPROVED、REJECTED，及决定时间/意见 | 一次提交覆盖全部明细；不遗漏、不重复、不接受外单行 ID |
| 明细执行 | 未批准时为空；获批后 PENDING、EXECUTED、ABANDONED、REVOKED | 临时阻塞不是新的持久化终局；只能成功执行或终结一次 |
| ApprovalEvent | 单据、可选明细、动作、操作者、时间和可选意见 | 保留提交、决定、撤回、放弃、撤销和执行事实；不覆盖旧事件 |
| ApprovalOperation | 当前作用域/操作者、操作、幂等键、指纹、完成结果 | 用于提交和审批生命周期命令，适配已有 IdempotencyKernel |
| InventoryTransaction | 可空的 approvalLineId，与实际获批明细同组织/工作区关联且唯一 | 直接操作为空；一条获批明细至多对应一笔实际库存流水 |

“全部批准、部分批准、全部拒绝”从明细决定汇总；“执行中、部分完成、全部已终结”从获批明细进度汇总。全部拒绝不能显示为全部执行成功；撤回单的未决定明细不能继续计入待审批。

保持 Decimal(20,6) 与材料数量精度。公开数量使用字符串，不经过 JavaScript number。来源和目标绑定由服务端读取，不能接受客户端自报的治理设施作为可信事实。快照不替代当前资源读取授权。

审批执行的成功回执仍归属 InventoryOperation，使用单独的操作标识并包含申请/明细关联；不为同一次执行再建第二份独立完成的审批幂等回执。数据库唯一关联同时阻止使用不同幂等键重复执行同一明细。

CHECK 约束动作与数量/目标字段的一致性、决定与执行状态的合法组合、执行关联和终局字段的一致性。跨行、跨表的业务授权不伪装成 CHECK 能保证的事情。原有整单 approvalRequestId 唯一执行关系必须移除。

## 5. 审批与库存如何协作

保留 `InventoryActionService.execute` 的直接入口及其权限含义。提取事务内的 `InventoryActionWriter`，集中负责当前库存事实、精确数量、有效期、来源生命周期、设施使用权、目标可用性、版本 CAS、占位、流水、库存审计和库存幂等回执。两条真实调用路径共用它，不复制库存算法。

Writer 是可信的模块间应用接口，必须处于既有 ReadCommitted 写事务，保留成员、资源读取和设施授权检查。直接用例先检查 `inventory.consume/transfer/...`；审批执行用例先检查自己的申请资格、参与身份、有效批准和范围绑定。调用契约明确各自必须完成的动作授权，不向 HTTP 暴露 `skipPermission`、`approved: true` 或可伪造的权限分支。

审批执行只从数据库里的申请明细产生实物、用量、来源和目标；执行请求不再次接收一套可替换的数量或目标。Approval 可以调用 Inventory 的窄事实读取接口准备申请及检查绑定，但不能越过其写接口直接改库存表。

单条执行使用一次 `OrganizationWriteKernel.run`：

1. 获取组织写锁，检查申请人当前资格、有效成员、单据身份和读取权。
2. 先识别已经成功的原明细或原请求；在当前授权下恢复并投影结果，不对成功事实重跑新写入前置条件。
3. 新执行要求整单已决定、该明细已批准且待执行；读取当前来源及转移目标，比较 POSITION 和治理设施绑定。
4. 以数据库明细内容调用共用 Writer，在当前库存版本上完成库存操作。
5. 同事务将明细标记已执行，关联实际流水，记录审批事件/审计并完成回执，任一步失败全部回滚。

执行与放弃/撤销使用相同写锁次序及明细状态 CAS，只有一方能提交有效终局。整单审批与撤回也按当前版本互斥。保持现有组织锁方案，不借本轮启动 1.0 并发架构重做。

申请时的库存版本只是观察信息，不能永久当作执行 expectedVersion。执行使用新读取的当前版本作并发保护；界面过旧可以冲突并刷新重试，但不因此要求重新审批。新请求若变更 expectedVersion，应在已确认原请求未成功后重新构造请求，不能变更旧幂等键对应的原始请求体。

恢复入口区分“当前还能否新执行”与“当前能否读取已成功事实”。不再使用直接动作权限拦截审批回执；也不因实物后来移动、已处置或当前来源停用，就把过去成功变成失败。资源和位置字段继续按当前权限隐藏，恢复结果从真实流水读取，不能把原始持久化快照直接返回。

## 6. 权限、读取与资源装配

| 拟定权限 | 作用 |
| --- | --- |
| approval.consume.apply / approval.transfer.apply | 对应动作的申请资格；获批执行时仍检查当前资格 |
| approval.consume.review / approval.transfer.review | 对应动作的审批资格；指定审批人自审永远禁止 |
| approval.read.all | 非参与者查询同工作区单据，仍不替代资源读取权 |
| approval.revoke | 独立撤销尚未执行批准的资格，不隐含直接库存操作权 |

参与者的有效成员资格和单据关系由 Approval 检查，资源动作由 AuthorizationKernel 判定。拥有独立撤销权限仍须处于正确工作区并通过必要读取检查，不能拿任意其他组织的明细 ID 试探数据。

候选审批人来自同工作区有效成员，排除申请人，并满足对应审批权限及所选资源访问资格；查询候选人之前先验证调用方的申请资格及所选对象读取权。实际提交与审批再核验，不信任候选列表快照。审批人合法决定后失去资格，不触发历史批准的自动失效。

在现有 bootstrap composition 贡献审批权限及默认角色策略，不绕过现有发现/授权机制，不根据前端角色名称硬编码放行。Approval Resource Provider 提供授权后的描述；默认标题不自动拼入可能失权后仍外露的材料或位置名称。明细当前不可见时返回受限投影，不从历史标签补回名称、数量、位置路径或隐藏标识。

## 7. 公开契约和入口

新增 `@talos-ark/contracts/approval` 子路径及后端错误定义。Controller 沿用 Method + ApiRoute，声明请求、成功与错误 schema，保持运行时校验及 `Cache-Control: no-store`。已知领域失败按现有工厂/mapper 体系表达，不新建另一套异常或响应包络。

以下均位于 `/organization/:organizationId/workspace/:workspaceId/approval`，名称在实施时按现有路由习惯落实：

| 方法/相对路径 | 作用 |
| --- | --- |
| GET context、POST approver/query | 当前申请能力、合资格审批人；多件选择放请求体而非 URL |
| POST / | 创建并立即提交整单；可引用原单建立重新申请关系 |
| GET /、GET summary | 我的申请、待我审批、待我执行及授权管理查询；按服务端当前范围过滤 |
| GET :requestId、GET :requestId/line | 单据与分页明细，分别投影权限 |
| POST :requestId/decision | 一次提交全部明细的批准/拒绝，带当前单据版本与幂等键 |
| POST :requestId/withdraw | 申请人撤回待审批整单 |
| POST :requestId/line/:lineId/abandon | 申请人放弃未执行获批明细 |
| POST :requestId/line/:lineId/revoke | 当前合资格审批人或独立撤销授权者撤销未执行批准 |
| POST :requestId/line/:lineId/execute | 申请人执行一条获批明细，仅接收执行并发信息和幂等键 |
| GET operation/:operationId | 当前授权下恢复命令结果；审批生命周期与库存执行回执按操作类型分派 |

每条可执行明细还暴露已成功的稳定流水/回执引用，使响应丢失且客户端没有拿到 operationId 时，也能从明细真实状态恢复。幂等键作用域、操作者与操作均进入指纹；同键换内容报冲突，不猜测为另一种合法重试。

业务不以表格每页 100 条限制申请件数，也不把“多件申请”偷换为多个独立单据。提交和决定均覆盖完整明细集，展示用稳定行序分页；请求体仍受实际 HTTP 容量保护，超限必须整单明确失败，不能静默丢行或自动拆单。实施时核对实际容量，若确需新增业务条数上限，先说明而不能自行加入 `MAX_ITEMS = 100`。不为尚未出现的超大请求增加草稿或分片提交协议。

## 8. 前端交接

库存单件及多选入口可以发起同一种动作的一份多件申请，进入专用编辑界面填写各实物用量或目标、说明和审批人；提交后显示服务端固定内容。单据详情可以分页，但审核提交必须包含全单每条明确结论，不把未加载或未勾选行自动视为拒绝。

详情分开显示审批结论和各明细执行进度。获批且待执行明细展示执行、放弃及适用的撤销动作；临时不可执行显示当前原因。执行按钮每次只操作一条明细，跨单批量及多明细一键执行留 P13。前端展示不能替代服务端再次授权和校验。

Workbench 接入真实待审批/待执行摘要，前者按单据计数，后者按未终结获批明细计数。暂不可执行的获批明细不能被静默隐藏成已经完成。普通任务和异常来源没有真实接口时继续使用明确的既有可用性边界，不伪造新数据，也不全量重写工作台。

提交中保持原请求体和幂等键；结果不明先恢复原结果；明确成功后读取失败仅重读。退出或切换工作区后不得执行旧界面命令或将晚到响应写入新上下文。页面排版遵循现有设计整改计划与组件体系，具体接入见[前端记录](../../../frontend/docs/design/mvp-p12-2026-10-20.md)。

## 9. 实施顺序与验收范围

| 阶段 | 工作 | 验证出口 |
| --- | --- | --- |
| A | 契约、模型、合法状态组合和权限贡献 | 模型/类型检查，确认逐明细唯一执行关联及无旧整单约束 |
| B | 共用库存 Writer 与直接入口保持 | P11 定向验证直接操作和原回执恢复，没有扩大直接权限 |
| C | 提交、决定、撤回、放弃、撤销及授权查询 | 完整明细原子决定、部分批准、不可自审、单据版本竞争 |
| D | 审批逐明细执行及回执恢复 | 无直接权限的合资格申请人可执行；现有库存规则照常生效 |
| E | 前端按契约接入并联合验收 | 两名真实合成用户走通申请、部分批准、分别执行和刷新恢复 |

验收聚焦七组，不重复跑完 P01—P11：

1. 多件申请跨展示分页，全部明细明确决定，批准不改变库存；一条拒绝不能执行。
2. 申请人没有直接动作权但有当前申请资格时可执行；丧失当前资格后新执行被拒绝；审批人事后失权不追溯作废合法批准。
3. 余量变化仍足够时按获批量执行，不足时不执行；来源/目标治理不匹配时拒绝，恢复原绑定和条件后可重试；过期和停用继续按 P11 处理。
4. 两次执行使用相同或不同幂等键、执行与放弃/撤销竞争，均至多一笔库存流水且状态不矛盾；另一条明细不被失败项连带回滚。
5. 写入中后段失败整笔回滚；响应丢失恢复原结果；成功后只读同步失败不重放写入，也不因后来库存状态变化改判原结果。
6. 申请人、审批人和授权查询者在有效成员及当前资源权限下读取；成员移除、资源失权、旧快照和旧链接不能绕过限制。
7. Web 完成我的申请、待审批、待执行计数和真实动作；切换上下文与晚到响应不污染新页面；不冒充通知已交付。

实施验证沿用已授权的本地 test.local 边界，仅在核对目标为 `talos-ark_backend_test` 后写合成记录和必要结构，不操作 dev/prod、不发真实邮件。不为本轮新增长期维护的测试脚本；暂存定向验收工具在交付中列出。Tauri、生产环境和高负载性能单列，不以本地 Web 结果代替。

## 10. 实际落点

Approval 的应用服务、查询、执行、访问投影、幂等仓储、资源 Provider、授权贡献和错误定义均已落地。额外的 `approval-governance.service.ts` 只实现旧组织默认角色的显式、可审计、幂等初始化，不在启动时静默增权。`POST /organization/:organizationId/approval/initialize` 仅允许当前组织所有者或既有系统管理例外。

Inventory 的事实读取单独落在 `inventory-action.reader.ts`，只返回库存 ID/版本、精确数量、状态、必要材料展示与来源事实，不公开完整 Prisma 实体。Writer 保持事务强制，直接入口与审批入口共用真实库存规则；审批明细状态、库存事实、审计和幂等完成在同一物理事务提交。

公开数量为字符串；申请、明细、事件和结果均通过公开 schema 校验。明细决定与执行状态分别持久化，实际流水通过唯一 `approvalLineId` 关联。新原生约束由 `db:apply-approval-ddl` 应用。

实际交付包括本线程前端，不再仅为接口交接。15 组真实 HTTP/数据库验证、8 组 Web 场景及最终新构建冒烟通过；具体证据和未验收范围以联合验收记录为准。
