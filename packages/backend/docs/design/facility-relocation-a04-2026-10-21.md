# A04 搬迁准备结果与治理事实收敛

日期：2026-10-21。状态：决策记录草案；对应代码已实施，尚未写入 CONTEXT.md 或 ADR。

## 问题与实际调用方

`FacilityRelocation.prepare()` 原来返回完整 Facility、StorageTopology、StorageFact 和设施准入行，并公开输入、持锁标志及事务 ID；公共类型直接由实现的 ReturnType 推导。唯一业务调用方 `InventoryRelocationService` 读取这些行，拼出确认指纹，并自行解释“管理工作区加设施准入工作区”的治理规则。

这些完整行已经参与现有指纹行为，不能当作无用字段删除。A04 的收益是减少跨 module 需要理解的实现知识，将治理事实的解释集中在 Facility；不以减少预览冲突或提高运行性能作为已证明收益。

真实请求经 `InventoryOperationController.preview/relocate` 进入。实现位于：

- `src/modules/facility/public/facility-relocation.ts`
- `src/modules/inventory/application/inventory-relocation.service.ts`

## 拟记录的决策

保留现有 Facility 与 Inventory 职责分工，并收窄两者之间的 interface：

- `PreparedStorageRelocation` 改为显式定义，公开来源和目标的设施/拓扑 ID、路径、管理及准入工作区，根节点的 ID/资源 ID/名称，以及子树节点 ID 列表。
- Facility 在 `prepare()` 内生成治理投影，保留管理工作区在首位、其余准入工作区沿用查询顺序的去重规则。
- 准备结果提供 `fingerprint(contentVersions)`。Inventory 仍负责按原顺序生成占位 ID、孔位 ID、库存 ID、工作区 ID、库存版本及实物 revision 的数组；Facility 不解释其内容，只将它与内部设施确认事实组合。
- 准备结果提供绑定本次准备状态的 `apply()`。输入、完整设施/准入行、持锁标志和事务身份留在闭包内。调用方不再接触这些状态；执行时仍检查准备时持锁且当前事务 ID 一致。
- 独立的 `authorize()` 只完成来源和目标授权，返回 void，供幂等重放前的当前授权检查使用。它与 `prepare()` 复用内部授权实现。

Facility 继续负责结构合法性、双设施授权、拓扑锁、移动和治理事实。Inventory 继续负责库存影响集合、库存权限及版本、工作区流水、审计和业务幂等。

## 指纹与对外契约

本轮保留原 SHA-256 输入的完整内容和 JSON 属性顺序：`input`、完整来源 Facility、完整目标 Facility、来源/目标拓扑 revision、根节点 ID、完整准入行、Inventory 提供的版本数组。旧指纹原本只读取拓扑 revision，没有序列化完整拓扑行。

因此修改前生成的预览指纹可在新代码中继续执行，也不改变相同执行 body 的业务幂等请求指纹。本轮无需双算法过渡。已提交请求仍先命中幂等记录，再按当前授权返回原回执，不重新运行结构准备或预览指纹检查。

保留的行为包括：

- preview 完成设施、全部受影响工作区和目标准入检查后才返回影响信息；执行重新授权。
- 执行顺序仍为组织锁、当前设施授权、幂等 claim、新操作的结构准备及稳定顺序拓扑锁、指纹检查、结构及库存写入、流水、审计、幂等完成。
- 节点/实物/库存/占位身份、数量、状态、保管人和工作区归属规则不变；历史路径使用移动前后的真实快照。
- 未持锁或不同事务的准备结果不能移动；所有写入继续参加原有物理事务，重放不追加流水。
- 10,000 节点与 1,000 库存项限制、空容器拒绝及原有生命周期规则保持原样；普通空结构移动入口没有调整。
- HTTP 路由、contract schema、预览和执行响应、错误映射及前端恢复流程保持原样。

将完整 Facility/准入事实替换为 `id + revision` 属于后续独立决策。当前业务入口会推进相关版本，但原生 SQL/底层 Writer 并不统一保证 revision；本轮既不缩减旧覆盖，也不扩大原有覆盖保证。未来新增设施字段仍可能影响当前全行指纹，不能将本轮解释成已经消除这项行为依赖。

## 验证及边界

一次性差分检查使用修改前保存的两个源码文件与本轮构建结果，并通过实际 FacilityRelocation、InventoryRelocationService、OrganizationWriteKernel 和 IdempotencyKernel 执行，基础设施与权限依赖受控。28 项检查通过，包括：

- 跨设施、同拓扑、设施顶层目标和可选参数的预览逐字段相同，查询及授权顺序相同。
- 不推进 revision 的设施描述、更新时间、准入级别及准入创建时间变化，仍使旧预览失效；拓扑、库存和实物版本变化同样失效。
- 旧代码生成的预览在新代码执行后，回执、结构写入参数、库存更新、按工作区生成的流水及审计与旧代码一致。
- 设施/库存工作区失权、目标无准入、生命周期拒绝、空容器及两个规模限制与旧代码一致。
- 准备结果的字段范围、未持锁及不同/缺失事务拒绝、同拓扑去重锁及版本推进符合原约束。
- 重放不移动或增加流水；已完成后生命周期或版本变化不阻止合法重放；同键不同 body 仍冲突；审计失败不完成幂等记录。

后端完整构建、两处业务文件 ESLint、Prettier 及 diff 检查通过。Standards 与 Spec 两路独立复查均无发现。一次性源码基线、脚本和结果保存在忽略目录 `output/architecture-a04-2026-10-21/`，没有新增永久测试文件。

本轮未运行真实 PostgreSQL 或 HTTP 验收。上述受控检查不能证明真实数据库并发、锁等待或后置失败回滚，也不能替代真实提交后的持久幂等验收。原有事务、SQL 和调用顺序的保留由差分检查及代码复核支持。
