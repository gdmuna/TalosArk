# I09: reliable background work

Status: implemented with isolated PostgreSQL/Valkey verification. Deployment activation is explicit.

## Ownership

`core/task` owns durable submission, input validation, versioned handler discovery,
execution policy snapshots, database leases, outcomes and manual recovery.
`infra/queue/bullmq` owns Redis connections, dispatch/reconciliation and BullMQ workers.
`system/maintenance` contributes `file.cleanup@1` through the existing Extension Discovery.
The ordinary Prisma `Task` model is unchanged. Event Outbox/Inbox placeholders are not activated.

`BackgroundJob` is both the background work record and its pending-dispatch outbox.
It stores bounded JSON payloads (64 KiB), policy, attempts, generation and safe failure labels.
Redis receives only `{ id, generation }`, never payloads, credentials or signed URLs.
No owner identity is restored as authentication in the new per-execution ALS context.

## Submission and execution

```typescript
await database.transaction.run(async () => {
    // Update business facts here.
    await task.enqueue(fileCleanupTask, { limit: 50 });
});
```

Submission requires an active managed transaction. Handler metadata and payloads are validated.
The dispatcher polls committed records in bounded batches using `FOR UPDATE SKIP LOCKED`.
Database transactions finish before Redis I/O. Dispatch leases expire after process loss.
PENDING becomes QUEUED before Redis add, so an immediately running worker can claim it.
The stable Redis job ID combines the database ID and explicit retry generation.

Worker admission locks one database row, increments the persisted execution budget and leases
the attempt. Heartbeats renew while underlying work is settling, including cooperative cancellation.
No database transaction surrounds the handler's external I/O. Result writes are fenced by the
execution token. A crash after a database-only effect still requires an owner transaction/idempotency
protocol: infrastructure leases do not make arbitrary external effects exactly once.

`TaskFailure('retry', safeCode)` requests retry; `permanent` stops; `unknown` requires review.
Unclassified errors stop rather than being assumed safe to retry. BullMQ receives safe labels only.
Timeout/shutdown sends AbortSignal and retains the worker slot until work settles. Non-cooperative
work may exhaust process shutdown and require interruption; there is no promise of forceful JS cancellation.
Non-repeatable interrupted work enters NEEDS_REVIEW. Repeatable work may resume within its persisted
budget. Manual retry increments generation and resets only that generation's budget, preserving total attempts.

## Recovery and failures

The same bounded scan reconciles QUEUED/RUNNING records with Redis. Missing jobs are recreated
only after execution leases expire and only when repetition is allowed. Failed/completed Redis jobs
without a durable success do not turn into success; they become FAILED/NEEDS_REVIEW for inspection.
Handler/version absence becomes NEEDS_REVIEW. Completed database records reject stale deliveries.
Dispatch failures retry on a later bounded scan without spending execution attempts; dispatchAttempts
and failureCode remain inspectable. An outage does not silently discard a record.

Queue retries use BullMQ fixed/exponential backoff and jitter. The persisted budget is authoritative
when stalled delivery or Redis recovery would otherwise reset BullMQ counters. Failed jobs may be
observed during reconciliation after the next 30-second check window.

## Runtime and operations

After schema synchronization, set TASK_ENABLED=true. Default Web behavior starts the dispatcher and
two worker slots. TASK_WORKER_ENABLED=false leaves Web dispatch active but consumption to independent
workers. `pnpm worker:local` / `pnpm worker:prod` start the built `dist/src/worker.js`; build first.
Worker composition imports configuration, storage, file maintenance, database and logging, without HTTP,
SMTP or IAM startup. It requires TASK_ENABLED=true and consumes regardless of TASK_WORKER_ENABLED.
All instances use the same database and prefix; separate environments must use separate prefixes.

Build first (`pnpm build`); CLI executes the compiled script so Nest constructor metadata is retained.
Run trusted maintenance with an explicitly selected runtime env, for example:

```powershell
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task file-cleanup --limit 50
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task inspect <id>
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task failures --limit 50
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task retry <id> --note "operator: reason and outcome confirmation"
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task prune
pnpm dotenvx run -f secrets/env/.env.development.local -f secrets/env/.env.development -- pnpm task recover
```

Inspect excludes payloads and lease tokens. Retry is restricted to FAILED/NEEDS_REVIEW and unexpired
work; the operator must resolve uncertainty before re-running external effects. Prune removes one
bounded batch of old SUCCEEDED/EXPIRED rows only. There is no public maintenance endpoint or Bull Board.
CLI requires trusted host/database access, not a user-facing bypass around application authorization.

Redis AOF everysec and noeviction are explicit in dev/full Compose. AOF everysec is not zero-loss
durability; database reconciliation remains necessary. Shared KVS deployments must not enable an
eviction policy incompatible with queue data. There is no automatic cross-broker failover.
Shutdown drains HTTP, stops task acceptance/dispatch, aborts active handlers, waits within the task
budget, then destroys other Nest providers, disconnects database and flushes logs. A failed task stop
fails shutdown rather than claiming that resources closed cleanly.

## First handler and validation

File cleanup remains an explicit bounded maintenance command, not a periodic scheduler. It uses
FileKernel.cleanup's public protocol and abort signal; partial failures request retry and are never
reported as successful. Its aggregate counts are persisted as the result. A successful empty batch
does not establish acceptance for populated object storage or all historical upload recovery scenarios.

Verified locally: Prisma generate and schema push to new isolated `talosark_i09_validation` only;
backend typecheck/build; Worker context start/close; rollback leaves no job; empty file cleanup through
real PostgreSQL/Valkey completes; concurrent execution increments once; non-repeatable interruption
requires review; manual retry preserves cumulative attempts; execution budget exhaustion stops.
Fault injection after Redis add before database release keeps one queue entry; removing that queue
entry and reconciling recreates and executes it. A validation handler requested two retries through
real BullMQ backoff and succeeded on attempt three.
No maintained test scripts were added. Existing dev/prod schemas, SMTP deliveries and user credentials
were untouched. Populated object-store cleanup, actual process termination during external I/O,
Redis server restart and deployment-specific recovery have not been verified.
The temporary validation database and the four validation-only Redis namespaces were removed
after verification. CLI failure listing was executed against the isolated database using compiled
Nest providers; direct tsx execution is intentionally avoided because it omits DI constructor metadata.

Deferred: RocketMQ/multi-driver routing, general event bus, workflows, recurring schedules, authenticated
operations UI and credential-bearing mail payload design. Existing invitation/recovery mail remains best-effort.
