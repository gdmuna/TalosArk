## 1. 问题与现有证据

批次保存与页面重新读取是两个不同阶段。后端已返回保存成功，而随后的读取失败时，前端必须保留“已保存”的事实，重试只读取，不能重新提交同一次业务写入。

现有代码已有这类保护。本候选针对共同规则分散带来的理解与修改成本，不将其表述为已经复现的重复写入故障。

## 2. 落地决策与修改范围

采用按页面实例创建的 [useMaterialBatchRecovery](../../src/module/material/model/useMaterialBatchRecovery.ts)，由现有 Material module 的 `model/` 维护共同规则。

1. 列表和详情传入当前材料 ID、原有 reader 的 `reload`；详情额外传入当前批次 ID。model 返回 `syncPending`、`synchronize`、`afterCommit` 和 `archive`，通过 Material 现有公开入口供详情消费，模块内部使用相对路径。
2. model 集中待同步状态、确认保存后的只读恢复、归档/恢复写入与后续同步的先后顺序，以及上下文和销毁代次检查。迟到的写入或读取不能更新当前恢复状态；不属于当前组织、工作区、材料或批次的确认结果不启动恢复。
3. 页面仍负责管理权限、按钮禁用、列表分页、选择和自己的读取范围。`archive` 的页面入口只做已有 UI 条件检查，写入后的恢复协议不再由两个页面拼接。
4. 编辑器继续持有 `committed` 回执，锁定已保存表单，并保留原有 `saved` 事件、`onCommitted` 回调和弹层 session。它通过同一回调进入页面的共同恢复规则；草稿与回执不升为全局共享状态。
5. `MaterialBatchEditor.vue`、`store.ts`、`useMaterialRead.ts` 均未修改。继续使用现有 MaterialDataSource seam、HTTP adapter、revision 自动刷新与进行中读取合并；没有增加转发 adapter 或通用写入恢复框架。

收益检查：列表与详情各自的 `generation`、`syncPending` 写入、`synchronize`、`afterCommit` 以及归档后的恢复顺序已收回一处。未来修改共同协议只需维护该 model；两处页面只保留各自的显示与读取选择。model 包含实际状态转移和过期结果保护，不是转发 source 的间接层。

## 4. 必须保留的行为与对外契约

- 已确认保存后的重试只读取；刷新失败不能抹去保存成功的事实。
- 归档、恢复与更新继续使用原有 `expectedRevision`；冲突或结果待核对时保留现有核对路径，新增时保留按原批号查找的规则。
- 已保存的表单不能因刷新失败再次提交；保留现有提示、允许关闭的时机与同步成功后的收尾行为。
- 保留 `MaterialBatchEditor` 的 `open`、`batch`、`materialId`、可选 `onCommitted` 和 `saved` 契约；`saved` 仍表示保存已确认，不推迟到读取成功之后。
- 组织、工作区、材料、批次或弹层会话改变，以及调用方销毁后，旧结果不能覆盖新数据、清理新错误、解除新状态的锁定或关闭新弹层。
- 保留 `revision` 自动刷新与显式 `reload` 复用进行中读取的行为，不能因收拢逻辑额外制造重复请求。
- 页面自己的列表分页、筛选、详情读取和权限读取不因共用恢复规则而合并或扩大；HTTP 路径、公开 wire schema 与后端语义不变。

## 5. 后续验证方法与完成标准

以下行为通过 OS 临时目录中的一次性 Vitest 验收脚本验证：挂载真实列表、详情和编辑器，替换现有 MaterialDataSource 的外部 I/O。没有向仓库新增或维护测试脚本。

1. 从列表、详情及新增/编辑入口制造“写成功 → 读失败 → 多次重新加载 → 读成功”。同一次操作的写请求始终只有一次，恢复阶段只发读请求，成功后按原有交互收尾。
2. 在旧写入或读取未完成时切换工作区、材料、批次，或关闭后重开弹层；随后完成旧请求。新上下文的数据、错误、忙碌状态与草稿不受影响。
3. 同时触发 `revision` 自动刷新与显式恢复，确认继续复用进行中的读取；列表与详情仍只读取其原有范围。
4. 作为行为不变的回归检查，回查更新冲突与新增结果待核对路径，确认 `expectedRevision`、原批号查找及草稿保护未被破坏；不以检查这些路径为由扩大重构范围。
5. 对照修改前后调用方：两份恢复协议应变为一处维护；如果只增加了一层转发，或调用方仍须掌握同样多的状态与顺序，视为未达到收益目标。
