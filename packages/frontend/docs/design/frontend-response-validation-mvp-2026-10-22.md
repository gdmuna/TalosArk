# MVP 前端响应校验与静默失败策略

日期：2026-10-22。状态：用户已确定策略并授权统一实施；已完成前端反馈调整。不更新 CONTEXT.md、ADR 或 Site。

## 用户确定的方向

公开 schema 来自 contract 包，作为共享公开数据结构及 TypeScript 类型的事实依据。MVP 阶段，前端可以进行运行时响应格式校验，也可以不做；请求与响应的身份、范围和内部关联检查也不要求全面补齐。是否校验、覆盖哪些条件，应在相关 module 的设计记录或 interface 说明中明确。

如果进行了这些校验，失败时静默失败。后续开发前端开发者工具 module 时，再考虑此类问题的诊断、展示和处理方式；当前不为此新增开发者工具、错误收集框架或复杂恢复流程。

以上策略由用户本次明确给出，优先于此前设计记录中要求向用户展示此类校验错误的约定。随后用户授权“统一修改其余页面”，实施范围和验证边界如下。

## 静默失败的处理口径

这里将“静默失败”落实为以下最小口径：

- 不因响应格式或关联校验失败向用户展示 toast、弹窗、协议错误文案或专门的错误面板。
- 正常结束本次加载或提交的等待状态；失败响应不作为成功结果发布，不用伪造的空列表、零统计或成功状态替代它。
- 不因该失败新增自动重试或重放业务写入。内部仍可通过原有失败返回值或错误机制完成状态收尾，无需将所有失败转成正常返回值。
- 已有数据和草稿继续沿用各 owner 的清理/保留规则：原先 protocol 清空的数据仍清空，原先同范围保留的数据不统一改写；首次无数据继续使用既有布局，不伪造成功快照。启动和 OIDC 回调按实际 pending 显示加载，校验失败后既不进入 ready，也不永久显示加载。

静默范围是前端发现的成功响应格式、身份、范围或关联不符。服务端明确返回的业务拒绝、HTTP 401/403、登录状态变化、网络失败等继续沿用各自处理，不因为这条策略一并静默。

## 实施范围与校验选择

| 位置 | 保留的校验选择 | 失败处理 |
| --- | --- | --- |
| `src/platform/http/client.ts` 的 decode | 继续执行现有成功 JSON envelope/payload schema 解析，保留声明的空 204 语义；未增加开关 | 保留 protocol 失败，不返回伪成功。消费端通过现有错误类别静默展示。 |
| 材料、库存、审批、设施和团队 | 保留现有身份、范围、分页和关联检查，不统一补齐缺失检查 | 错误 mapper 对响应校验失败返回空展示文案；reader/command 仍记录实际失败并结束 loading/busy。 |
| 审计、组织、资源授权、集成、通知策略、部署信息和工作台概览 | 保留现有公开 schema 或来源检查；集成 reader 中的响应 Zod 失败同样处理 | 不显示协议错误、兜底失败面板或错误原因推导出的工作区选择提示。权限、网络和业务失败继续显示。 |
| 账户、工作区和保留的工作台动作 | 保留原有来源及检查；工作区身份失配和账户身份失配使用 protocol 类别，账户既有比较在发布快照前执行 | 字符串结果中的成功仍为 `''`，静默失败返回 `null`，UI 严格判断成功，避免把空错误文案当作已保存。 |
| 登录、恢复、刷新、退出、OIDC 回调及邀请页 | 保留凭据格式/有效期、会话身份及真实跨标签变更处理 | 成功响应校验失败不冒充登录失效；内部 error 状态可以无展示文案。启动停在失败阶段；回调结束 spinner；退出仍保留未确认事实及禁止自动恢复的标记。 |
| 附件和文件传输 | 保留现有分片计划、完成清单、进度、签名方法/URL 和 ETag 检查 | 原先直接抛普通 Error 的响应关联检查改为明确的响应校验错误；文件传输使用本模块的 FileTransferResponseError，由附件 owner 静默处理，不引入 file-transfer 对 http 的依赖。文件选择、本地格式/大小、网络及存储业务失败继续反馈。 |

本条策略只处理前端消费后端响应时的可选检查与反馈，不修改后端输入校验、授权、响应投影或 contract 的公开数据结构。

### 展示与操作状态分开

- 设施、团队、管理详情、账户、工作区及保留的工作台动作使用独立的待同步状态阻止重复提交，不再把 `syncError` 是否有字当作同步成功或失败的依据。
- 材料/库存/审批 reader 保留实际 failure，供写后同步提示区分响应校验失败和普通失败。需要聚合多个 reader 时，普通失败继续保留反馈，不用其中一个 protocol 失败掩盖其他错误。
- 库存入库、库存动作、搬迁及审批的原恢复记录增加可选的 `responseValidationFailed` 布尔标记。它只控制派生提示，随原记录持久化；原请求、幂等键、未知结果和已有合法回执不被丢弃。旧记录仍可读取。重新核对成功会清标记，其他失败恢复对应反馈。
- 退出的原协调标记使用可选 `silent` 区分静默的未确认结果；`confirmed` 仍为 false，跨刷新/跨标签不重新生成该错误提示，也不把退出伪装为已确认成功。
- 不新增后台重试、写入重放、诊断收集或开发者工具。恢复仍由原有入口执行；已确认写入的恢复仍只重读。
- 对原本通过同步错误面板提供重读入口的页面，静默失败后保留同一回调的中性“重新加载”按钮，不展示警告框或错误说明。启动和工作区上下文核对同样可以手动重读，不自动进入下一阶段。

## 后续工作采用的记录方式

修改相关 module 时，直接在它的 interface 说明或现有设计记录中注明：是否执行运行时校验、执行格式还是关联检查、失败如何静默结束。可以继续采用现有 schema 解析，不要求为了统一形式增加配置、抽象层或迁移全项目。

这一记录方式用于说明实际选择，不把“尚未增加某项前端校验”自动列为 bug。对于既有代码，也不能在没有单独范围和收益依据时批量增删检查。

B04 保持 Speculative，当前不实施新增身份比较。其历史实验仅说明假设错响应的后果；若以后选择增加检查，失败处理遵循本记录，诊断能力留待前端开发者工具 module 再评估。
