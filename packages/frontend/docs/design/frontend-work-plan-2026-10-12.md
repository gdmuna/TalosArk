## 工作包

### F01：写入结果与快照同步分离

状态：已完成（2026-10-12）。保留原操作返回类型，增加 `syncError` 与只读 `retrySync`；暂缓旧快照上的 owner 写入，保留浏览、导航与其他 owner 操作。

来源：候选 01，Strong。第一优先级，影响后续远程写入的结果可信度。

- 在 account、workspace、workbench 各自业务 module 内区分写入提交与后续快照同步。
- 写入已成功时保留结果和新记录标识；同步失败不得被报告为该写入没有成功。
- 明确同步失败时的用户反馈和恢复归属；恢复只重载，不隐式重做写入。
- 保留现有 busy 与操作协调；不新增跨业务万能 store，不借此改变后端幂等性契约。

验收：分别观察写入失败、写入成功且重载成功、写入成功但重载失败。
最后一种仍保留提交结果，并且恢复不会执行第二次写入；现有成功流程和选择上下文不回归。

先确认：公共操作结果是否改变、部分成功如何表达、调用方如何处理同步失败。
这些语义不以现有返回字符串/null 的形状为唯一约束；如果需要改变公共 interface，先列消费方与影响，再确认实施。

### F02：工作台时间状态的失效与投影

- 明确后台暂停、恢复可见性和释放行为；不使用每行 timer 或持续 rAF。

### F13：真实会话刷新与退出联调

来源：报告保留的 auth seam，加上审查后已经实现的后端契约；不是新的业务扩张。
无需等待 F06-F11 全部完成，但需先确认退出/失败策略。

- 通过 module/auth/data 的 HTTP adapter 接通共享 refresh schema，并由现有 session runtime 与 barrier 负责凭据推进。
- refresh 不依赖有效 AT，不进入自身认证等待；禁用对同一 RT 的盲目网络重试，保留 single-flight、取消、迟到结果隔离。
- 当前 HTTP decoder 要求成功 JSON 包络；为已确认的 logout 204 无响应体提供准确支持，不对任意非法响应放宽校验。
- 服务端会话撤销和本地清理分别处理；保持登录 revision，晚到回调/刷新不能复活已清理的会话。
- main.ts 仍是装配和释放 owner；platform/http 不导入业务 module。
- 同步前端 CONTEXT 的后端状态、已接能力和未接能力，不以接通刷新冒充完整用户资料/工作区业务联调。

验收：并发请求只发起一次刷新；有效 RT 在 AT 过期时可推进；明确失效 RT 得到确定失败；204 退出不被判为协议错误。
取消、退出和迟到响应的组合不复活旧会话；网络中断不回放已可能消费的 RT；本地清理不被宣传为已确认服务器撤销。
隔离联调与真实身份提供商端到端验收分别记录，未做的部分保持明确留白。

先确认：退出网络失败时是否仍清理本地会话、如何提示未确认撤销，以及刷新提交结果不明时如何结束当前认证状态。
凭据持久化、跨标签同步、第一方登录、全部设备退出与提供商单点退出不属于这个工作包，另有需求再评估。
