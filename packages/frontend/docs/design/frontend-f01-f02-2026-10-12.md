# F01 / F02 实施记录

日期：2026-10-12。范围仅为 [前端工作计划](./frontend-work-plan-2026-10-12.md) 中的 F01、F02。

## F01：提交与同步

用户确认采用兼容方案：保留原来的错误字符串与巡检 ID/null 返回类型。
操作函数只报告写入失败，不因提交后的快照读取失败而丢失成功结果。

| 状态 | 返回与快照 | 后续操作 |
| --- | --- | --- |
| 写入失败 | 返回原错误；不加载快照 | 保留原有错误处理，可修正后再提交 |
| 写入成功，同步成功 | 返回成功；应用新快照 | 正常操作 |
| 写入成功，同步失败 | 仍返回成功或新 ID；保留旧快照，设置 `syncError` | 浏览/导航可用；暂缓该 owner 的写入；显式只读恢复 |

Account、Workspace、Workbench 各自拥有同步状态与私有 `synchronize`，没有新建跨业务万能 store。
新增 `retrySync()` 仅在 `syncError` 存在时加载数据，沿用 `busy` 串行协调。
它不是普通刷新 API，不会执行原写入，失败时保留提示、成功后恢复写入。

巡检创建返回的 ID 不因同步失败变成 null。工作区创建/加入返回的目标 ID 保留至
恢复同步；用户显式选择已知工作区时，新选择优先。目标工作区未出现在返回快照时，
同步继续视为未完成，不静默丢弃该目标。

`component/data-sync` 只负责提示呈现和 retry 事件。
`layout/shell/DataSyncStatus` 组合三个 owner，保证切换页面后仍有恢复入口。
三个工作台 Inspector 与工作区表单在自己的模态上下文内也提供恢复。
工作区表单在部分成功后留作确认态，禁止重提，恢复成功后关闭；也可主动关闭。
批量操作禁用原因优先说明需要重新同步，避免误报记录状态不合法。

### SaaS 参考的边界

腾讯云 [StopInstances 文档](https://cloud.tencent.com.cn/document/product/213/15743)
区分成功受理的请求与后续实例状态查询；[Go SDK 文档](https://cloud.tencent.com/document/sdk/Go)
限制非幂等请求的自动网络重试。
这些公开资料支持“提交与读取分开、恢复不重放写入”的设计，
但不证明其控制台采用整模块禁用策略，也没有实测腾讯云控制台。
本项目因当前 source 加载整个 owner 的快照，选择暂缓该 owner 写入的保守策略。
后续有细粒度服务端版本与幂等契约时，可以另行评估对象级限制。

当前依旧使用原 mock adapter，没有新增后端端点、自动写入重试、乐观业务数据或幂等契约。
网络错误下服务端是否已经提交的不确定结果，不在本轮假定为成功。

## F02：共享响应式时间

按用户指出的既有能力，采用 VueUse `useTimestamp`，而非自建业务时间边界调度器。
使用当前已安装版本的实现，[官方说明](https://vueuse.org/core/usetimestamp/) 为参考。

- 私有 `model/clock.ts` 在工作台 store scope 内创建一个每秒时钟，显式避免默认 rAF。
- 隐藏页面时暂停；恢复可见性或收到 focus 时立即读取当前时间校准。
- 定时器与监听随 store scope 释放；应用卸载和入口 HMR 释放 Pinia。
- store 对外提供 `overdue`、`displayStatus`、`today`、`displayTime` 投影。
- 概览、待办统计、表格筛选与状态、Inspector 使用同一来源。
- 日期或逾期分类改变时更新 `currentTasks` 数组身份，失效 TanStack 缓存；普通时钟 tick 不重建表格数据。

前台正常调度下更新时间约一秒，不承诺系统卡顿下的严格实时性。
保留 `status === 待处理 && dueAt < now` 的严格判定以及原 dayjs 本地自然日语义。
原公开任务 helper 保留单参数，避免 `.filter(isTaskOverdue)` 将数组索引误当当前时间。
内部使用显式时间的 `isTaskOverdueAt`；shared 日期 helper 增加可选 now 参数，无业务日期格式化继续留在 shared。
