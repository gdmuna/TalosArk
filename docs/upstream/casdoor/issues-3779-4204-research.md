# Casdoor issues #3779 and #4204: upstream research

Checked on 2026-09-25. This is a research note, not an issue draft or a claim that either feature is implemented. Sources are Casdoor's own issue/PR records and contributor documentation.

## What the two issues actually say

| Record | Requested behavior | Observed maintainer action | Current result |
| --- | --- | --- | --- |
| [#3779](https://github.com/casdoor/casdoor/issues/3779) | When a third-party provider omits a field marked required in an application's Signup Items Table (the example is QQ without email), ask for that field before account creation. | [hsluoyz replied](https://github.com/casdoor/casdoor/issues/3779#issuecomment-2903900389) that `required` only controls the normal registration form and pointed to the application's Providers-table Prompt page. The same reply says Prompted was then supported for third-party login providers. He [closed the issue at the same time](https://api.github.com/repos/casdoor/casdoor/issues/3779/timeline); the issue is labeled `question`, and no PR is linked on the issue page. | Closed, GitHub `state_reason=completed`; no evidence in that issue of a merged missing-field implementation. |
| [#4204](https://github.com/casdoor/casdoor/issues/4204) | After SSO auto-registration, collect necessary registration items (example: phone when the upstream identity supplies only email) *before the authorization redirect*. | Maintainer labeled it `enhancement` and assigned Copilot; the [issue timeline](https://api.github.com/repos/casdoor/casdoor/issues/4204/timeline) cross-references two implementation PRs. The [issue comments endpoint](https://api.github.com/repos/casdoor/casdoor/issues/4204/comments) currently returns no comments. | Still open; both linked PRs are closed without merge. |

These are materially the same missing-field scenario, but their timing requirements differ: #3779 asks for completion **before account creation**, whereas #4204 expressly asks for it **before the authorization redirect**. It is reasonable to infer that the earlier Prompt answer did not settle the requested behavior, but **there is no maintainer statement explaining a change of policy**. Do not present the differing actions as a confirmed policy reversal.

The word `Prompted` is overloaded in this discussion. The #3779 maintainer comment points specifically to the application's **Providers** table and says it then applied to third-party login providers. The current [Sign-up items table documentation](https://casdoor.ai/docs/application/signup-items-table/) separately documents a `Prompted` column for signup fields. The existence of that column does not, by itself, prove that the SSO auto-registration path enforces it before user creation or authorization redirect. The later PRs attempted to bridge precisely this gap.

## The two #4204 implementation attempts

1. [PR #4307](https://github.com/casdoor/casdoor/pull/4307) was opened on 2025-10-24 by Copilot after assignment from the issue. Its proposed changes included a backend check for missing required Signup Items, frontend prompt rendering, and an OAuth-login redirect to that prompt. **Its own example creates the Casdoor user before collecting the missing phone number**, so it does not meet #3779's pre-creation requirement. [hsluoyz asked the issue author to test it](https://github.com/casdoor/casdoor/pull/4307#issuecomment-3444256311). He closed the PR unmerged on 2026-01-30. When asked why, [he pointed to a new PR](https://github.com/casdoor/casdoor/pull/4307#issuecomment-3854169039).
2. [PR #4985](https://github.com/casdoor/casdoor/pull/4985) was opened on 2026-02-05. It proposed expanding PromptPage to collect fields explicitly configured as both `required` and `prompted`, plus documentation. [hsluoyz again asked the issue author to test it](https://github.com/casdoor/casdoor/pull/4985#issuecomment-3854169980). It was closed unmerged on 2026-04-18. Its visible comments and timeline give **no stated reason** for that closure; do not infer rejection or acceptance of the idea.

The two PR descriptions differ in policy: #4307 would detect missing *required* fields automatically, while #4985 would require explicit `prompted: true` as well. This is an unresolved design choice, not current Casdoor behavior. Neither closed PR establishes shipping support. [#4307 PR](https://github.com/casdoor/casdoor/pull/4307), [#4985 PR](https://github.com/casdoor/casdoor/pull/4985).

## Casdoor community norms relevant to new issues

- [Official contributor guide](https://casdoor.ai/docs/contributing/) asks reporters to start with GitHub Discussions or Discord for feature ideas and to **describe an issue in English**. The [repository README](https://github.com/casdoor/casdoor#contributing) recommends opening an issue before a change larger than a small fix so the approach can be agreed with maintainers.
- The current [`.github` directory listing](https://api.github.com/repos/casdoor/casdoor/contents/.github) contains no `ISSUE_TEMPLATE` directory, so no repository-specific issue form was found in that location. A concise free-form Markdown issue with problem, present behavior, desired behavior, scope, compatibility, and open questions is appropriate.
- The [contributor guide's PR rules](https://casdoor.ai/docs/contributing/) call for one logical change per PR and lowercase Conventional Commit **PR** titles. These are PR requirements, not a requirement for issue titles.
- [Casdoor's security policy](https://github.com/casdoor/casdoor/blob/master/SECURITY.md) says not to report vulnerabilities directly in public GitHub issues; use `admin@casdoor.org`. A general account-linking design proposal can be public, but a demonstrated account-takeover path should go through the private channel and should not include exploit details in a public draft.

## Implications for the two planned proposals

- **Profile completion:** Since [#4204 remains open](https://github.com/casdoor/casdoor/issues/4204) and already has two closed, unmerged PRs, consider adding a scoped comment there or explicitly linking it in a new design issue rather than presenting the request as new. Ask maintainers whether they want a narrowly generic, opt-in per-application policy and whether `required` alone or `required + prompted` should trigger it. Business-specific downstream profile rules are a separate concern.
- **Account ownership proof before linking a new external identity:** Keep this separate from the missing-profile request. Clarify that an attribute match finds a *candidate* Casdoor account; it is not proof that the external identity owner controls that account. A proposal should ask for an explicit re-authentication/ownership-proof gate before binding. If the current implementation can demonstrably enable takeover, follow the private security reporting route first.
