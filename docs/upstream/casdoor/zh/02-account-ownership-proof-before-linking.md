# 草案：在关联外部身份之前先验证账户归属权

> 本文为英文原文的简体中文译本，原文见 [../02-account-ownership-proof-before-linking.md](../02-account-ownership-proof-before-linking.md)。

**状态：** 仅为草案，尚未提交至 Casdoor。
**安全处理方式：** 若调查确认可利用属性匹配访问他人的 Casdoor 账户，请先遵循 [Casdoor 的私下安全报告政策](https://github.com/casdoor/casdoor/blob/master/SECURITY.md)并联系 `admin@casdoor.org`，然后再对外发布 issue。不要在公开 issue 中写入复现细节或利用路径。下文的提案是一份可公开发布的功能性讨论，应在上述分流处置**之后**再使用。
**建议标题：** `[Feature] Verify account ownership before linking an external identity`

---

## 概要

当一个新完成认证的外部身份通过邮箱、手机号或用户名等属性匹配到某个既有 Casdoor 用户时，应将该用户视为**候选账户**，而不是一个已经验证过的账户绑定。应提供一次互动，让用户先证明其对该既有 Casdoor 账户的控制权，然后才把新的外部身份关联到该账户上。

## 动机

Casdoor 文档所述的提供方绑定规则（Binding Rule）会按顺序检查 `Email`、`Phone` 和 `Name`，并关联第一个匹配到的用户。属性匹配有助于发现候选账户，但它与"证明通过新提供方完成认证的那个人确实控制着该既有账户"是两种不同的操作。这两种操作应具有各自独立的状态与结果。

本诉求针对的是 **Casdoor 账户的归属权与外部身份关联**，而不是下游应用业务资料的完整性。

## 建议方案

- 当外部提供方身份**已关联**到某个 Casdoor 账户时，普通登录流程保持不变。
- 当外部身份是新的、且属性匹配找到了一个既有 Casdoor 账户时，暂停关联步骤。要求用户先以该 Casdoor 账户已有的某种方式完成认证，或使用该账户一个已建立且足够新的 Casdoor 会话，然后才确认这条新关联。
- 若不存在候选账户，则沿用该应用现有的注册策略。若匹配结果存在歧义，或用户无法证明归属权，则不得自动关联；应提供相应的找回或支持途径。
- 不得把"在新收到的外部资料中持有某个属性"当作对该既有 Casdoor 账户归属权的证明。
- 证明成功之后，只创建一次外部身份关联，确保它不与其他账户冲突，并恢复原来的授权事务。若证明被取消或超时，则不得创建该关联，也不得为该账户签发成功的授权结果。
- 对 Casdoor 托管的 UI 与任何 API 驱动的登录路径，使用同一套服务端规则。专有的互动 API 可以暴露一个待处理的下一步动作，但标准 OAuth/OIDC 或 SAML 端点只应在互动进入终态时才输出其正常的成功或错误响应。

## 验收标准

- [ ] 此前已关联的外部身份可以直接登录，无需在每次登录时重复进行账户归属权证明。
- [ ] 仅通过属性匹配到既有账户的新外部身份，在证明对该账户的控制权之前不会被关联。
- [ ] 无匹配、多重匹配、证明失败、用户取消、超时以及并发关联尝试，均有明确且安全的处理结果。
- [ ] 待处理的证明无法通过其他登录 API、也无法经由其他路径申请 OAuth/OIDC 授权码、令牌或 SAML 断言来绕过。
- [ ] 既有的关联仍然可用；对现有自动绑定行为的任何改动，都配有文档化的迁移与兼容策略。

## 留给维护者的问题

1. 哪些既有的 Casdoor 认证方式应被视为足以支撑一次新关联的证明？既有会话是否应要求近期重新认证？
2. 基于属性的绑定规则应继续用于发现候选账户、并在关联前要求证明，还是应由管理员为某些提供方显式选择一种受信任的自动关联策略？
3. 对于使用 Casdoor API 或 SDK、而非 Casdoor 托管登录 UI 的应用，待处理的互动应如何恢复？
4. 维护者是否更希望先私下完成安全审查，然后再在 GitHub issue 中讨论公开的功能与迁移设计？

## 已考虑过的替代方案

- **在首次属性匹配时就自动关联：** 保留了当前行为，但把账户发现与归属权证明混为一谈。
- **始终创建独立的 Casdoor 账户：** 避免了自动关联，但会产生重复账户，并让正当用户缺少安全连接其身份的途径。
- **由每个下游应用各自完成关联：** 重复实现 IAM 账户关联规则，且无法一致地保护 Casdoor 自身的用户目录。
