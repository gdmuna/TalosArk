# P12 固定审批交付与验收

日期：2026-10-20。结论：本地真实 HTTP、PostgreSQL 和 Web 定向验收通过。后端与前端均在本线程完成；这不是生产部署、Tauri 或高负载验收。

业务依据为 [P12 对齐记录](mvp-p12-alignment-2026-10-20.md)，代码边界见[后端实施方案](../../packages/backend/docs/design/mvp-p12-plan-2026-10-20.md)与[前端接入记录](../../packages/frontend/docs/design/mvp-p12-2026-10-20.md)。

## 实际交付

用户可以从库存单件菜单、多选菜单或工作台发起消耗、转移申请。一单一种动作，可以包含多件实物，指定一名合资格的非本人审批人。审批人必须一次明确全部明细的批准或拒绝结论，可以部分批准；申请人再逐明细执行。批准不预留、不扣量、不移动位置，也不授予通用直接执行权限。

待审批整单可撤回；重新申请创建关联新单。获批未执行明细可由申请人放弃，或由当前合资格的指定审批人、独立撤销授权者撤销。已执行事实不回滚。每条明细分别显示决定、执行状态、当前位置/治理绑定或临时阻塞原因，不把“批准”显示成“已执行”。

工作台的“我的待办”接入待执行与我的申请，“待审批”接入指定审批人队列，概览接真实审批摘要和最近待审批。待审批按单据计数，待执行按未终结获批明细计数。普通任务和异常来源仍保持其未交付边界，没有用 mock 或假零填补。

## 验证环境与数据

仅操作已授权的 `test.local` 数据库 `talos-ark_backend_test`。先核对旧审批表无记录、旧整单执行关联无记录，再对相关表加锁复核，以同一事务应用本次审批模型变更和原生 CHECK；没有操作 dev/prod，也没有清空其他表。测试新增独立组织、工作区、合成成员和 108 件合成实物。

真实服务为 `http://localhost:3112/api/v1`，Web 为 `http://localhost:4462/`。Node Playwright 使用本机 Edge 内核、真实账密登录、Cookie 恢复和 HTTP 业务接口。没有向真实 SMTP 发信。测试运行时的独立 KVS 库、合成 SMTP/存储地址、限流放宽和两个本地 Origin 只存在于忽略的临时工具，不修改部署 env 默认值。

## HTTP 与数据库结果

| 场景 | 结果 |
| --- | --- |
| 101 条明细跨展示分页；少行、重复行、外单行、自审等非法输入 | 整单拒绝非法决定；完整部分审批成功，库存不变 |
| 只有申请权、没有通用直接动作权的申请人执行 | 按获批内容成功；丧失当前申请资格后新执行被拒绝 |
| 相同幂等键重放、不同键重复执行同一明细 | 恢复原回执；同一明细至多一笔真实流水 |
| 库存不足后恢复余量；审批人后来失去审批资格 | 阻塞时明细保留待执行；恢复后可执行；合法批准不追溯失效 |
| 实物离开原位置后返回；目标容器改变治理设施后返回 | 绑定不匹配拒绝；恢复原 POSITION/治理设施身份后可重试 |
| 执行与撤销竞争、整单撤回与完整审批竞争 | 终局互斥，没有同时撤回又决定、同时撤销又执行 |
| 故意令执行末段审批审计写入失败 | 库存、占位、明细状态、流水、幂等回执全部回滚；解除故障后原请求成功 |
| 多条明细共用目标位置 | 允许提出意图；实际占用只阻止当前明细，不代替预留或连带撤销其他明细 |
| 过期、来源容器停用、目标已占用 | 沿用 P11/设施规则阻止新执行，不自动撤销批准 |
| 非参与者查询、成员离开、库存/设施读取权变化 | 独立查询权不能绕过资源投影；旧快照不补回隐藏字段；离开成员不能读旧单 |
| 候选人、关联重申请、处理历史、默认角色显式初始化 | 当前资格检查、历史关联和审计正确；初始化重复调用无额外变更 |

两批共 15 组真实 HTTP/数据库检查通过。最终重新构建并重启后，又验证了提交回放、当前姓名/处理记录、批准不扣量、窄库存事实接口、单次执行与回执恢复。

## Web 结果

| 场景 | 结果 |
| --- | --- |
| 两个真实合成账户：多件表单提交、指定审批人、一次逐项部分批准 | 完成；未明确全部结论前无法提交审批，批准前后库存不变 |

## 接入与部署注意

新增公开契约 `@talos-ark/contracts/approval`。查询/命令位于组织及工作区作用域的 `/approval` 下。合资格审批人查询采用 `POST approver/query`，避免多件选择塞入 URL。独立查询权限正式命名为 `approval.read.all`，其余为 `approval.consume.apply/review`、`approval.transfer.apply/review` 和 `approval.revoke`。

新组织的默认工作区管理角色包含这些定义。旧组织不会在启动时静默增权；所有者可显式调用 `POST /organization/:organizationId/approval/initialize` 补齐默认角色，或使用团队管理给自定义角色授予所需权限。普通申请人不应因此获得通用库存直接动作权。

其他环境升级前应核对审批旧结构和数据，并先同步模型、再应用 `db:apply-approval-ddl`。本轮只验证空旧审批表的 test 库，不提供含历史审批记录的自动迁移承诺。已有 identity/inventory/storage DDL 的部署要求不被本轮替代。

## 边界与遗留

没有自动到期、库存预约、通用工作流、服务端草稿、整件借出、普通归还、跨单批量审批或多明细一键执行。跨单/执行批处理留 P13，独立通知、未读计数、邮件和推送留 P16。审批件数不按表格 100 条分页静默截断，但仍受 HTTP 请求体和真实服务器容量约束。当前 Fastify 默认限制为 1,048,576 字节；真实超限请求验证返回 413 / `REQUEST_PAYLOAD_TOO_LARGE`，整单失败，不拆单或截断。

生产打包仍有既有大 chunk 提示；运行时观察到 pg 的同一 client 并发 query 弃用告警，本轮没有扩展为事务基础设施整改。它们不是已通过的生产性能或未来 pg 版本兼容承诺。Tauri、部署环境和高并发仍单列。

临时验证脚本、JSON 与截图位于忽略的 `output/p12-2026-10-20/`；它们不是新增的长期测试套件，也不包含在应提交的代码清单内。并行线程的管理详情、导航、分页校验等变更未由本轮回退或归入 P12。
