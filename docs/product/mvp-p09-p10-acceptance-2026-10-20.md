## 发现并修复的问题

前端入库适配器要求回执 nodeId 必须等于提交孔位，但公开 OperationReceiptSchema 允许该字段为 null，后端入库回执也确实返回 null。
因此第一笔真实入库已提交，前端却将结果当成协议错误，显示“响应信息不一致”并锁定为未确认请求。

修复位于 `packages/frontend/src/module/inventory/data/api.ts`：允许空 nodeId，保留 kind、库存 ID、实例 ID 校验，并继续拒绝不匹配的非空 nodeId。
没有改变库存写入、公开 schema 或后端回执语义。

真实页面的后续入库/原键恢复已通过；另用当前源码适配器验证了空值允许、匹配值允许、错误非空值拒绝、缺库存身份拒绝四个分支。

## P10 结果

| 场景 | 实际结果 |
| --- | --- |
| 单次签名 PUT | 真正写入独立 RustFS，随后由后端读取和校验 |
| 开始/完成/绑定重放 | 分别复用同一会话、资产和引用，没有重复有效绑定 |
| 下载 | 真正使用签名 GET，下载内容 SHA-256 与原字节一致，响应使用 attachment disposition |
| 双分片上传 | 8,454,144 字节、2 个分片；实际 ETag、分片大小、进度、合并及完整下载哈希均核对 |
| 完整哈希错误 | MATERIAL_ATTACHMENT_INTEGRITY_MISMATCH，不发布 assetId |
| 取消分片上传 | 实际取消，后续签名拒绝；失败完整性校验的会话也可取消 |
| 跨材料会话访问 | MATERIAL_ATTACHMENT_UNAVAILABLE，不能复用另一材料的会话 |
| Web 文件闭环 | 选择文件、哈希、上传、绑定、列表、浏览器下载字节比对、确认解绑均实际执行 |
| 上传完成后丢弃响应 | 刷新并重选原文件后继续原 session，不新增 begin，完成原绑定 |
| 无成员资格/已撤权账户 | 不允许列附件、新签下载或继续已有上传会话 |
| 归档材料 | 保留附件读取，拒绝新上传；验证后恢复测试材料 |
| 解绑 | 列表移除，不能再获取新下载签名 |
| 既有下载签名 | 撤权后在原有效期内仍可使用；实际等待自然到期后返回 403 |
| 签名 HTTP 响应 | sign/download 返回 Cache-Control: no-store |

没有关闭浏览器 CORS、修改签名地址或用请求替身伪造存储成功。故障注入仅在真实服务端已经处理后丢弃响应，或拦截写后列表读取。

首次浏览器下载曾因响应缺少 Access-Control-Allow-Origin 而失败。桶的实际 CORS 规则读取正确；后续保持同一规则，对同对象和新上传对象重新签名下载均成功。
本轮未确定这次瞬态响应的根因，因此保留为存储部署联调风险，不声称已修复供应商实现，也不由本地成功推导生产稳定性。
