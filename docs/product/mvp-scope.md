## 1. 结论

建议首版围绕以下目标收敛：

**一个实验室团队能够在自己的组织和工作区内，登记材料、管理库存与位置、完成领用/归还/转移和必要审批，并查到待办、风险提醒与操作记录。**

这里的“最小”是业务流程、材料类型和治理复杂度最小，不是省略租户隔离、权限、库存一致性和追溯。首版不以实现全部 71 张设计图、完整概念 ER 或所有 Core Kernel 为交付标准。

- 核心工作面：工作台、材料、库存；设备入口按实际已实现能力开放。
- 核心管理面：组织、工作区、成员和最小授权管理。
- 必要支撑：自有身份/会话、绑定型附件、审计、站内通知、权限感知的查询。
- 本轮明确延期：视觉识别、机械臂取放、真实设备控制及其端到端联动验收。
- 建议后续演进：完整培养/QC/谱系、可配置工作流、复杂设备集成、商业计费和企业级治理。

## 3. 产品定位、用户与价值

### 3.1 产品定位

综合材料/库存/设施/设备的领域划分和当前导航，TalosArk 的软件部分适合定义为：**面向科研与实验室团队的资源协作和运营管理平台**。样本与试剂的登记、定位、协作和追溯是首个切入场景，不是通用知识库，也不应在首版承担完整 ELN、LIMS 或临床系统的全部职责。[S1][S2][S3]

商业计划书仍突出“视觉识别 + 自动存取”的软硬件整体产品；这与先验收软件不矛盾，硬件能力是后续阶段，不是从产品路线中删除。[S8][S12]

### 3.2 首批用户

计划书的人群画像是依赖 Excel/人工台账、拥有少量低温存储设施的中小生命科学团队，示例规模为 5-50 人。这个数字是用户画像，**不是并发指标、授权席位或系统数据容量限制**。[S8]

建议首批试点明确三类使用者，名称和最终角色配置待确认：

- 团队管理者：建立工作区、配置成员和权限、掌握库存及风险。
- 实验人员：找到材料和位置，发起或执行领用、归还、转移，处理个人任务。
- 库存负责人/审批人：维护存储位置、入库与盘点，审核申请、处理差异和提醒。

这些是职责画像，不是强制三种数据库角色；一个人可以兼任多种职责。

### 3.3 应验证的价值

- 从“知道材料名称”到“找到可用库存及准确存储位置”能形成连续路径。
- 多人操作后库存、位置和历史一致，不依赖人工维护多份表格。
- 能回答谁在何时，以哪个工作区上下文，对什么对象做了什么。
- 工作台能反映真实可处理事项，不展示无法追溯来源的模拟 KPI。

试点成功的业务指标建议记录查找耗时、定位成功率、台账/实物差异和流程完成率；具体阈值由试点规模确定，不在没有基线时编造提升比例。

## 4. 已有领域约束与术语

| 概念 | 当前可确认的边界 | 不应直接推导的结论 |
| --- | --- | --- |
| Organization | 硬租户边界，包含工作区 [S1] | 组织成员自动拥有组织内全部资源权限 |
| Workspace | 协作和查询上下文；当前前端的页面、搜索、详情、批量动作使用当前工作区 [S4] | 前端按 workspaceId 过滤即可代替后端鉴权 |
| Acting Workspace | 设计清单存在此入口；历史总结将其作为操作上下文 [S2][S3] | 首发必须开放独立于当前工作区的任意切换 |
| Material | 描述材料“是什么”，与库存分离 [S1][S3] | 一个材料只有一个位置、一个数量或一个通用状态 |
| MaterialBatch / MaterialInstance | 概念图保留批次和实例，实例可属于批次 [S1] | 所有材料必须有批次，或专业子模型已冻结 |
| StockItem / Placement | 库存主体及位置关系；核心链为 StockItem -> Placement -> StorageNode -> StorageTopology -> Facility [S1] | Material/Batch/Instance 多态外键已经确定 |
| Facility | 属于 Organization；Workspace 的管理/共享与租户归属分离 [S1] | 设施可见就自动获得设备、存储和材料权限 |
| Equipment | 平台能够读取、监测或控制的数字化设备 [S2] | 普通柜子/没有接入能力的冰箱必须建成设备 |
| ResourceIdentity | 文件、任务、审计等跨模块能力的业务资源身份与引用入口 [S1] | 它本身就是权限图谱，或所有鉴权都必须经过资源身份 |
| FileObject / FileAsset / FileReference | 存储对象、用户可见文件资产、文件与业务资源的绑定关系 [S1][S3] | 文件独立授权、版本、跨工作区复用规则已定案 |
| Workbench | 查询面/读模型，不是业务事实来源 [S1] | 直接修改工作台快照就完成库存/审批业务 |

权限的明确 MVP 约束为 **allow-only + deny-by-absence，不设计显式 Deny**。[S1] RBAC/ReBAC、有限 ABAC、查询权限下推属于历史架构讨论；具体权限点、授权来源和继承规则仍须落实到首发用例，不能仅凭缩写完成设计。[S3]

I05 仍负责资源身份与引用，不接管该解析器或复制所有权。前端消费引擎无关的 capability，不引入第二套授权事实。
子节点可以不继承父节点授权，但这是长期规则方向，不等于已将完整节点授权纳入首发；停止继承不是显式 Deny。
当前实现与待补项见[权限与权限上下文设计](../../packages/backend/docs/design/permission-authorization-2026-10-18.md)，不据此宣称功能完成。

存储节点不应被旧 README 的 ROOT/CONTAINER/BOX/BOX_SLOT 四级结构锁死；最新概念图采用拓扑与节点。是否采用 ltree 等物理实现，不属于本次范围冻结。[S1][S3][S9]

### 5.1 身份范围不能反向由现有代码决定

在 `TalosArk · 前端` 对话中，用户明确要求：TalosArk 维护自己的登录体系；平台管理员可以配置外部身份提供商；产品登录页需要账密、手机号、邮箱等传统方式。[S10]

因此，M01 的首发收敛只是建议，不是撤回该产品要求。**账密、邮箱、手机和外部身份源中哪些必须首发，哪些可以延后，仍需用户明确确认。** 也不能因为当前 Casdoor/OIDC 已有代码，就将其视为唯一身份系统。

### 5.2 首发材料类型和数量模型

建议以当前场景中的试剂瓶、冻存管等库存为第一个落地切片，但示例中的 DMEM、HeLa、FBS 不能证明首发类型已经冻结。[S2][S6]

需先决定：按瓶/管逐件追踪，还是按总体积/质量管理；批次是否必需；打开/耗尽/过期如何表达；单位精度与归还规则是什么。材料定义、批次、实例和库存之间的边界不能靠复制 Mock 类型解决。

完整 Cell Bank、Cell Culture、传代/复苏、谱系、QC 方法及结果评价建议延期。普通“冻存细胞材料登记和库存”不等于必须同时交付培养管理。

### 5.3 共享和操作上下文

建议先覆盖组织内、当前工作区以及明确授权的共享设施，暂不做组织间资源共享。概念文档明确 Facility 组织归属，但 **Material 与 Workspace 的治理/所有权/共享模型仍为 Open**，不能据此自行确定材料都属于工作区。[S1]

首版可考虑操作上下文默认使用当前工作区；是否允许选择独立 Acting Workspace、共享资源由谁负责审核和审计归属，必须先确定。租户归属、资源所有权、可见性、管理权和本次操作上下文应分别建模。

### 5.4 软件首发中的设备

本轮已确认不以真实硬件联动作为首版验收门槛。[S12]

建议首版最多保留必要的设备资料和人工维护/巡检关联；遥测、在线状态、设备告警、命令执行结果没有真实数据来源时应禁用或延后，不将模拟在线/温度当成交付。

已有冰箱/柜子的存储位置管理仍属于 Facility/Storage 范围，不依赖设备接入。设备基础信息是否首发必需，也可以按试点需求裁减，而不阻塞材料库存闭环。

### 5.5 首批数据进入系统

如果试点已经有大量 Excel 台账，基础模板导入应纳入首发；如果首批仅验证少量新登记材料，可先人工录入。导入范围建议限制为已冻结字段的标准 CSV，不先做任意 Excel 映射和通用 ETL。

基础导出建议首发保留。导出、附件访问和导入同样需要授权，不能绕过列表的数据范围。历史商业记录支持保留数据查看/标准导出方向，但其最新原件本轮未找到，不能直接据此冻结订阅到期规则。[S11]

## 6. 可验收的端到端闭环

这些是评审后应执行的业务验收场景，不是本次已完成的测试，也不要求现在新增测试脚本。

1. **团队建立**：用户登录 -> 建立/加入组织和工作区 -> 管理者授予成员所需权限 -> 成员只看到授权数据；未授权成员不能通过复制 ID 或直接调用接口访问。
2. **材料入库**：登记材料 -> 建立必要批次/实例 -> 选择设施、存储节点和孔位 -> 完成入库 -> 材料详情、库存列表、存储浏览和流水能互相对应。
3. **查找与流转**：从材料检索找到可用库存和位置 -> 按授权直接操作或申请领用 -> 审核 -> 确认执行 -> 数量、位置、状态和历史一起更新；归还/转移可追溯。
4. **盘点纠偏**：限定盘点范围 -> 记录实物差异 -> 授权确认调整 -> 生成调整流水与审计，而不是直接覆盖库存数字后丢失原因。
5. **协作收尾**：审批结果同步关联待办；普通任务可完成，审批类待办不能绕过申请流程；工作区切换后不会对上一个工作区的旧勾选执行批量动作。
6. **风险处理**：真实库存/截止时间触发提醒 -> 查看对象 -> 处理或忽略 -> 留下处理记录；标记提醒已处理不等于库存不足或设备故障已经自动消失。
7. **一致性与重试**：重复提交、两个用户争用最后库存或同一孔位、重复批准同一申请时，不产生双重扣减、重复流水或相互覆盖；失败有明确结果。
8. **持续使用**：刷新页面后业务仍存在；会话可续期/退出；数据可按授权导出；备份恢复后仍能关联库存和操作记录。

第 3 条中的“批准”和“执行”不能默认为同一时刻。批准时扣减、预留还是执行确认后扣减，以及拒绝/撤回后的处理，是尚待确认的业务规则。

## 7. 延期边界

| 能力 | 本次归类 | 保留的演进方向 |
| --- | --- | --- |
| 视觉识别、机械臂取放、真实设备联动 | **已确认下一阶段** | 在软件库存/授权/审计闭环上接入真实设备，不另造孤立台账 |
| 广泛设备协议、实时遥测、控制台、命令重试/回执 | 建议随硬件阶段 | 单一真实设备闭环优先，不先支持所有厂商 |
| AI Agent 的自然语言执行编排 | 建议延期 | 商业记录讨论过组织版能力；套餐承诺不等于软件 MVP 必须同时实现 |
| 完整培养、谱系、QC、Cell Bank 专业工作区 | 建议延期，需确认试点是否硬需求 | 保留材料/批次/实例边界，不先实现全部专业子表 |
| 通用工作流、多人会签、自动升级、复杂预约/预留 | 建议延期 | 先从已确定的固定流程演进 |
| 组织间共享、跨组织搜索、跨工作区聚合工作台 | 建议延期 | 不突破硬租户边界；另做治理设计 |
| 自定义材料 Schema、公式、通用资源建模平台 | 建议延期 | 根据真实材料类型需求决定是否需要 |
| 全量 Webhook/外部同步、集成市场 | 建议延期 | 后续从一个有客户需求的集成开始 |
| 在线付费、套餐自动结算、席位计费和超额计量 | 建议延期 | SaaS 商业模型与首版是否集成计费分别确认 |
| SSO/SCIM、企业治理、复杂审计留存策略、多区域 | 建议延期 | 基础权限和基础审计不能因此从首版剔除 |
| 六端同时交付、完整离线同步 | 建议延期 | 先确定一个可部署的 Web/桌面首发载体 |

延期不是删除旧需求，不改变已写入产品路线的长期目标。没有明确批准前，不执行相应删除或破坏性改动。

## 9. 后端推进顺序

本节保留初稿概要；逐项执行使用 [P00-P19 工作安排](mvp-work-plan.md#3-按什么顺序交付)，不把概要当作可直接实现的任务说明。

每个切片都同时覆盖数据模型、权限、事务/审计、API 契约和前端接入；不要先把所有底层能力建完才开始业务。[S5][S10]

1. **范围与术语定案**：先确定第 10 节的高影响问题，选定首发材料和第一个真实用户故事。产出明确业务不变量，不先生成全部候选表。
2. **身份和团队边界**：可用登录/会话 -> 组织/工作区成员关系 -> 最小权限点 -> 服务端校验上下文。验证同租户未授权和跨租户两类拒绝路径。
3. **第一条入库切片**：材料 -> 必要批次/实例 -> Facility/Storage -> 入库流水。用一条记录贯穿真实数据库、API 和界面；附件可在此或紧接其后接入。
4. **库存流转切片**：领用/归还/转移 -> 简单审批 -> 执行和一致性保护 -> 待办/通知/审计投影。先确定状态机，再实现批量动作。
5. **盘点和风险切片**：受控调整、盘点差异、低库存/到期提醒。复用已有流水和授权，不创建第二套库存事实。
6. **工作台与试点交付**：真实查询替换 Mock、权限感知摘要/搜索、必要导入导出、部署和备份恢复验收。硬件联动另立下一阶段范围。

技术范围按真实用例拉动：事务、权限、附件和审计是这些切片的必要支撑；通用 Task/Event/Cache/Lock/Realtime/Quota/Risk 平台、可插拔注册体系和完整配置界面，不因目录存在而全部先做。

现有仓库规则要求未批准纵向切片不得实现 TODO；当前阶段不重建历史迁移/seed，也不擅自新增或维护测试脚本。[S5] 本文仅描述将来验收要求，没有执行数据库同步、创建测试或实现 TODO。
