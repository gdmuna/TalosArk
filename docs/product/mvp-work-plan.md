## 1. 先看结论

接下来的主线是软件业务闭环，不是再做一轮全仓重构：

**能登录和恢复账户 -> 能建立团队并正确授权 -> 能登记材料和位置 -> 能真实入库 -> 能安全流转和审批 -> 能盘点、处理待办和提醒 -> 能交付试用。**

基础能力并没有停做，而是跟具体任务一起交付：做团队就补授权，做资源引用就补 Resource，做附件就补 File，出现不能丢的异步工作才补可靠任务。
不先填满全部 Kernel、Registry、Port 和目录，再开始第一条业务接口。

### 已确认的规则，不再重新讨论

- 先验收软件，真实视觉、机械臂与设备控制留到下一阶段。
- 第一方账密登录和邮箱找回密码在 MVP；手机认证延期，现有 OIDC 保留，Casdoor 继续必配。
- 本地密码账户采用邀请或管理员开户，不开放自助注册。P01 先提供受控运维开户，组织成员邀请和管理界面放在 P06。
- 用户名和邮箱均可登录；用户名区分大小写，邮箱忽略大小写，标识去掉首尾空格，不合并邮箱的点或 + 后缀。首次密码通过专用、一次性、限时激活链接由用户设置，与找回密码凭据分开。
- OIDC-only 用户登录后主动设置本地密码；找回密码只恢复已有本地密码的账户，不借恢复流程创建密码。
- 会话支持页面刷新和重新打开：RT 使用持久化 HttpOnly Cookie，AT 只留在内存。现有 JSON 返回/接收 RT 的公开协议须随账户切片调整，不能只改前端存储。
- Organization 是硬租户边界；当前工作区是默认操作上下文，不能只靠前端过滤保证隔离。
- 材料独占一个工作区；MaterialType 是平面分类，不做材料跨工作区共享。
- 逐瓶/逐管跟踪，批次可选；一件实物最多有一个当前位置。
- 批准不预留、不扣库存；执行时重新校验，成功执行才改变库存。
- 权限采用 allow-only，未获得授权就是拒绝；不新增显式 Deny。
- 权限执行采用本地 Casbin，Casdoor 保留身份集成。I04 的 Authorization 统一解析业务目标真实 scope 并编排判定；I05 ResourceIdentity 仍是跨模块引用，不是权限图谱。
- 普通任务不等于审批待办，也不等于后台 Job；逾期是根据时间计算的显示/查询状态。
- 使用现有错误工厂、共享 wire contract 和 DatabaseRuntime；公开响应不暴露内部 metadata。
- 不恢复旧 migrations/seed，不擅自执行 db:push/db:init/migrate，不自动新增或维护测试脚本。

## 4. 每项任务具体做什么

### P00：把当前阶段的规则和验证环境定清楚

**不是再写一套架构，而是消除马上会阻塞开发的决定。** 后面阶段的问题到开始那个阶段时再定。

1. 核对最新提交、Cookie 绑定等在途改动、W01-W07 记录；列出这轮实际可复用的接口和仍未接入的客户端功能。
2. 从第 6 节决策表先确认 D01-D03 中本轮涉及的产品选择：本地账户如何产生、登录标识与恢复资格、前端会话保存方式；技术默认方案随对应实现提出，不在 P00 展开所有参数。
3. 确定隔离验证环境以及能否创建合成记录；数据库、邮件、Casdoor、对象存储分别说明本轮是否有真实环境。
4. 选择一条具体试用故事，例如“实验人员登录自己的工作区，登记一瓶试剂并放入某个孔位”。不一次支持全部材料专业模型。
5. 为本轮任务写出接口职责、成功结果、典型拒绝结果和涉及模块，再开始实现。URL 和 wire 字段在契约任务中定，不在计划里凭空冻结。

**产出：** 第 6 节更新过的决定、本轮任务范围、验证环境边界。
**验收：** 开发者不用重新猜测账户来源、恢复策略或数据库操作授权；后续任务有明确输入。
**这次不做：** 全局插件框架、全仓目录搬迁、生产数据修改、预先生成全部 API/schema。

2026-10-13，P00 已完成。源码/在途改动核对、只读运行环境检查和本轮产品选择已记录：用户名区分大小写、邮箱忽略大小写，首次密码使用专用激活链接。用户允许在已有 `talos-ark_backend_test` 先只读核查，再执行明确列出的必要 Schema/DDL 和本轮合成记录写入；不清空库、不删除原有数据、不操作 dev/prod，破坏性变更先暂停说明。两个 `.env.test.local` 已符合目标。技术方案随对应任务提出，P02 的邮件细节不阻塞 P00；尚未实施 P01 或数据库写入。详见 [核对记录](mvp-p00-2026-10-13.md)。

### P01：完成第一方账密登录和真实当前账户

涉及：`backend/src/modules/auth`、`modules/user`、`core/identity`、`core/session`、`contract/src/auth`。
依赖：P00 的 D01/D03；账号创建方式不能默认等于开放注册，首次登录交付必须遵守已选 Cookie 协议。

1. 用户名和邮箱均可登录；标识去掉首尾空格，用户名区分大小写，邮箱忽略大小写，不合并邮箱的点或 + 后缀。落实匹配及唯一性，检查既有邮箱碰撞及数据库约束；必要的 Schema 变化先说明，不自动合并或删除原有账户。
2. 提供受控运维开户入口，创建无密码账户和专用、一次性、限时激活链接，由用户设置密码，只保存密码 hash，不恢复 seed、共享临时密码或匿名注册。组织邀请和管理界面留到 P06；OIDC-only 账户登录后主动设置密码，不复用找回密码来完成首次设置。
3. 实现账密登录：识别账户、验证密码、按既有 Session 能力签发会话；登录失败不泄露究竟是账户不存在还是密码错误。
4. 增加当前账户查询，返回客户端需要的身份与资料，不返回 hash、内部 Token 或未经授权的组织资料。
5. 为入口增加失败频率限制，声明请求、成功响应和错误契约；密码和登录凭据不得写日志。
6. 按职责把新增 Auth 代码放到 api/application 等位置；现有平铺文件只在本任务确有需要时迁移，不为目录整齐拆转发类。
7. 登录成功和 RT 轮转由 HTTP 层写 Cookie，公开 JSON 不再返回 RT，刷新不再接收 body 中的 RT。同步调整 OIDC、refresh/logout 的契约与必需客户端类型；复用 Session 的签发和轮转，不把 Fastify Cookie 放进 Core。Cookie/CSRF/CORS 的明确策略以及退出时 AT 已失效的处理，在实现前一并定清。

**产出：** 账密登录、选定的开户能力、当前账户接口及对应公开契约。
**验收：** 正确密码得到可验证的凭据；错误密码、重复标识、OIDC-only 账户走明确拒绝路径；当前账户来自验证后的身份，而不是请求 body 中的 userId。
**这次不做：** 手机、MFA、任意 IdP 注册、自动合并同邮箱账户、自动开放自助注册。

2026-10-13，P01 后端完成，真实页面接入留到 P03。已实现受控开户/激活重发、首次密码、账密登录、当前账户及统一 Cookie 会话；实际 test 库同步和 94 项一次性检查、CLI/HTTP/OpenAPI 证据见 [P01 实施记录](../../packages/backend/docs/design/mvp-p01-2026-10-13.md)。没有把隔离提供商或后端验收当作真实浏览器/Tauri/生产验收。

同日按讨论完成 [P01 fix](../../packages/backend/docs/design/mvp-p01-fix-2026-10-13.md)：统一 HTTP/Auth 来源策略，开发回环端口放通，Argon2id/PHC、私有凭据实现和事务外密码预计算；Auth 统一编排密码/会话事务。六份 env 默认已落实，真实 test 库/Valkey/Fastify 的 88 项检查及受控开户 CLI 通过。旧配置名和 scrypt hash 不兼容，未清库或迁移；P02/P03 状态不变。

### P02：完成邮箱找回密码

涉及：Auth/Identity、Session、`infra/mail`、`PasswordResetToken`。
依赖：P01；OIDC-only 处理已确认，开始前提出 D02 的有效期/发送限制方案并确认邮件要求。

1. 提供申请恢复入口：存在与不存在的账户采用批准的统一外部响应，限制对同一目标和来源的发送频率。
2. 生成高熵恢复凭据，只保存 hash、有效期、目标邮箱快照和消费状态；邮件发送不能让尚未提交的数据库事实被误当成功。
3. 实现确认恢复：验证凭据未到期、未撤销、未消费，且邮箱仍与账户一致。
4. 在一次事务内消费凭据、修改密码、撤销其他恢复凭据和旧会话；任何一步失败都不留部分结果。
5. 明确邮件失败后的用户提示和重新申请方式。若要求自动可靠重试，启用第 5 节的可靠异步任务，不用一次 best-effort hook 冒充送达保证。
6. 客户端能填写邮箱、打开恢复链接、提交新密码和看到有效/失效结果；恢复凭据不进入观测日志或埋点。
7. 对 OIDC-only 账户采用既定规则：不能用邮箱恢复入口首次创建本地密码；有无可恢复账户仍保持一致的外部响应。

**产出：** 恢复申请/确认接口、邮件模板、恢复页面、错误和频率限制规则。
**验收：** 两次并发使用同一凭据只能成功一次；消费后不能重放；邮箱变化、过期或撤销时拒绝；原会话在恢复完成后失效。
**这次不做：** 短信恢复、客服人工解锁、复杂身份验证流程。

### P03：让前端真正使用后端会话和当前用户

涉及：`frontend/src/module/auth`、`module/account`、`platform/http`、`main.ts`。
依赖：P01；恢复页面依赖 P02；采用 D03 已确认的会话保存策略，实际载体与失败行为在开工方案中列明。

3. 登录成功后获取真实当前账户；清理模拟身份、旧组织上下文和上一次会话的数据。

**产出：** 前后端认证接通，真实用户资料，登录/恢复/退出与重新进入的页面流程。
**验收：** AT 过期后只进行必要的刷新；刷新失败不会循环；退出后晚到的旧响应不能复活会话；刷新页面后的行为符合选定保存策略。

### P05：以真实授权定义落地最小 Discovery

**交付与验收：** 2026-10-22 已完成真实登录 Web、原接口和 test 数据库联合验证，包含审批并发撤回、入库占位冲突、丢失成功响应、刷新原键恢复、零量占位、成功后读取失败的 GET-only 恢复。详见 [P13 实施记录](mvp-p13-2026-10-22.md)。
**这次不做：** 任意跨工作区批次、直接批量消耗/转移/处置、任务/提醒批量写入、通用服务端 bulk engine、后台自动继续、跨 tab 恢复；Tauri/部署验收单列。

### P14：实现首发选定范围的人工盘点

涉及：Stocktake、Inventory、位置浏览和盘点界面。是否首发包含本项，先在 D12 确认。
依赖：P11 的受控调整；不能直接覆盖 StockItem 当前值。

1. 创建盘点会话，固定本次工作区/位置/实物范围和用于判断差异的版本。
2. 记录逐件实物数量、位置、备注和完成状态，区别“未核对”和“核对后数量为零”。
3. 提供差异查询；盘点途中发生出入库时，按版本冲突规则要求重新核对，不能把旧观察覆盖成新事实。
4. 确认差异时检查操作权限、所需核对状态和当前版本，生成 ADJUSTMENT 流水，原子修改当前库存及审计。
5. 发现系统里没有登记的实物，走材料登记/入库，不创建没有对象的盘点行来绕过登记。

**产出：** 盘点创建/录入/差异/确认能力，实际盘点界面与调整关联。
**验收：** 版本变化不会静默覆盖；重复确认不会多次调整；盘点差异可追溯到哪次调整以及当时的操作者。
**这次不做：** 复杂盲盘/复盘、多阶段组织流程、扫码硬件工作站。

### P15：实现普通任务，不把它和审批或后台 Job 混在一起

涉及：普通任务的业务模块、Resource/Permission、我的待办界面；按本任务批准范围建立实际业务所有者。
依赖：P06/P07；审批待办的联合展示依赖 P12。

1. 实现本轮需要的创建/指派、详情、完成和历史；具体可修改/取消范围先定，不凭空开放全部状态动作。
2. 当前负责人必须有有效成员资格，相关对象属于授权上下文；操作者 ID 来自认证上下文。
3. 完成普通任务记录完成者、时间和事件；不能通过这个入口批准申请或确认库存执行。
4. 截止时间仍是事实字段，已逾期在查询/展示时推导，不新增一份可独立写入的 OVERDUE 状态。
5. 当前工作区、个人权限、状态和时间筛选在服务器查询时生效；不是把全部任务拉给客户端再隐藏。
6. 明确普通任务的业务模块与 `core/task` 后台 Job 的区别，接口和状态不共用同一套词义。

**产出：** 普通任务实际接口、权限感知个人查询、历史和待办页的对应真实操作。
**验收：** 普通任务能完成；审批类待办没有这个写入口；移除成员后不能继续操作；跨过截止时间不需要另一条写入才能显示逾期。
**这次不做：** 通用工作流、周期性任务编排、用 BullMQ 保存普通待办事实。

### P16：让异常提醒和站内通知来自真实业务

涉及：Alert/Notification 的业务所有者、库存/任务来源、提醒界面；可靠后台触发有需要时启用第 5 节。
依赖：P09/P12/P15 中对应的数据来源；开始前确认 D11。

1. 先选数量有限的低库存、临期/过期、任务逾期规则，明确阈值、时间和来源；不用设备模拟温度生成告警。
2. 选择触发方式并保证进程重启后能够补查；需要可靠跨进程执行时启用任务/Outbox，不靠一次内存 timer 充当永久保证。
3. 同一来源/规则去重，恢复后再次出现时按已定规则重新打开并追加事件，不能丢掉之前处理历史。
4. 实现处理、忽略与记录；标记提醒已处理不改变库存，也不自动完成普通任务。
5. 站内通知保存收件人各自的未读/已读状态；审批等必须与业务一致的通知采用同事务写入。
6. 读取和跳转相关对象时仍检查当前权限，不能通过提醒卡片或旧通知绕过资源授权。

**产出：** 已选规则的实际触发/补查、异常处理、站内通知和对应页面。
**验收：** 同一风险不刷出无穷重复提醒；重启后能补查；处理后来源仍异常时不伪装成已恢复；一个收件人已读不会改变其他人的状态。
**这次不做：** 硬件告警、所有邮件/短信/推送渠道、通用 Rule Engine 或 AuditEnricher Registry。

### P17：把工作台和相关前端数据逐批换成真实接口

涉及：工作台查询所有者、`frontend/src/module/workbench/data/source.ts`、`model/overview.ts` 及各资源数据源。

前端执行与验收由 [R10 工作台专项](../../packages/frontend/docs/remediation/2026-10-15/r10/README.md) 跟踪：先接已有资源概览，任务/审批/提醒随各自源业务分批交接，不能因缺少总快照而阻断整个工作台。
依赖：所展示的源业务已经完成；本项按来源分批做，不等全部后端完成才开始联调。

1. 从已授权的任务、申请、提醒等事实计算卡片和列表；不建一份客户端可以提交修改的 Workbench 总快照。
2. 明确每个列表的过滤、组合排序、分页和数量统计范围；统计必须与权限感知列表一致。
3. 拆分需要的读接口与投影，不照搬 mock `load()` 必须一次返回全工作区全部记录的形态。
4. 让详情、批量操作和资源跳转回到各业务所有者；工作台不承担另一套审批/库存写入规则。
5. 已完成业务切换到 API 数据源；未完成业务继续明确未接入或只在开发模式用 mock，不静默回退模拟成功。
6. 检查过期/逾期时间口径、切换工作区后的旧请求取消、重新加载失败和未授权对象显示；写入权限及截止判断以服务端为准。
7. 每一批接入同步更新对应前端 Context，保留现有表格设置和交互，不把“换数据源”扩成组件重写。

**产出：** 真实工作台摘要/列表、模块 API 适配器、明确的空/失败/未授权/未接入状态。
**验收：** 修改源业务后工作台能更新；刷新不恢复 fixture；列表和卡片不会泄露未授权记录；旧工作区响应不能覆盖新工作区。
**这次不做：** 跨工作区聚合、全局全文搜索、实时大屏或虚构设备在线 KPI。

### P18：提供有权限边界的标准导出，需要时再做导入

涉及：选定业务模块的查询/写入和导入导出界面。首发是否包含及覆盖哪类数据，由 D12 确认。
依赖：P07/P09；导入库存还要遵守已经完成的写入规则。

1. 确认首发必须导出的字段、格式和数据范围；导出使用与正常列表一致的授权规则。
2. 根据试点量设置可用的分页/条数限制、超限提示和一致性口径，不默认一次加载全部数据。
3. 如果需要导入 Excel 旧台账，先提供固定字段的标准 CSV 模板、校验和可理解的行级错误，不做任意列映射平台。
4. 导入通过现有材料/入库用例，不能直接批量插表绕过权限、单位、位置、幂等、流水和审计。
5. 明确文本转义、公式执行风险、重复导入、失败后恢复和个人信息字段取舍。

**产出：** 已选范围的导出、必要时的导入模板/预检/结果与界面。
**验收：** 导出不能扩大到无权限数据；重复导入不重复建库存；非法位置或单位行被明确拒绝；用户知道成功和失败各是哪几项。
**这次不做：** 任意 Excel ETL、通用迁移平台；确有大规模后台导出需求才启用可靠任务。

### P19：完成一次团队能持续使用的试点交付

**验收：** 约定试点人员能连续使用；重启不丢业务事实；恢复后库存、位置、附件和历史仍对应；跨租户拒绝及关键并发结果有真实证据。
**这次不做：** 硬件阶段验收、六端同时交付、企业级灾备或未确认的商业计费。

## 5. 基座工作何时插进来

这些不是默认排在业务前面的另一条大主线。触发条件出现时，它们就是对应任务的一部分，不能拿“以后再做”搪塞可靠性。

| 触发条件                                                           | 当时必须补什么                                                 | 不顺便扩到哪里                       |
| ------------------------------------------------------------------ | -------------------------------------------------------------- | ------------------------------------ |
| 第一个管理或业务写入                                               | 最小审计，与受审计业务保持明确提交关系                         | 全域审计插件/富化机制                |
| 第一次可能重试的关键创建/执行                                      | 请求幂等、内容比对、条件写入和冲突结果                         | 通用 distributed lock/fencing 平台   |
| 首批授权贡献，后来加入资源或文件用途                               | 复用 P05 的采集/校验机制，由各宿主管自己的注册表               | 不一次实现所有贡献类型               |
| 文件要求必须完成后处理，邮件要求自动可靠重试，或跨进程副作用不能丢 | TaskHandler、任务发送/消费、必要 Outbox/幂等及 Worker 生命周期 | 通用工作流、为普通待办建 Job         |
| 同一进程内多个动作重复同步逻辑                                     | 先收敛所属业务模块的操作                                       | 不为抽象复用提前建 EventBus          |
| 某条查询有真实重复加载或性能问题                                   | 先优化授权后的查询；必要时最小 Cache 策略与失效规则            | 全量 SWR、分布式 SingleFlight/PubSub |
| 客户端确实要求实时更新而轮询不足                                   | 对那类消息明确权限、断线恢复和可靠性，再接 SSE/WS              | 所有接口重写为实时协议               |

可靠异步任务最少要交代：谁保存任务事实、何时提交、谁消费、怎么重试、重复执行如何无害、失败能否排查、停机怎样收尾。
需要保证发送时，与业务事实同事务保存待发送记录，再在事务外派发；不把 DatabaseRuntime.afterCommit 的 best-effort 当成不会丢的消息机制。
队列/存储/权限执行器用显式装配，业务 Handler/Subscriber 用实际需要的 Discovery；普通策略参数仍是 typed config。

若用户批准的决定与现有模型/契约冲突，要先说明具体差异和破坏点再改；不能用“快速迭代”作为隐藏业务变化的理由。

## 7. 文件按什么职责放，不再搞一次全仓搬迁

| 工作                               | 放在哪里                                               | 不该放在哪里                                              |
| ---------------------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| 请求/响应和公共错误 schema         | `packages/contract/src/<业务>/`                        | Prisma 模型、Nest 类、供应商 SDK 类型不能放进公开 wire 包 |
| HTTP 参数绑定/Controller           | `backend/src/modules/<业务>/api/` 与既有 Platform 支撑 | Controller 不组装跨域库存写入                             |
| 一次具体操作的编排和事务           | `modules/<业务>/application/`                          | 不塞进全局 Bootstrap 或巨型 Core Kernel                   |
| 数量、状态、流程等领域规则         | `modules/<业务>/domain/`                               | 不做成 Common 通用规则集合                                |
| 跨模块调用入口                     | `modules/<业务>/public/`                               | 不直接调用别的模块私有 Repository                         |
| 业务贡献                           | `modules/<业务>/extensions/`                           | Core 不硬编码 Material/Equipment 等所有模块清单           |
| 对数据库的业务私有查询/写入        | 所属模块实现或 `infrastructure/persistence/`           | 不为了每条查询都强制建转发 Port/Repository                |
| Nest Discovery 采集及运行时桥接    | `platform/extensions/`，装配在 Bootstrap               | Registry 校验的业务知识仍归宿主                           |
| 通用数据库/HTTP/对象存储等技术实现 | 现有 `infra/` 所有者                                   | 不为目录对称复制一份能力                                  |
| 前端端点/解码/映射                 | `frontend/src/module/<业务>/data/api.ts`               | Platform HTTP 不知道业务状态                              |
| 前端业务动作与状态                 | 该模块 `model/`，由应用入口显式装配                    | 页面不直接绕过业务模块改会话/共享状态                     |

小模块不需要填满上述目录。只在职责真的出现时新建文件；Auth 的已有文件迁移随新增用例进行。
不恢复全局 constants、Common error/result 总体系或 Core TransactionKernel；普通待办的业务所有者与后台 `core/task` 分开。
前端继续使用现有模块边界、组件和数据源接口，不用这份计划覆盖用户正在进行的前端重构。

## 8. 一项工作怎样才算完成

每个任务交付时都给出下面这些，不只报告“代码写好了”：

1. 明确范围和规则已确认；未实现项写清楚，不把建议自动当承诺。
2. 业务实现、必要数据库变化和公开契约对应；新配置有默认口径，并落实到相关 example/实际 env 文件，不输出真实凭据。
3. 成功、无权限/跨租户、重复提交/过期/版本冲突、部分失败等适用场景有实际检查结果。
4. 对应前端真正调用接口；如果本轮只交付后端子任务，必须标“后端完成，前端未接”，不能把整项任务标完成。
5. 构建、定向 lint、格式和差异检查通过；源码、文档、API 文档按改动更新。
6. 验证环境和证据说清楚：静态检查、隔离依赖检查、本地真实数据库、真实提供商、浏览器、部署分别记录，不能互相替代。
7. 失败恢复、事务提交前提和已知限制可理解；写入成功而同步失败时，不靠再次写入“修复”。

当前不自动新增/维护仓库测试脚本。可以在批准的环境做一次性验证；需要保留自动化回归脚本时先单独确认。
没有环境操作授权，不执行数据库同步/DDL、不触碰现有真实数据、不停止用户服务、不轮换密钥。计划不是这类操作的许可。

### 怎样更新任务进度

状态只使用：**待确认、待启动、开发中、后端完成待接入、待整体验收、已完成、延期**。

- 开始一个任务时，写批准范围、决定编号和当前依赖。
- 完成子步骤不等于完成任务；前后端/环境证据欠缺要直说。
- 标记已完成时附实施记录或验收结果及日期，并更新第 3 节，不维护第二张相互矛盾的主任务表。
- 新出现的基座问题，说明正在阻塞哪一项，再插入那个任务；不要扩成没有结束条件的“基础设施优化阶段”。

## 9. 暂时不做的事

硬件联动、通用工作流、完整 Search/Realtime/Quota/Risk、所有缓存策略、所有 Event/Task Registry、插件市场、商业计费、专业培养/QC/谱系和企业治理，都不是默认先行任务。
