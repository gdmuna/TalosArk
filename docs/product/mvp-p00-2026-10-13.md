### 账户数据模型的边界

- `User` 目前有唯一 `username`、唯一 `email`、可空 `passwordHash`；数据库唯一约束本身没有定义账号规范化策略。
- P01 按已定规则实现标识匹配及唯一性，并检查现有邮箱是否有忽略大小写后的碰撞；发现冲突时报告，不自动合并账户、修改既有用户名或清理原有数据。
- `PasswordResetToken` 已有 hash、邮箱快照、到期/消费/撤销时间，但恢复服务尚未实现。
- 当前身份模型未记录邮箱验证事实；不能把“数据库里有 email”当成“用户证明拥有该邮箱”。
- 现有模型没有专用的本地开户激活凭据；已选专用激活链接，P01 需列明对应模型变化，不能偷偷借找回密码完成首次设置。
- Common 中保留的旧密码 schema/bcrypt 工具不自动成为新账户的准入和哈希策略；当前没有账密登录消费者。

### 前端当前状态

- `module/auth/data/api.ts` 只接了 OIDC start/callback。
- `model/session.ts` 将完整 `SessionCredentials` 放在内存，并依赖可读 RT 的值/到期时间；这需要随 D03 改为公开会话投影。
- `main.ts` 没有传入刷新适配器；账户/工作区/工作台仍使用 mock 数据源。
- HTTP 已设置 `withCredentials: true`，但这不等于 Cookie 会话已接通。
- HTTP 解码器要求成功包络；当前不能直接处理 logout 的 204，需要明确无内容响应契约。
- 前端 Context 中“refresh/logout 仍返回 501”的说明已经过时；P03 接入时同步修正文档，不以该描述否定当前后端接口。

## 5. Cookie 方案要改什么

这一节是开工约束和下一轮设计清单，不是已经落地的实现。

1. Core/Access 继续拥有原始签发结果，只有 HTTP 适配层设置/清除 Cookie；Core 不接收 FastifyReply。
2. 登录、OIDC 成功和刷新都遵守同一套规则：RT 只写 Cookie，公开 JSON 不再含 RT；刷新不再消费调用方 body 中的 RT。公开响应、OpenAPI 和客户端解码一起调整。
3. 为重新打开后恢复会话设置有限的 Cookie 寿命，不超过相应凭据有效期；服务器继续检查到期/撤销，Cookie 不作为权限事实。HttpOnly、生产 HTTPS/Secure、SameSite、Path/Domain 和清除时一致的属性要明确。依据：[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。
4. 当前 CORS 在 development 放行来源，配置允许列表为空时也放行；不能直接把这种规则用于带凭据的新会话入口。明确来源及 CSRF 防护，不能只设置 HttpOnly/SameSite 就声称防护完成。依据：[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。
5. 启动恢复使用不依赖 AT 的刷新路径；无有效 Cookie 回到未登录，不无限刷新。已有 gate 不应等待它自己的刷新请求。
6. 单页面并发刷新、多标签页共享 RT Cookie、退出和晚到 Set-Cookie 都要考虑。现有前端 revision 只保护内存结果，无法撤回浏览器已经应用的 Cookie；不能照搬旧 JSON 逻辑就认为竞争已解决。
7. 退出不能接受客户端自报 sessionId；需明确 AT 已过期时的验证/撤销途径。网络或提交结果不明时区分“当前页面已退出”和“服务器已撤销”，前端也不能自行删除 HttpOnly Cookie。
8. 开发 Vite 与生产 Tauri 使用的来源/载体不同；Tauri 配置存在不代表持久 Cookie 已验证。先约定本轮验证载体，不用放行任意来源或 `Origin: null` 来凑通。

不顺便改变 W05 已确认行为：RT 重用拒绝当前请求，不自动撤销整个 Session；正常轮转保留未到期且所属 pair/Session 有效的旧 AT。
现有公开 JSON 协议的变更必须在 P01/P03 实施记录中列明；不维持一套可绕过 Cookie/CSRF 规则的“临时兼容”入口。

## 6. 推荐的第一条试用故事

以下是计划用的具体例子，**不是已经确认的 D06 材料必填字段或专业模型**：

> 实验人员通过受控开户获得自己的账户，登录并加入一个实验工作区；管理员登记一种 DMEM 培养基，在普通存储容器下建立一个位置；实验人员将一瓶 500 mL 的材料入库，刷新后能查看当前位置、剩余数量和入库流水。

后续用同一瓶材料继续验收领用/归还或转移、固定审批和附件；另一个组织的用户不能读写它。
本轮只准备这条故事的账户部分，不创建模拟组织/材料，也不让 OIDC 登录直接获得组织管理权限。
具体材料、单位/数量、设施授权和试点人员在 P04-P09 开始前按 D04-D07 确认。
