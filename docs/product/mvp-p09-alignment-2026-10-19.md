# P09 真实入库业务对齐

日期：2026-10-19。状态：业务规则与治理迁移边界已确认，随后获准执行，后端已交付并完成 test.local 定向验证。本文保留产品决定；当前实现和前端待接范围见 [交付记录](../../packages/backend/docs/design/mvp-p09-2026-10-19.md)。

本文承接 [MVP 工作计划](mvp-work-plan.md) 与 [P08 方案](mvp-p08-plan-2026-10-19.md)，区分已经确认的规则和仍需当面讨论的问题。后续决定继续更新本文，不将建议自动视为已批准范围。

## 1. 本轮目标

先明确一件实物如何登记、如何标识、如何计量和定位，再确定带存量容器搬迁的授权边界。最终形成可直接实施的入库、读取与搬迁规则；本次对齐不开发采购、单位换算、自动拆分或跨组织调拨。

P09 的主线是：用户在自己的工作区选择材料，填写可选批次、实例资料、数量与日期，选择有权使用的空位置。成功时实物、当前库存、位置、业务流水、资源身份和审计一起提交；失败不能留下半条业务记录。前端实施与后端交付分开验收。

## 2. 已确认的领域口径

| 项目 | 已确认规则 |
| --- | --- |
| 材料 | 一种材料的定义，独占一个工作区，不保存可写的库存汇总余额；已有实例后不能更换计量单位或业务分支 |
| 实物实例 | 可独立存放、独立流转的一件实物，可以是瓶、管、袋或盒；不是仅限瓶管，也不是一个材料的汇总行 |
| 计量 | 同一种材料始终使用同一单位；一盒 100 支吸头在材料单位为“支”时，是 1 个实例、初始数量 100 支，单位为“盒”时则是 1 个实例、初始数量 1 盒 |
| 数量精度 | 材料增加数量精度，范围 0～6，默认 6；0 只允许整数，其余限制最多小数位数，不按单位自由文本猜测规则；已有实例后不可修改精度 |
| 拆分和换算 | 首版不自动换算单位，不因部分消耗自动拆分并生成新实例 |
| 初始数量 | 首次登记入库时的实际剩余量，允许为 0，不允许负数；它不是原包装标称量，也不代表在系统中补造此前的消耗 |
| 首次库存 | 入库提交时的当前数量与本次确认的初始数量一致；例如原包装 500 mL、剩余 200 mL，按 200 mL 登记 |
| 零量实物 | 数量为 0 时标为已耗尽（DEPLETED），不计入可用存量，但保留实物记录和位置占用；不自动视为已处置，释放位置须通过后续明确操作 |
| 日期精度 | 生产日期、有效期按日表达，有效期当天仍有效；开封时间和系统操作时间按时刻表达 |
| 有效期含义 | 明确区分未知、无期限和指定到期日期；未填写默认为未知，不等于永久有效。生产日期、开封时间未知时允许留空，不编造日期 |
| 业务时区 | MVP 使用部署级统一业务时区，默认 Asia/Shanghai、可配置；有效期到该时区次日零点才过期，不随浏览器时区变化，本轮不增加组织级时区管理界面 |
| 实例日期 | 入库时以批次生产日期/有效期作为默认值，允许为本件实物明确覆盖，最终保存到实例；后续批次修改不静默改变已登记实例日期，实例资料纠正走单独、带审计的修改 |
| 已开封与过期存量 | 两者均允许登记；已过期实物提交时必须明确确认，并在库存中展示过期风险。登记成功不表示允许继续领用，领用限制留 P11 确认 |
| 历史到货 | 可选填实际到货日，未知留空；入库流水与审计记录服务端实际登记时间，不回溯库存生效时间、不补造历史领用流水 |
| 实例编号 | 系统默认生成，允许入库前手工指定；工作区内唯一，创建后不修改，历史编号不复用 |
| 编号边界 | 实例编号、材料编号、来源批号与入库流水号各自独立；实例编号不编码当前位置 |
| 批次 | 某一种材料的厂家或来源批次，可选，不等于一次入库；同一批次允许分多次入库 |
| 批号唯一性 | 同一材料下批号唯一，不同材料可以重复 |
| 批次选择 | 入库时选择已有批次或明确新建批次，不因批号相同悄悄覆盖已有资料；新建的竞态处理不得变成隐式修改 |
| 入库提交 | 一次提交登记一件实物，必须选择有权使用的真实空 POSITION；同批次可连续登记，无位置入库、暂存区和多件整体提交不在本轮，批量能力留 P13 |
| 资料更正 | 可更正标签、备注、生产日期/有效期、开封时间和实际到货日；必须填写原因并留下审计，不通过普通编辑修改材料/批次归属、实例编号、初始数量、当前数量或位置 |
| 库存事实与历史 | 不删除或重写已提交流水；数量与位置的后续修正留 P11 明确操作，不以资料编辑替代库存执行 |
| 基本权限 | 读取库存、登记入库、维护批次、纠正实物资料分别授权，不因可编辑材料就自动获得全部库存权限；库存读取/操作另要求能读该材料，入库另要求目标设施使用权 |
| 新建批次权限 | 有入库权但无批次维护权时，可不填批次或选择已有批次；新建批次须额外具有批次维护权，不能借内联表单绕过 |
| 材料与批次归档 | 停止以已归档材料或批次登记新实物，但保留已有实例、库存、占位与历史；有权用户仍可查看并通过库存操作移动或移出实物，不以归档代替耗尽、处置或释放位置；P09 不开放实例归档/删除入口，具体领用限制留 P11 |
| 当前位置 | 沿用 P08：一件实物最多占一个 POSITION，一个 POSITION 同时最多放一件实物；位置预检不是位置预留 |
| 所有权 | 材料与库存的工作区归属不因使用共享设施或容器搬迁而改变；可见位置不代表可见其他工作区的材料明细 |
| 混合存量搬迁 | MVP 允许同组织内混合工作区存量的容器整体搬迁；操作者须有来源和目标设施结构管理权，并在每个受影响工作区具备有效成员资格、库存读取/转移及材料读取权限，目标设施须向这些工作区全部开放使用。任一条件不满足整次拒绝，不泄露无权材料明细；组织所有者不自动绕过 |

## 3. 接下来的对齐顺序

### 数量与日期：本轮口径已确认

本节已收口到上表：材料级数量精度、零量实物、按日有效期及业务时区、实例确认日期、未知与无期限、历史到货日与真实登记时间。实施方案将据此列出合法日期组合和精确数量校验，不扩大为单位换算、开封后效期推导或历史库存重放。

### 写入边界与基本权限：本轮口径已确认

单件提交、必须选空位置、资料与库存事实分开更正、独立权限、批次内联新建的额外授权及归档保留既有库存均已确认。混合工作区存量的搬迁采用上表授权交集。

### 带存量搬迁：沿用 P08 的事务边界

P08 已确认同组织子树搬迁保持节点及实物身份、Placement 所指位置、数量和工作区所有权；带存量迁移由库存编排，各工作区流水分别归属其真实工作区，并与结构和审计处于同一次物理事务。任一步失败整次回滚，不将 P13 的逐项批量能力提前混入容器整体迁移。普通结构接口仍拒绝有占用子树。这些既定边界不重新假设为用户尚未选择的建议。

用户已接受 MVP 采用全部相关工作区授权取交集、目标设施向各库存所属工作区开放的规则，同时提出治理上下文迁移是否合理的问题。下节明确所有权与治理关系的区别，不将这项批准泛化为任意业务实体均可变更 scope。

最终方案同时写清重复提交、位置竞争、提交成功但响应丢失的结果；不会将一次结构移动冒充库存搬迁完成，也不会借本轮开放尚未确认的领用、归还和库存调整。

## 4. 与实施前模型的对照

下表记录对齐时的差异，不代表当前仍未实现。后续实际模型和数据库操作见交付记录。

| 当前事实 | 对齐时需要处理的内容 |
| --- | --- |
| MaterialInstance.code 已有工作区唯一约束 | 系统编号生成、创建后不可改和历史编号不复用仍须由实际用例落实，不能视为已有完整能力 |
| MaterialBatch 已有同材料批号唯一约束 | 查询、选择、新建与并发冲突的实际接口尚须在 P09 实现 |
| Material 只有单位字段，尚无数量精度字段 | 已确认增加 0～6、默认 6 的材料级数量精度，已有实例后与单位一样冻结；涉及 P07 材料资料和公开契约的扩展，尚未改运行代码 |
| initialQuantity 与当前 StockItem.quantity 分开 | 初始数量按首次登记实存量且允许为 0；零量为 DEPLETED 且保留占位；普通资料编辑不能改初始数量、当前数量或位置，后续库存修正留 P11 |
| 生产、有效期和开封字段目前均为时间戳，实例没有生产日期字段 | 生产日期和有效期已确认按日，实例保存确认日期；实施时须调整日期字段语义、存储及实例生产日期，不能伪装成 UTC 零点。过期判断使用部署级业务时区 |
| 可空 expiresAt 不能区分未知和无期限，实例没有到货日字段 | 已确认有效期三态和可选实际到货日，须显式扩展模型与契约；到货日不能替换系统登记时间 |
| 原设计说明提出实例有效期覆盖批次有效期、否则动态继承 | 本轮已改为实例入库时确认并保存日期，批次变更不静默影响已登记实例；这是设计规则调整，尚未修改运行代码或数据库 |
| 库存接口仍为骨架，精确数量解析已有实现 | 本文不声称真实入库、流水、幂等业务适配或库存页面已经可用 |

具体模型改动、模块职责和交付顺序见 [实施方案](mvp-p09-plan-2026-10-19.md)；获准执行后的 Schema/DDL、合成写入和验证边界另载于交付记录，不扩大为其他环境的授权。

## 5. 搬迁改变什么，不改变什么

这里需要区分租户归属、库存工作区归属与设施治理关系。它们不是同一种 scope：

| 边界 | 同组织跨设施搬迁的结果 |
| --- | --- |
| Organization 租户归属 | 不变；本轮不允许跨组织搬迁 |
| 材料、批次、实例与库存的 workspaceId | 不变；不发生所有权调拨或材料跨工作区共享 |
| 存储节点的组织级资源归属与 ID | 不变；不是重建实物、节点或 ResourceIdentity |
| 节点所在设施、拓扑与路径 | 可通过合法搬迁改变；不能用普通资料编辑任意改归属 |
| 当前结构治理与可见范围 | 按目标设施的现有管理、共享关系重新判断，确实可能变化；不能宣称搬迁完全没有权限影响 |
| 材料与库存明细可见性 | 仍受原工作区及材料/库存读取授权约束；目标设施管理员不因接收容器自动获得明细读取权 |

因此，这项能力是“同租户内的存储结构搬迁，伴随设施治理上下文变化”，不是通用的租户/所有权转移功能。现实中冰箱和盒子会整体迁移，保留身份比复制重建更符合连续追踪，但需承担治理范围变化的处理成本。

实施方案须保留以下约束：搬迁是显式业务命令而非通用改父节点；提交前展示来源、目标、受影响存量及设施治理/结构可见范围变化；提交时在统一写事务中重新鉴权、检查修订并原子记录结构、分工作区流水和审计。预检不是授权凭据，历史位置使用当时的快照，不能按新父节点重解释旧流水。

设施结构的名称、路径、占用等信息会按目标设施规则开放，这与材料内容保密是不同层面。不能只保证后者便忽略结构信息的可见范围变化。用户已接受这项受控治理边界迁移的合理性及以上约束。实施方案明确 MVP 沿用来源/目标管理资格与各工作区授权交集，不增加超级搬迁权、审批或越权代办机制。

将来接入节点级授权、在途审批、盘点和设备绑定时，各业务必须明确搬迁对其作用域和有效性的影响；不能假设所有关联只要保留外键就语义不变。本轮不提前实现这些未来机制。

相似产品的公开机制只用于说明这类操作并非不可设计，不代表可以照搬权限语义：[GitHub 仓库转移](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository)要求来源和接收侧权限，转移后适用目标组织默认权限；[Notion 分享与权限](https://www.notion.com/help/sharing-and-permissions)说明了页面继承权限及移动到 Private 后访问关系的变化。库存业务仍需独立保证实物、数量、位置与历史一致。
